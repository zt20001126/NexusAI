# 会话与消息表结构设计提案

- 状态：设计提案，尚未应用
- 范围：会话、消息及其与 Agent 运行记录之间的关系
- 当前实现：见[数据库结构说明](数据库表结构.md)

## 设计目标

- 会话 ID 和消息 ID 在数据库中使用自动生成的纯数字主键。
- 消息表不保存 `sequence` 等独立排序字段；历史记录按 `created_at` 展示。
- 消息正文以 PostgreSQL `JSONB` 保存，便于验证结构并为多模态内容扩展。
- 分页在相同创建时间下仍有稳定顺序，避免漏项或重复。

## ID 的生成与传输

建议 `conversations.id` 和 `messages.id` 使用 `BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`。PostgreSQL 在插入记录时从 identity 序列分配整数，应用不再生成 UUID 主键。身份序列允许有空号；ID 只用于唯一标识，不承诺连续，也不代替消息时间。

数据库中的 ID 类型是整数。对外 API 和前端建议以十进制数字字符串传输，例如 `"123456789012345678"`，字符串只含数字。PostgreSQL `BIGINT` 的取值范围大于 JavaScript `Number` 可精确表示的范围，若把较大的 ID 作为 JSON 数字传给浏览器，可能发生精度丢失。前端因此应保留字符串，不应将 ID 转成 `Number`。

数据库主键列统一命名为 `id`；API 字段名继续使用 `conversation_id` 和 `message_id`，只调整其值为十进制数字字符串，减少无关的字段命名变更。

`agent_runs.run_id` 暂时保持现有 UUID 文本主键；本提案只将其 `conversation_id` 外键改为 `BIGINT`，以匹配会话主键。

## 目标表结构

### `conversations`

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGINT` | Identity，主键 | 数据库自动生成的数字会话 ID |
| `owner_id` | `TEXT` | 非空 | 会话所属可信主体 |
| `title` | `TEXT` | 可空 | 会话标题 |
| `created_at` | `TIMESTAMPTZ` | 非空，默认当前时间 | 会话创建时间 |
| `updated_at` | `TIMESTAMPTZ` | 非空，默认当前时间 | 最近更新时间 |

建议索引：`(owner_id, updated_at DESC, id DESC)`，供会话列表按最近更新时间倒序查询，并用 `id` 处理相同时间的稳定顺序。

### `messages`

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGINT` | Identity，主键 | 数据库自动生成的数字消息 ID |
| `conversation_id` | `BIGINT` | 非空，外键 | 关联 `conversations.id`，删除会话时级联删除 |
| `run_id` | `TEXT` | 可空，外键 | 关联产生该消息的 Agent 运行；用户消息可关联本轮运行 |
| `role` | `TEXT` | 非空，仅允许 `user`、`assistant` | 消息角色 |
| `content` | `JSONB` | 非空 | 结构化消息内容 |
| `created_at` | `TIMESTAMPTZ` | 非空，默认当前时间 | 消息创建时间 |

不再创建 `sequence` 字段，也不保留 `(conversation_id, sequence)` 唯一约束。

建议 `content` 采用带版本号和内容片段的对象：

```json
{
  "version": 1,
  "parts": [
    { "type": "text", "text": "你好，世界" }
  ]
}
```

当前文本消息使用 `type: "text"`。将来需要图片、附件或其他内容时，可在 `parts` 中增加明确类型的片段；由 Pydantic/API 层校验对象版本、片段类型和必需字段。数据库至少应确保 `content` 是非空 JSON 对象，具体约束强度应与应用校验同步。

建议索引：`(conversation_id, created_at DESC, id DESC)`，支持单个会话的历史分页。`id` 只用于 `created_at` 相同时确定稳定顺序，不是另一个业务排序字段。

### `agent_runs` 的关联字段

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `run_id` | `TEXT` | 主键 | 保留现有 UUID 文本标识 |
| `conversation_id` | `BIGINT` | 非空，外键 | 关联 `conversations.id` |
| `status` | `TEXT` | 非空 | 运行状态 |
| `metadata` | `JSONB` | 非空，默认空对象 | 运行恢复所需元数据 |
| `created_at` | `TIMESTAMPTZ` | 非空，默认当前时间 | 运行创建时间 |
| `updated_at` | `TIMESTAMPTZ` | 非空，默认当前时间 | 最近状态变更时间 |

此处列出 `agent_runs` 是为了说明会话 ID 类型变化带来的外键联动，不代表要在本次提案中重设计 AgentRunner 或运行生命周期。

建议索引：`(conversation_id)`，支持按会话查询运行记录，并避免关联查询扫描整张运行表。

## PostgreSQL 建表参考

以下 DDL 展示目标字段与主要约束；实施时还需按现有迁移框架和部署策略编写正式 migration。

```sql
CREATE TABLE conversations (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    owner_id TEXT NOT NULL,
    title TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE agent_runs (
    run_id TEXT PRIMARY KEY,
    conversation_id BIGINT NOT NULL
        REFERENCES conversations(id) ON DELETE CASCADE,
    status TEXT NOT NULL,
    metadata JSONB NOT NULL DEFAULT '{}'::jsonb,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE messages (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    conversation_id BIGINT NOT NULL
        REFERENCES conversations(id) ON DELETE CASCADE,
    run_id TEXT REFERENCES agent_runs(run_id),
    role TEXT NOT NULL CHECK (role IN ('user', 'assistant')),
    content JSONB NOT NULL CHECK (jsonb_typeof(content) = 'object'),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_conversations_owner_updated
    ON conversations (owner_id, updated_at DESC, id DESC);

CREATE INDEX idx_agent_runs_conversation_id
    ON agent_runs (conversation_id);

CREATE INDEX idx_messages_conversation_created
    ON messages (conversation_id, created_at DESC, id DESC);
```

## 消息历史查询与分页

首次查询和后续查询统一按 `(created_at, id)` 倒序取一页：

```sql
SELECT id, conversation_id, run_id, role, content, created_at
FROM messages
WHERE conversation_id = :conversation_id
  AND (
    :before_created_at IS NULL
    OR (created_at, id) < (:before_created_at, :before_message_id)
  )
ORDER BY created_at DESC, id DESC
LIMIT :page_size;
```

服务端把结果反转后按时间正序交给聊天界面。下一页游标由本页最旧一条消息的 `created_at` 与 `id` 组成；两个值一起比较，才能在多条消息时间相同的情况下可靠翻页。游标是请求分页所需的数据，不需持久化为表字段。

## 迁移时必须联动的部分

本提案没有修改数据库、API 或前端。正式实施前至少需要同步迁移：

1. 为现有会话和消息分配新的整数 ID，并保留旧 ID 到新 ID 的映射；同步调整 `agent_runs.conversation_id` 外键和历史索引。
2. 将现有文本消息转换为版本化 JSON 对象，并明确处理空值、特殊内容和无法解析的历史数据。
3. 修改持久化读写、Pydantic 响应模型、控制器游标参数、前端 API 类型和消息渲染映射。
4. 将 LangGraph Checkpointer 使用的会话 `thread_id` 与迁移后的会话 ID 对齐。当前运行流程把可信主体和会话 ID 组合为图线程标识，因此需要保留或重映射该关联，并验证已有 checkpoint 能继续恢复，不能只改业务表主键。
5. 做兼容部署和备份/回滚设计，确认历史会话、运行记录和 checkpoint 的关联均可读取后再切换。

## 决策摘要

- ID：数据库使用 `BIGINT IDENTITY`；HTTP/JSON 以只含数字的字符串传输，避免 JavaScript 精度问题。
- 排序：删除消息 `sequence`；展示与分页依据 `created_at`，以消息 ID 作同时间的稳定比较键。
- 内容：`content JSONB` 保存带版本的结构化对象；文本是 `parts` 中的一种片段。
- 实施状态：仅完成设计文档；需要另行实现迁移和应用适配后，才能把该提案视为生效结构。
