# 数据库结构说明

本文记录应用直接管理的 PostgreSQL 表。运行时模型定义位于 `backend/app/models/`，由 `backend/app/db/database.py` 初始化；已有数据库的升级脚本位于 `backend/migrations/`。LangGraph Checkpointer 的内部表由官方适配器管理。

## ID 约定

- 应用业务表中的主键和关联 ID 使用 PostgreSQL `BIGINT` 保存雪花 ID。
- API 将雪花 ID 作为十进制字符串传输，避免 JavaScript `Number` 精度损失。
- 智能体类型由共享字符串枚举 `AgentType` 定义，数据库只在 `conversations.agent` 保存枚举值；运行和任务结果通过会话读取智能体，不重复存储智能体字段。
- 当前认证上下文提供的是可信主体字符串。`users.account` 保存该映射值并对应内部雪花用户 ID；业务表仍使用 `user_id` 作为所有者 ID。
- `SNOWFLAKE_WORKER_ID` 必须在同时运行的后端进程间唯一，允许范围为 0–1022；1023 为历史数据迁移保留。

## 表及关系

| 表 | 用途 | 主要关系 |
|---|---|---|
| `users` | 用户账号、密码哈希和角色 | 一个账号对应一个内部用户 ID |
| `user_credits` | 用户当前积分余额及缓存版本 | 每个用户一行 |
| `credit_entries` | 注册赠送、对话扣费和退款明细 | 多条明细属于一个用户 |
| `credit_topups` | 支付尝试及 Stripe Checkout Session 状态 | 多次尝试属于一个用户；Session ID 唯一 |
| `conversations` | 会话归属、标题、智能体和时间 | 一个会话包含多条消息和多次运行 |
| `messages` | 用户消息和助手回复 | 属于一个会话，可关联运行 |
| `agent_runs` | 智能体运行状态和恢复元数据 | 属于一个会话 |
| `task_results` | 所有智能体共享的任务结果及 JSON 元数据 | 关联会话和可选消息；所有者及智能体从会话读取 |
| `resumes` | 简历助手的内容和排版配置 | 每个 `users.user_id` 最多一份简历 |
| `literature_documents` | 文献来源、OSS 对象及导入状态 | 关联文献所有者 |
| `literature_chunks` | 文献正文、位置和 1024 维向量 | 关联文献并级联删除 |
| `literature_conversation_documents` | 文献助手会话的当前文献选择 | 关联会话和文献 |

参考图、生成图和 PDF 原件只存放在私有阿里云 OSS Bucket 中，不把文件字节写入 PostgreSQL。图片 OSS 元数据按用途保存在 `task_results.input` 和 `task_results.result` JSONB 中；文献对象键保存在 `literature_documents.object_key`。

## `users`

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `user_id` | `BIGINT` | 主键 | 内部雪花用户 ID |
| `account` | `TEXT` | 非空、唯一 | 账号；当前兼作可信主体映射值 |
| `password_hash` | `TEXT` | 可空 | 密码哈希；既有账号未设置密码时为空 |
| `role` | `TEXT` | 非空，默认 `user`，仅 `user`、`admin` | 用户角色 |
| `created_at` | `TIMESTAMPTZ` | 非空 | 账号创建时间 |

现有库升级时执行 `backend/migrations/008_user_accounts.sql`。迁移将 `user_identities` 重命名为 `users`、把 `external_principal` 重命名为 `account`，并保留原用户 ID、账号值、创建时间及外键关系。旧记录没有本地密码凭据，因此 `password_hash` 对这类记录为空；设置密码后再用于本地密码认证。全新数据库由 ORM 直接创建 `users` 表。

邮箱注册账号将规范化的小写邮箱保存为唯一 `account`，密码仅保存 scrypt 哈希。验证码和临时会话均由现有 Redis 服务使用 TTL 管理，不新增认证数据库表；验证码仅存 pepper HMAC 摘要，Redis 会话绑定当前密码哈希指纹。重置密码后旧会话指纹自动失效，退出时删除当前 Redis 会话键。已有数据库若包含早期版本创建的 `email_verification_codes` 或 `auth_sessions` 表，可执行 `backend/migrations/017_redis_auth_state.sql` 清理；新部署无需认证表迁移。

新注册账号在创建用户的同一事务中创建 `user_credits` 余额 100 和一条 `registration_grant` 明细。通过其他旧身份映射创建的用户余额为 0。启用计费时先执行 `backend/migrations/018_user_credits.sql`；迁移为所有现有账号补建 0 分余额，不生成赠送明细。运行时 `create_all` 不会替代该迁移。

## `user_credits`

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `user_id` | `BIGINT` | 主键、外键到 `users.user_id`，删除用户时级联 | 每个用户唯一的积分账户 |
| `balance` | `BIGINT` | 非空，默认 0，检查 `>= 0` | 当前可用积分 |
| `version` | `BIGINT` | 非空，默认 0，检查 `>= 0` | 每次变更递增，用于阻止 Redis 旧快照覆盖新值 |
| `updated_at` | `TIMESTAMPTZ` | 非空，默认当前时间 | 最近一次余额更新时间 |

新注册账户的初始余额和版本分别为 100、1；迁移补建的旧账户为 0、0。新对话事务锁定该行，并在同一事务内扣费；数据库余额是账务事实来源，Redis 只缓存余额和版本。

## `credit_entries`

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `event_key` | `TEXT` | 主键 | 全局幂等键：`grant:<user_id>`、`debit:<run_id>`、`refund:<run_id>` 或 `top_up:<top_up_id>` |
| `user_id` | `BIGINT` | 非空，外键到 `users.user_id` | 积分所属用户 |
| `run_id` | `BIGINT` | 可空 | 对话扣费和退款关联的运行 ID；注册赠送和充值为空 |
| `kind` | `TEXT` | 非空，仅 `registration_grant`、`message_debit`、`run_refund`、`top_up` | 积分事件类型 |
| `delta` | `BIGINT` | 非空；原事件分别为 +100、-1、+1，充值为任意正整数 | 本次积分变化量 |
| `balance_after` | `BIGINT` | 非空，检查 `>= 0` | 本次事件提交后的余额 |
| `created_at` | `TIMESTAMPTZ` | 非空，默认当前时间 | 明细创建时间 |

索引 `(user_id, created_at)` 支持按用户核对明细；索引 `(run_id, kind)` 支持按运行查找扣费及退款记录。新对话受理在单个事务内写入用户消息、queued run、余额扣减和 `message_debit`；失败或主动取消时按 `run_id` 幂等写入 `run_refund` 并返还 1 分。SSE 断开不改变运行状态，也不产生退款。`backend/migrations/018_user_credits.sql` 同时创建两张表并为已有用户补建零余额行。

## `credit_topups`

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `top_up_id` | `BIGINT` | 主键 | 充值尝试雪花 ID，API 使用十进制字符串 |
| `user_id` | `BIGINT` | 非空，外键到 `users.user_id`，删除用户时级联 | 充值归属 |
| `request_id` | `TEXT` | 非空；与 `user_id` 组合唯一 | 客户端重试幂等键 |
| `currency` | `TEXT` | 三位小写币种代码 | Stripe presentment 币种 |
| `amount` | `BIGINT` | 正整数 | 用户金额主单位及充值积分数 |
| `stripe_amount` | `BIGINT` | 正整数 | 按 Stripe 规则换算后的最小单位金额 |
| `stripe_session_id` | `TEXT` | 可空、唯一 | Stripe Checkout Session 关联 |
| `checkout_url` | `TEXT` | 可空 | 浏览器跳转地址；待支付时可供同请求重试 |
| `status` | `TEXT` | `pending`、`paid`、`failed`、`expired` | 支付尝试状态 |
| `created_at`、`updated_at` | `TIMESTAMPTZ` | 非空 | 创建及最近更新时间 |

迁移既有数据库时，018 后执行 `backend/migrations/019_credit_topups.sql`。成功 Webhook 在同一事务内锁定充值尝试和用户余额，更新状态及余额，并以 `top_up:<top_up_id>` 写入唯一明细；重复通知不会重复增加余额。新表无需历史回填。

## `conversations`

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `conversation_id` | `BIGINT` | 主键 | 会话雪花 ID |
| `owner_id` | `BIGINT` | 非空，外键 | 关联 `users.user_id` |
| `agent` | `VARCHAR(64)` | 非空，受枚举检查约束 | `AgentType` 字符串值，如 `common_agent` |
| `title` | `TEXT` | 可空 | 根据首条用户消息生成的会话标题 |
| `created_at`、`updated_at` | `TIMESTAMPTZ` | 非空 | 创建及最近更新时间 |

索引：`(owner_id, updated_at DESC)`。

已有数据库在启用 `job_agent` 前执行 `backend/migrations/016_job_agent_conversation_type.sql`，扩展 `ck_conversations_agent_type` 检查约束以允许求职会话。全新数据库由当前 ORM 中的 `AgentType` 创建同等约束。

## `messages`

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `message_id` | `BIGINT` | 主键 | 消息雪花 ID |
| `conversation_id` | `BIGINT` | 非空，外键 | 所属会话，删除会话时级联删除 |
| `role` | `TEXT` | 非空，仅 `user`、`assistant` | 消息角色 |
| `content` | `JSONB` | 非空 | 按顺序保存含稳定块 ID 的文字、图片、追问和任务结果内容块 |
| `created_at` | `TIMESTAMPTZ` | 非空 | 创建时间 |

索引 `(conversation_id, created_at DESC, message_id DESC)` 支持稳定的历史分页；相同创建时间按消息 ID 排序。助手消息在首次文本增量前创建；增量按同一 `message_id/block_id` 更新 JSONB，完整快照与消息历史保持一致。心跳和工具进度不作为消息记录保存。历史 JSONB 中缺少块 ID 的内容由历史接口确定性补齐，不需要迁移数据。

升级已有数据库时依次执行 `backend/migrations/006_message_context.sql` 和 `backend/migrations/007_rename_message_context_to_content.sql`：先把旧文字转成 JSON 内容块并回填历史图片引用，再将 JSON 字段命名为 `content`。原文本列和 `run_id`、`sequence` 及可能存在的 `attachment_ids` 会被移除。旧追问答案以历史 `question_answers` 块保留；新写入的追问和答案使用 `question` 块。图片字节仍留在私有 OSS，访问接口同时校验会话所有权和消息中的图片引用。

## `agent_runs`

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `run_id` | `BIGINT` | 主键 | 一次运行的雪花 ID |
| `conversation_id` | `BIGINT` | 非空，外键 | 所属会话 |
| `status` | `TEXT` | 非空 | `queued`、`running`、`waiting`、`completed`、`cancelled` 或 `failed` |
| `metadata` | `JSONB` | 非空，默认空对象 | 结果 ID、附件 ID、待回答问题等恢复元数据 |
| `created_at`、`updated_at` | `TIMESTAMPTZ` | 非空 | 创建及最近更新时间 |

索引：`(conversation_id)`，以及对按可信主体和 request_id 计算的 `metadata->>'request_key'` 的部分唯一索引，用于提交幂等。运行的智能体从所属会话的 `agent` 字段读取；恢复运行时还会校验会话、用户、状态和智能体归属。`queued` 和 `running` 对应 Celery Agent Worker 生命周期，SSE 连接状态不会改变运行状态。

已有数据库升级时执行 `backend/migrations/011_agent_stream_resume.sql`，该迁移允许 `queued` 状态并建立请求幂等索引，不删除或重建运行和消息记录。全新数据库会由当前 ORM 元数据创建相同约束和索引。

## `task_results`

这是所有智能体共用的任务结果表。新增业务专属结果时优先扩展 JSON 元数据，不新建只存输出文件的表。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGINT` | 主键 | 任务结果雪花 ID |
| `conversation_id` | `BIGINT` | 非空，外键 | 所属会话，删除会话时级联删除 |
| `message_id` | `BIGINT` | 可空，外键 | 关联助手问题或最终回复消息 |
| `status` | `TEXT` | 非空，受限值 | `pending`、`awaiting_input`、`running`、`succeeded`、`failed` 或 `cancelled` |
| `input` | `JSONB` | 非空，默认空对象 | 业务输入摘要及所需对象元数据 |
| `result` | `JSONB` | 非空，默认空对象 | 图片 OSS 元数据或完整业务结果 JSON |
| `created_at` | `TIMESTAMPTZ` | 非空 | 创建时间 |

索引：`(conversation_id, created_at)`、`(message_id)`。

结果所有者通过 `conversation_id` 关联的 `conversations.owner_id` 校验；智能体通过 `conversations.agent` 推导。`result_type` 由会话智能体类型推导，不单独持久化。运行 ID 仅用于写入时验证运行上下文，不保存在本表。

表中不再有 `image_url`、`image_data`、`input_files`、`result_files` 或 `error_data` 等独立列。图片不保存在数据库字节字段中；JSON 里的对象键指向私有 OSS，图片读取接口会校验会话所有者后从 OSS 读取。失败原因仅通过安全的 API/SSE 响应返回，不作为任务结果错误字段持久化。

## `resumes`

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGINT` | 主键、自增 | 简历记录 ID，不作为前端身份字段返回 |
| `owner_id` | `BIGINT` | 非空、外键、唯一 | 关联 `users.user_id`；用户删除时级联删除 |
| `content` | `JSONB` | 非空、顶层为对象 | 基本信息、教育、专业技能、工作和项目；技能、工作和项目内容均为受限 Tiptap JSON |
| `style_config` | `JSONB` | 非空、顶层为对象 | 简历字体、字号、颜色、间距和页面边距 |
| `created_at`、`updated_at` | `TIMESTAMPTZ` | 非空 | 创建及最近更新时间 |

唯一约束 `uq_resumes_owner_id` 保证一个用户只有一份简历；JSONB 检查约束拒绝非对象顶层值。`content.basic_info` 保存联系方式、求职意向、可空整数 `age`（0–120）、可空整数 `work_experience_years`（0–80）和证件照 `photo_id`；年龄和工作经验年限由用户手动填写。出生年月不再属于当前 JSON 契约。页首学历由 `content.educations` 中第一条学历文本非空的记录提供。专业技能、工作和项目描述保存经过后端白名单校验的 Tiptap JSON；技能最多 10,000 字符，单条工作或项目文档最多 4,000 字符，全简历富文本合计最多 20,000 字符。旧版技能 `string[]` 由 `backend/migrations/015_resume_skills_tiptap.sql` 转换为段落文档；当前 Compose 数据库已执行迁移。应用新版 API 前，其他已有数据库也必须执行此迁移；API 不再接受旧版数组载荷。每个邮箱账号映射到自己的 `users.user_id` 并拥有独立简历。原固定主体 `nexusai-resume-owner` 的简历保留原所有者，不会自动关联到任何新账号。

已有数据库执行 `backend/migrations/013_resumes.sql` 新增此表；后续依次执行 `backend/migrations/014_resume_profile_fields.sql` 移除已有简历 JSON 中的 `birth_month`，以及 `backend/migrations/015_resume_skills_tiptap.sql` 将技能字符串数组转换为 Tiptap 段落文档。015 在事务中锁定 `resumes` 表，校验旧数组最多 20 项且每项不超过 500 字，保持原条目顺序和空项，并保留 `updated_at`。当前 Compose 数据库已应用 015。014 不会根据出生年月推算年龄，新增年龄和工作经验字段由模型以空值默认。全新数据库启动时由 ORM 元数据创建同等表结构；显式迁移不改变表列。照片字节不写入本表，照片通过 `photo_id` 引用私有 OSS 对象。

## 文献解读助手表

`literature_documents` 保存文献所有者、私有 OSS 对象键、文件摘要和导入状态。新建文献只通过 PDF 上传，因此 `source_type` 为 `pdf_upload`。`source_url` 和 `pdf_url`/`web_url` 来源类型仅为兼容既有链接导入记录保留；新接口不再创建此类记录。状态为 `queued`、`processing`、`ready` 或 `failed`；只有 `ready` 文献可被问答检索。

`literature_chunks` 保存解析后的原文分块、章节和节标题、PDF 页码范围、页内段落范围以及 `VECTOR(1024)` 向量。`(document_id, chunk_index)` 唯一；对文献 ID 和向量余弦距离建检索索引。既有网页来源文献可能没有页码和段落；新上传 PDF 按解析结果生成可用位置。

`literature_conversation_documents` 用 `(conversation_id, document_id)` 保存会话当前选择。所有查询都通过会话所有者、文献所有者和文献 ready 状态校验；删除文献时级联清理分块与会话选择，历史消息本身仍保留。

升级已有数据库时执行 `backend/migrations/005_literature_reader.sql`。该迁移要求 PostgreSQL 已安装 pgvector；Compose 使用的 `pgvector/pgvector:pg17` 镜像包含该扩展。

### Listing 任务结果

Listing Agent 不增加专用结果表。成功任务将 schema_version、商品事实、视觉识别结果和 3 个版本的标题、卖点、纯文本详情描述、关键词及商品属性完整写入 task_results.result JSONB；任务输入摘要保存在 input。视觉分析所需图片从私有 OSS 读取，图片字节不会写进 PostgreSQL。结果读取 API 使用会话所有者校验。

全新数据库由当前 ORM 模型创建目标结构。旧版 `backend/migrations/009_task_results_compact_schema.sql` 会删除并重建 `task_results`，不迁移旧表数据；仅当确认可以清除已有任务结果时才使用。

数据库仍处于 `task_result_id`、`generation_status` 和 `conversations.agent_id` 旧结构时，先停止后端和 Worker，再执行 `backend/migrations/012_legacy_schema_data_preserving_upgrade.sql`。该迁移原位转换任务结果字段，保留已有任务结果 JSON 和会话/消息关联，并完成智能体字符串映射、运行状态约束及请求幂等索引；所有权、运行关联、智能体 ID 或状态不符合预期时会回滚。不要在有重要任务结果的数据库上先执行 009。

若数据库已经使用当前 `task_results` 字段，但会话仍使用旧 `agent_id`，先停止旧版后端，再执行 `backend/migrations/010_agent_type_strings.sql`，最后执行 `backend/migrations/011_agent_stream_resume.sql` 并部署新版。010 支持项目历次静态雪花 ID 映射；未知值或会话与运行的智能体不一致时会中止。

## OSS 对象组织

Bucket 应设置为私有。代码将文件存放在 `ALIYUN_OSS_OBJECT_PREFIX` 下的 `staged/`、`references/`、`generated/`、`resume/<主体摘要>/staged/`、`resume/<主体摘要>/final/` 和 `literature/<主体摘要>/<文献 ID>.pdf` 前缀，并将用户主体摘要写入对象路径与 OSS 元数据，避免把认证主体原文放入对象键。简历照片先进入 staging，数据库保存新 `photo_id` 后再清理旧照片；Bucket 生命周期规则应在 `resume/<主体摘要>/staged/` 前缀下配置 7 天过期。生成图片通过 `/api/task-results/{task_result_id}/image` 返回，不向前端暴露 OSS 公共地址或 TokenHub 临时地址。

所需配置为 `ALIYUN_OSS_ACCESS_KEY_ID`、`ALIYUN_OSS_ACCESS_KEY_SECRET`、`ALIYUN_OSS_ENDPOINT`、`ALIYUN_OSS_BUCKET` 和可选的 `ALIYUN_OSS_OBJECT_PREFIX`。访问密钥应使用 RAM 用户并限制到目标 Bucket 所需的读写权限；不要把密钥提交到 Git。

## 从 TEXT ID 和 BYTEA 图片升级

`003_snowflake_ids_oss_task_results.sql` 是一次性迁移。它要求先停止运行中的任务，并且所有旧图片字节已转存 OSS。建议按以下顺序执行：

1. 备份 PostgreSQL 数据库，并确认 OSS Bucket 为私有且后端已配置有效密钥。
2. 在 `backend/` 目录运行 `python -m migrations.migrate_media_to_oss`。脚本把旧 `task_results.image_data` 和 `message_attachments.image_data` 写入 OSS；只有每项写入成功后，才在数据库事务中清空/删除旧字节。
3. 确认脚本成功后，在旧数据库执行 `migrations/003_snowflake_ids_oss_task_results.sql`。
4. 部署当前后端，并为每个并发后端进程设置唯一的 `SNOWFLAKE_WORKER_ID`。

SQL 会把会话、消息、运行、用户和任务结果 ID 迁移到雪花 BIGINT，保留关联和兼容的 Checkpoint 线程标识，移除旧附件表及图片字节列。若旧数据的所有者或智能体关系不一致，迁移会中止并报告，不会猜测修复。此迁移只用于旧 TEXT/ BYTEA schema；空白数据库由当前版本的运行时建表代码直接创建目标结构，不应对它运行 003。

LangGraph Checkpointer 自有的内部 ID/键继续按框架类型保存，不属于应用业务表 ID。
