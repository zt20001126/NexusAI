# 邮箱注册登录与首页实现方案

> 日期：2026-10-22（Asia/Shanghai）
> 状态：需求已确认；实施过程中按用户反馈修订认证状态存储方案
> 需求确认：邮箱验证码注册、邮箱密码登录、邮箱验证码重置密码、智能体介绍首页；采用 HttpOnly Cookie 登录态；简历按邮箱账号隔离。

## 实施阶段设计修订（2026-10-22）

用户指出 `users` 表已经以邮箱作为账号并包含密码字段，新增验证码表和会话表属于不必要的数据库结构。本次实施采用以下最终方案，本文后续原始设计章节中涉及新增认证 SQL 表的内容均以本节为准：

- 账号邮箱和 scrypt 密码哈希复用现有 `users.account`、`users.password_hash`，不新增认证 PostgreSQL 表。
- 一次性验证码、重发冷却和不透明 Cookie 会话使用项目已有 Redis，通过 TTL 管理；验证码只保存 pepper HMAC 摘要。密码哈希指纹绑定会话，密码重置后旧会话自动失效，退出时删除当前会话键。
- `backend/migrations/017_redis_auth_state.sql` 仅用于清理早期迭代生成的空 `email_verification_codes`、`auth_sessions` 表；新部署无需执行认证表迁移。

本节描述实际实现采用的决策，前文与后文保留为需求澄清及最初方案的历史记录。

## 1. 目标与背景

- **要解决的问题：**当前前端直接进入聊天或简历页面，开发模式以固定 `local-development` 主体工作；项目没有账号注册、登录和密码找回流程。简历接口还使用固定主体 `nexusai-resume-owner`，不能安全地供多个邮箱账号分别使用。
- **功能目标：**以邮箱验证码完成注册和密码找回，以邮箱＋密码登录；未登录访问者先看到左侧智能体目录、右侧认证表单的首页。登录后，聊天、文献和简历等用户数据均按邮箱账号的可信主体隔离。
- **预期最终效果：**新用户可完成邮箱验证并建立账号，之后登录进入现有工作台；登录用户可退出。密码重置后使用新密码重新登录。项目从 QQ 邮箱 SMTP 发出带验证码的邮件，SMTP 凭据只由后端配置读取。

## 2. 已确认需求

- **使用者 / 调用方：**访问 NexusAI 的未登录访客，以及已注册的邮箱账号持有人。
- **触发方式：**打开项目显示首页；用户在右侧选择登录或注册；登录界面可进入忘记密码流程；已登录用户可主动退出。
- **输入：**邮箱、邮件验证码、密码和确认密码；登录时为邮箱及密码；找回密码时为邮箱、验证码、新密码及确认密码。
- **输出：**安全 Cookie 登录态；验证邮件；登录、注册、重置密码和登出结果；首页展示当前可用智能体及图标。
- **主流程：**
  1. 未登录访问者进入首页；前端公开读取 `GET /api/agents`，左侧展示当前注册表内智能体及头像，右侧显示登录/注册表单。
  2. 注册者申请注册验证码，后端生成限时一次性验证码并通过 QQ 邮箱 SMTP 发给输入邮箱；用户提交验证码和密码后建立邮箱账号并登录。
  3. 已注册用户提交邮箱和密码，认证成功后后端设置 HttpOnly 会话 Cookie；前端进入现有聊天或简历路由。
  4. 找回密码者申请找回验证码并提交新密码；后端核验后更新密码、使已有会话失效，并返回登录流程。
  5. 用户登出后，后端撤销当前会话并清除 Cookie，前端回到首页。
- **业务规则与边界：**验证码仅用于注册和找回密码；邮箱唯一；新邮箱用户从独立数据开始；每个邮箱账号独立拥有简历。原 `local-development` 和固定简历主体数据不自动迁移或合并。
- **异常行为：**无效邮箱、验证码错误或过期、邮箱重复、密码不匹配、登录凭证无效、邮件发送失败、服务配置缺失等情况均提供受控错误，失败时不建立账号或登录态。找回验证码请求对未注册邮箱返回与已注册邮箱一致的公开响应，避免暴露账号存在性。
- **权限与数据范围：**注册、验证码申请、登录和智能体目录为公开能力；聊天、文献、简历、上传、运行和结果接口须认证。用户所有权继续由服务端可信主体提供，不能从请求载荷接收。
- **约束：**登录 Cookie 设为 HttpOnly、SameSite=Lax；线上启用 Secure。QQ 邮箱使用已启用的 SMTP 服务和授权码，不使用邮箱网页登录密码。账号/SMTP 密钥不得写入仓库或日志。

## 3. 范围

- **本次包含：**主页面与智能体图标目录；注册、邮箱密码登录、登出、当前会话查询和密码找回；验证码邮件发送及模板；受保护 API 的认证；每账号简历数据隔离；配置、数据库结构、接口文档、变更记录和相应测试。
- **本次不包含：**第三方登录、手机号登录、管理员账号管理、邮箱变更、多因素登录、旧固定主体数据迁移、独立的邮件服务供应商接入界面。

## 6. 架构设计

### 模块职责与边界

| 模块 | 职责 | 依赖方向 / 边界 |
|---|---|---|
| `app.router.auth`（新） | 认证 HTTP 边界、设置/清除 Cookie、返回稳定响应 | 只调用 Auth Service，不执行 SQL 或发 SMTP |
| `app.schemas.auth`（新） | 邮箱验证码、注册、登录、找回密码及当前会话请求/响应 DTO | 不作为 ORM 或内部会话实体 |
| `app.service.auth`（新） | 组织验证码用途验证、注册、登录、会话发放/撤销、密码重置 | 注入用户/验证码/会话仓储、密码工具和邮件发送适配器 |
| `app.crud.auth`（新） | 用户凭据查询及验证码/会话持久化 | 用现有 `User`，新增认证 ORM 模型；不处理 HTTP/SMTP |
| `app.models.email_verification`、`app.models.auth_session`（新） | 保存一次性验证码元数据和可撤销会话 | 外键关联 `users.user_id`；仅存验证码哈希和会话令牌哈希 |
| `infra.email_sender`（新） | 使用 SMTP SSL 发送纯文本及 HTML 邮件 | 从 `AppSettings` 读取 SMTP 配置；SMTP 调用在线程池执行，避免阻塞 FastAPI 事件循环 |
| `app.service.auth_email_templates`（新） | 生成注册和找回密码邮件主题、纯文本及 HTML 正文 | 不读取凭据；只接受收件人、验证码及有效时长参数 |
| `app.dependencies.auth`（修改） | 校验会话 Cookie 并将账号映射成可信主体 | 所有业务 Service 仍只接收主体字符串，不感知 Cookie |
| `frontend/src/features/auth/`（新） | 认证 API、登录/注册/重置表单、状态 Hook | 使用共享 HTTP API，浏览器不读取会话 Cookie |
| `frontend/src/features/home/`（新） | 公共 Agent 展示和右侧认证区域的首页布局 | 通过公开 Agent API 获取列表；复用提取后的共享 Agent 头像 |

### 关键流程

```text
首页 → GET /api/agents + GET /api/auth/session
注册/登录/验证码请求 → Auth Router → Auth Service → Auth CRUD + EmailSender
受保护 API → get_principal_id → Session Store 校验 HttpOnly Cookie → User.account 主体
简历 API/求职助手 → 当前 principal_id → Resume Service/Repository → 该用户的 resumes.owner_id
```

将认证放进现有 Auth Service/CRUD/infra 边界，保持 Router 不直接操作数据库或 SMTP。会话使用随机高熵不透明 Cookie；Redis 以 Cookie token 的 SHA-256 摘要作为键，并存储邮箱和当前密码哈希指纹。Cookie 设置 HttpOnly、SameSite=Lax、Path=/，生产环境 Secure；所有变更请求校验同源 Origin，并拒绝不可信跨站请求。`get_principal_id` 由 Redis 会话映射查得用户账号后提供现有可信主体接缝，开发环境不再自动共享本地主体。

注册及重置分别采用 6 位数字验证码；验证码只将带用途的 HMAC 摘要存入 Redis，10 分钟失效、一次性使用、连续错误 5 次作废，同一邮箱/用途每 60 秒可重发一次。重置流程的无账号申请使用与账号存在时相同的公开成功响应。所有邮件发送失败均不新建用户/登录态；注册码验证后创建的用户凭据写入既有 `users` 表。

### QQ 邮箱配置

按附图先在 QQ 邮箱“设置 → 账号与安全/账户 → POP3/IMAP/SMTP 服务”中启用 SMTP 并生成授权码。后端配置建议如下：

| 配置项 | 值 / 含义 |
|---|---|
| `MAIL_SMTP_HOST` | `smtp.qq.com` |
| `MAIL_SMTP_PORT` | `465` |
| `MAIL_SMTP_USERNAME` | 完整发件邮箱地址，例如 `name@qq.com`；部署者用自己的发件账号填写 |
| `MAIL_SMTP_PASSWORD` | QQ 邮箱生成的 SMTP 授权码，不是邮箱网页登录密码 |
| `MAIL_FROM_NAME` | `NexusAI` |

连接使用 SSL/TLS；发件地址与 SMTP 登录邮箱保持一致。`MAIL_SMTP_PASSWORD` 使用 SecretStr，不输出到日志或错误响应；开发使用私有 `.env`，生产使用部署环境的 secret 注入。截图中的具体邮箱地址不作为配置默认值。QQ 邮箱帮助中心提供 POP/IMAP/SMTP 服务及授权码说明：[如何开启 POP3/SMTP/IMAP 服务并获取授权码](https://help.mail.qq.com/detail/106/985)；腾讯云邮件连接器文档列出 QQ 邮箱 SMTP 地址 `smtp.qq.com` 和 465/587 端口，并说明 SMTP 需使用服务授权码：[腾讯云 Email 连接器配置](https://main.qcloudimg.com/raw/document/product/pdf/1270_46586_cn.pdf)。

### 验证邮件模板

邮件通过 HTML 和纯文本双格式发送。验证码仅用于相应操作，不放入 URL，不记录明文；以下内容由模板函数替换 `{{code}}` 和 `{{expires_minutes}}`：

**注册邮件**

- 主题：`【NexusAI】注册验证码`
- 正文：

  ```text
  你好，

  你正在注册 NexusAI 账号。本次验证码为：

  {{code}}

  验证码 {{expires_minutes}} 分钟内有效，请勿向他人透露。如果这不是你发起的操作，请忽略此邮件。

  NexusAI
  ```

**找回密码邮件**

- 主题：`【NexusAI】密码重置验证码`
- 正文：

  ```text
  你好，

  你正在重置 NexusAI 账号密码。本次验证码为：

  {{code}}

  验证码 {{expires_minutes}} 分钟内有效，请勿向他人透露。如果这不是你发起的操作，请忽略此邮件。

  NexusAI
  ```

HTML 正文沿用相同文字语义，提供 NexusAI 标题、突出显示的验证码、有效期和安全提示；不嵌入追踪像素或外链图片。

## 9. 接口、数据与兼容性变更

### API 草案

| 方法与路径 | 认证 | 请求 / 结果 |
|---|---|---|
| `POST /api/auth/email-codes` | 否 | `{email, purpose: "register" | "password_reset"}`；统一返回请求已受理，实际未送达时返回稳定服务错误 |
| `POST /api/auth/register` | 否 | `{email, code, password, password_confirmation}`；成功建立账号并设置会话 Cookie |
| `POST /api/auth/login` | 否 | `{email, password}`；成功设置会话 Cookie |
| `GET /api/auth/session` | 否 | 返回当前账号摘要或 `authenticated=false`，不返回密码/内部 ID |
| `POST /api/auth/logout` | 会话可选 | 撤销当前会话并清除 Cookie；重复登出幂等 |
| `POST /api/auth/password-reset` | 否 | `{email, code, new_password, password_confirmation}`；更新成功并撤销该账号现有会话 |
| `GET /api/agents` | 否 | 继续供未登录首页读取当前 Agent 清单 |

成功响应沿用 `{success, data}` 封装。认证失败使用稳定 401，输入校验使用 422，频率限制使用 429，邮件配置/上游发送故障用受控 503/502，不返回 SMTP 异常正文。

### 持久化（实施阶段修订后）

- 不新增认证 PostgreSQL 表。验证码、失败次数、发送冷却和 Cookie 会话放入现有 Redis，通过 TTL 过期管理。
- 邮箱账号和密码哈希复用 `users.account` 与 `users.password_hash`；注册不额外建立邮箱到用户的映射。
- `017_redis_auth_state.sql` 用于清除早期版本曾创建的空认证表；仅有这些旧表的数据库需要执行。
- `users.account` 继续作为稳定主体字符串并唯一映射到现有 `users.user_id`；新增邮箱小写规范化后写入，旧 account 原值保持不变。
- `resumes` 表当前已用唯一 `owner_id` 外键支持每用户一份，无需数据迁移。固定主体 `nexusai-resume-owner` 的已有简历保留原 owner，不复制、不指派给任何邮箱账号；新账号首次访问获得独立空简历。

## 10. 分步实施计划

### 步骤 1：认证配置与复用现有持久化

- **目的：**复用用户账号表和 Redis，准备 QQ SMTP 配置。
- **涉及文件：**`backend/infra/settings.py`、`backend/.env.example`、`backend/app/crud/auth.py`、`backend/infra/redis_auth_store.py`、`backend/migrations/017_redis_auth_state.sql`、`backend/tests/test_settings.py`、`backend/tests/test_auth_service.py`、`docs/数据库文档.md`。
- **实施内容：**定义 SecretStr 邮箱授权码；将账号凭据存入既有 `users` 表，以 Redis TTL 管理验证码和会话；如数据库存在早期空认证表则清理。
- **前置依赖：**无。
- **验收标准：**
  - [ ] 不新增 PostgreSQL 认证表；邮箱与密码哈希落在既有 `users` 表。
  - [ ] 一次性验证码按邮箱和用途存于 Redis，过期、消费、超限后不可再次验证。
  - [ ] Redis 会话按 token 摘要校验和撤销；密码重置后已签发会话失效。
  - [ ] `.env.example` 不含真实账号授权码，SMTP 密码由 SecretStr 表示。
- **验证方式：**CRUD/设置单元测试；在 PostgreSQL 测试配置执行迁移升级与 ORM 对齐检查。

### 步骤 2：邮件模板和 QQ SMTP 发送适配器

- **目的：**按附图的授权码方式发出注册与密码找回邮件。
- **涉及文件：**`backend/app/service/auth_email_templates.py`、`backend/infra/email_sender.py`、`backend/infra/settings.py`、`backend/tests/test_auth_service.py`（模板/发送桩测试）、`README.md`。
- **实施内容：**通过 `EmailMessage` 或等价标准 MIME API 组装纯文本和 HTML 双格式；以完整邮箱地址登录 `smtp.qq.com:465` SSL；模板分别使用注册和密码重置主题，插入 6 位验证码及 10 分钟有效期；SMTP 同步 I/O 经线程池执行。
- **前置依赖：**步骤 1。
- **验收标准：**
  - [ ] 两类邮件主题及正文区分注册和密码重置，均包含验证码、有效时长、勿泄露提示和误操作忽略提示。
  - [ ] 邮件不含验证码 URL、追踪像素、QQ 登录密码或日志用凭据。
  - [ ] SMTP 未配置/认证失败时返回受控错误；调用方不接触服务端 SMTP 异常文本。
- **验证方式：**模板快照/断言和伪 SMTP 客户端测试；可选通过部署提供的测试账号执行一次人工收件验证，不将授权码提交到仓库。

### 步骤 3：注册、登录、验证码和密码重置用例

- **目的：**实现后端认证业务规则和公开认证 API。
- **涉及文件：**`backend/app/schemas/auth.py`、`backend/app/crud/auth.py`、`backend/app/service/auth.py`、`backend/app/router/auth.py`、`backend/bootstrap/application.py`、`backend/bootstrap/runtime.py`、`backend/app/models/__init__.py`、`backend/tests/test_auth_service.py`、`backend/tests/test_auth_api.py`。
- **实施内容：**规范化邮箱；使用 secrets 生成一次性验证码；保存验证码哈希；10 分钟过期、5 次错误作废、60 秒重发冷却；使用标准库 scrypt 以随机盐保存密码哈希；注册验证码校验和账号建立同事务；登录统一错误响应；找回密码成功后撤销该用户全部现存会话；对未注册邮箱的重置验证码请求返回相同公开响应。
- **前置依赖：**步骤 1、步骤 2。
- **验收标准：**
  - [ ] 注册必须提供匹配用途的有效验证码和符合长度规则的匹配密码；并发重复注册至多创建一个用户。
  - [ ] 已注册邮箱无法重新注册；错误密码和不存在账号得到同类登录错误。
  - [ ] 验证码过期、错误次数到上限、已消费码均无法注册或重置密码。
  - [ ] 重置成功后旧密码不能登录，重置前的所有 Cookie 会话均失效。
  - [ ] 邮件失败时不创建账号、不签发 Cookie；未注册邮箱不因公开响应暴露存在性。
- **验证方式：**Auth Service 单测、路由契约测试、数据库并发唯一性测试、邮件失败注入测试。

### 步骤 4：Cookie 主体解析及保护全部用户 API

- **目的：**让用户 API 从服务端会话取得可信主体，并取消匿名共享开发身份。
- **涉及文件：**`backend/app/dependencies/auth.py`、`backend/app/router/resume.py`、`backend/app/dependencies/resume_owner.py`、`backend/bootstrap/runtime.py`、现有 `backend/app/router/agents.py`、`conversation.py`、`research.py`、`literature.py`、`resume.py`，`backend/tests/test_api.py`、`backend/tests/test_resume_api.py`。
- **实施内容：**会话解析写入/返回账号 `principal_id`，缺失、过期、撤销均返回 401；只保留健康检查、Agent 列表和认证 API 为公开路由；所有简历照片、导出、读取、保存均加入认证依赖；校验 Cookie 的 SameSite/HttpOnly/Secure/Path/Max-Age 与同源变更请求检查。
- **前置依赖：**步骤 3。
- **验收标准：**
  - [ ] 未认证 API 请求不能落入 `local-development` 固定主体。
  - [ ] 未认证用户访问任何聊天、运行、文献、上传、结果或简历 API 收到 401；健康和公开智能体列表仍可用。
  - [ ] Cookie 为 HttpOnly、SameSite=Lax，生产环境 Secure；登出清除并撤销 token。
  - [ ] 两个邮箱账号不能通过猜测对方会话、上传 ID、会话 ID 或结果 ID 读取其数据。
- **验证方式：**受保护路由矩阵集成测试、cookie 属性断言、跨账号越权回归测试。

### 步骤 5：简历和求职助手按登录账号隔离

- **目的：**落实已确认的每邮箱账号独立简历，避免仍读取固定共享简历。
- **涉及文件：**`backend/app/router/resume.py`、`backend/app/dependencies/resume_owner.py`、`backend/app/service/job_resume.py`、`backend/agent/runner.py`、`backend/agents/job_agent/agent.py`、`backend/agents/job_agent/factory.py`、`backend/agents/job_agent/tools/read_saved_resume.py`、`backend/agents/job_agent/nodes/resume_optimization_node.py`、`backend/tests/test_resume_api.py`、`backend/tests/test_job_resume_reader.py`、`backend/tests/test_runtime.py`、相关求职助手测试、`backend/agents/job_agent/README.md`、`docs/数据库文档.md`。
- **实施内容：**所有简历请求传入 `get_principal_id` 结果；在 JobAgent 运行时上下文中使用 Runner 已持有的可信 principal，读取和确认写回均绑定同一主体；删除固定 owner getter；保留旧固定 owner 行但不迁移。
- **前置依赖：**步骤 4。
- **验收标准：**

  - [ ] 两个用户的简历照片 staging/final OSS 前缀各不相同，不能交叉读取或删除。

  - [ ] 原固定主体简历未被自动关联到任何新邮箱账号。
- **验证方式：**简历 API 所有权集成测试、求职助手工具主体传递测试、照片隔离测试。

## 12. 风险、假设与运行考虑

- **非阻塞假设：**
  - 使用 6 位验证码、10 分钟有效期、最多 5 次错误尝试、每邮箱/用途 60 秒重发间隔。
  - 密码长度为 8–128 个字符，scrypt 哈希；不再增加未确认的复杂度组合规则。
  - 会话有效期暂定 7 天，浏览器关闭后 Cookie 按该时长保留；登出撤销当前会话，重置密码撤销该账号全部会话。
  - 首页公开调用 Agent 列表；健康检查和文档页维持现状，所有涉及用户数据的业务 API 需要登录。
- **主要风险及应对：**
  - QQ 邮箱可能限制发送频率或拒收邮件：验证码请求有冷却，响应隐藏上游异常，部署须用实际授权码验证收件。
  - SMTP 网络端口可能被部署网络拦截：启动不因邮件未配置而拒绝服务，但验证码发送受控失败；上线前需验证出站 465/TLS。
  - Cookie 鉴权引入 CSRF 风险：SameSite=Lax 且变更请求校验 Origin；上线代理需正确保留 Host/Origin 和 HTTPS。
  - 现有开发固定身份数据在认证切换后不能自动作为任何邮箱用户数据：原记录保留，接受新账号独立开始的已确认范围。
  - 求职助手旧固定主体闭包若遗漏改造会造成跨用户读写：测试必须覆盖用户主体贯穿读取、Checkpoint 恢复和确认保存链。
- **安全 / 隐私 / 可观测性：**密码仅存 scrypt 哈希；验证码、会话 token 和 SMTP 密码只存哈希或 SecretStr；响应及日志不得包含验证码、密码、Cookie、授权码、简历内容或 SMTP 原始异常。认证失败日志只记录稳定原因类别。
- **发布、迁移或回滚：**新部署无需认证数据库迁移；若旧环境包含早期创建的认证临时表，备份后执行 `017_redis_auth_state.sql` 清理。上线前配置 Redis、SMTP 授权码和 pepper。回滚到旧版会恢复开发固定主体行为，只能用于可信本地网络，不能作为生产回滚方式。跨账号登录启用后不做旧主体数据自动映射。
