# 积分充值与 Stripe 沙盒支付实现方案

> 日期：2026-10-23（Asia/Shanghai）
> 状态：已按方案实施；人工 Stripe 沙盒支付验收待配置 Webhook 签名密钥
> 需求依据：[已确认的充值需求](../requirements/2026-10-23-002-credit-top-up-stripe-sandbox.md)

## 1. 目标与范围

已登录用户从账号栏积分旁打开充值弹窗，选择当前 Stripe 沙盒账户可用的支付币种，输入正整数金额，看到同数值积分和应付金额，再跳转到 Stripe 托管 Checkout。服务端确认测试支付成功后，给发起充值的账号增加同数值积分；刷新后仍可用。同一笔支付只能加分一次。支付失败、取消或待确认均不加分。

本次仅接入沙盒、银行卡测试支付及所配置的可用币种；不启用真实收款、汇率、人工补分或真实退款业务。可选币种以部署时在该沙盒账户验证过的配置白名单为准，不能把 Stripe 的全球币种清单直接当成当前账户的可用清单。

## 3. 方案与关键流程

### 职责分配

| 层 | 责任 |
|---|---|
| 前端 `features/topup/` | 充值弹窗、币种/金额校验、支付跳转、返回后的状态展示；调用现有余额刷新 |
| `app/router/topups.py`（拟新增） | HTTP 参数、认证依赖、同源校验、原始 Webhook 请求体、统一响应 |
| `app/service/topups.py`（拟新增） | 创建充值尝试、校验金额和币种、管理状态转换、核实 Stripe 支付结果、触发到账 |
| `app/crud/topups.py`（拟新增）与现有积分模型 | 持久化充值尝试；在同一 PostgreSQL 事务中锁定尝试和余额、写入充值明细并加分 |
| `infra/stripe_checkout.py`（拟新增） | 通过注入的测试密钥创建/查询 Checkout Session、验证 Webhook 签名；不执行业务加分 |
| `infra/settings.py` | 测试密钥、Webhook 签名密钥、站点返回地址和币种白名单等配置 |

### 创建与支付

1. 前端获取当前可用币种及每种币种的可输入范围。用户选择币种、输入正整数；实时展示 `N 积分` 与 `N <币种>`。前端校验只用于即时提示，后端重复校验。
2. `POST /api/credits/top-ups` 用可信主体创建充值尝试。请求含币种、正整数金额和客户端重试时保持不变的 `request_id`，不含 `user_id`。同一用户同一 `request_id` 与相同参数返回同一尝试；参数不同返回冲突。
3. 服务端先保存尝试，再以该尝试的稳定标识作为 Stripe 幂等键创建 `mode=payment`、`payment_method_types=['card']` 的托管 Checkout Session。Stripe Session metadata/client reference 仅放内部尝试标识；本地保存 Session ID 和 Checkout URL。客户端只接收可跳转 URL 与本地尝试 ID。
4. Stripe 按币种最小单位收款：例如 10 USD 传 `1000`、10 JPY 传 `10`；用户可得积分始终为 `10`。[Stripe 币种、零小数位及额度规则](https://docs.stripe.com/currencies)。后端同时检查配置的币种白名单、该币种适用的最小支付额、Stripe 请求金额上限及 `BIGINT` 余额上限。白名单和界面范围由同一服务端配置提供，Stripe 仍做最终受理判断。

### 支付结果与到账

1. `POST /api/stripe/webhook` 读取原始请求体并验证 `Stripe-Signature`；仅接受沙盒来源且关心 Checkout 支付完成/过期相关事件。不能信任浏览器成功 URL 或未经验证的事件数据。[Stripe Webhook 签名文档](https://docs.stripe.com/webhooks/signature)。
2. 对 `checkout.session.completed`，仅在 Session `payment_status=paid` 时到账。若事件或会话仍未支付，保持待确认；对可选的异步成功/失败事件做对应终态处理，即使当前只开放银行卡，也避免误将完成事件等同付款成功。[Stripe 支付完成与异步事件说明](https://docs.stripe.com/payments/existing-customers?platform=web&ui=stripe-hosted)。
3. 到账前核对 Session ID、沙盒标志、金额最小单位、币种及本地尝试状态与持久化记录一致；用户归属只取本地尝试。数据库事务原子地将尝试标记为 `paid`、锁定 `user_credits` 行、增加积分及版本，并写一条 `top_up` 明细，其唯一 `event_key` 由本地尝试 ID 构造。重复、乱序 Webhook 均不得重复加分。提交后更新 Redis；缓存失败不回滚数据库账务，可由现有余额读取回填。
4. Checkout 的成功和取消返回地址都进入前端充值结果视图，携带本地尝试 ID；视图调用本人可访问的状态接口。成功返回仅显示“待确认”，直到服务端状态为 `paid`；失败或取消返回不直接修改账务。取消返回时 Checkout Session 可能仍为 `open`，界面显示“未完成支付”，真正过期由 Stripe 事件/查询结果确认。用户关闭浏览器也不妨碍 Webhook 到账。

### 取舍与故障恢复

选择 Stripe 托管 Checkout，符合需求中的跳转交互，也避免项目接触银行卡资料。选择独立 `credit_topups` 表，因为余额与明细无法表达尚未到账的支付尝试、关联 Stripe Session、幂等创建和本人状态查询。余额仍只有一份事实来源，不另建支付钱包。

Stripe 幂等键用于 API 创建重试；它不是永久去重保证，Stripe 文档说明键可能在至少 24 小时后清理。因此本地尝试与唯一明细约束才是长期到账去重依据。[Stripe 幂等请求说明](https://docs.stripe.com/api/idempotent_requests)。如果创建 Stripe Session 后本地写回失败，重试应复用同一尝试/幂等键；Webhook 可凭 metadata 中的尝试 ID 与已保存金额核对并补齐 Session ID。超过 Stripe 幂等保留期的未知创建结果，先查询/对账，不直接创建新的支付尝试。Webhook 数据库提交失败返回非 2xx，让 Stripe 重投；提供按尝试 ID 查询和受控重放的运维核对手段，避免静默漏账。

## 5. 接口影响

成功响应沿用项目 `{success:true,data:...}`；受控失败沿用 `{success:false,code,message}`。下列路径为方案中的拟新增契约，实施时同步到接口文档。

| 方法与路径 | 操作 | 请求与响应要点 | 复用与兼容性 |
|---|---|---|---|
| `GET /api/credits/top-up-options` | 新增 | 需登录；返回币种代码、可输入最小/最大整数金额及展示信息 | 现有 session 不含币种约束；独立查询避免把支付配置混入认证响应 |
| `POST /api/credits/top-ups` | 新增 | 需登录和同源校验；`{currency, amount, request_id}`；返回 `{top_up_id, checkout_url, status}`。无效金额/币种 422，同键异参 409，未配置 503，上游暂不可用 502/503，错误码稳定 | 现有聊天提交不能表达支付；同键同参重试返回相同尝试和 URL |
| `GET /api/credits/top-ups/{top_up_id}` | 新增 | 需登录；返回本人尝试的 `pending/paid/failed/expired` 与金额、币种、积分；其他用户和不存在统一 404 | 现有 session 只给余额，无法表示这笔尝试的结果；ID 按项目约定传十进制字符串 |
| `POST /api/stripe/webhook` | 新增 | 不用浏览器 Cookie；仅接受有效 Stripe 签名的原始事件。合法重复事件返回 2xx；签名无效 400；暂时处理失败返回非 2xx | 现有认证接口不适合 Stripe 服务端回调；不能把该入口交给通用 JSON 解包 |
| `GET /api/auth/session` | 保持不变 | 原有 `credits` 字段在到账后返回新余额 | 前端复用既有余额刷新，无破坏性契约变化 |

Webhook 签名验证、`livemode=false`、Session 身份及账务匹配均为服务端边界。建议对 Webhook 请求体设大小限制，对重复事件只记录必要标识及状态，不记录完整支付资料。

## 6. 数据库影响

| 表 / 字段 | 操作 | 用途、复用判断与迁移 |
|---|---|---|
| `credit_topups`（新表） | 新增 | 保存尚未到账和已到账尝试；现有 `credit_entries` 仅有余额变动事件，不能保存待支付状态。字段：`top_up_id BIGINT` 主键、`user_id BIGINT` 外键、`request_id`、`currency`、`amount`（整数主单位）、`stripe_amount`（最小单位）、`stripe_session_id` 可空、`status`、`created_at`、`updated_at`。`top_up_id` 采用现有雪花 ID；API 按字符串传输。唯一 `(user_id,request_id)` 和非空时唯一 `stripe_session_id`；金额与状态检查约束。新表无历史回填。请求摘要由金额+币种比较，无需另存一份摘要字段。Checkout URL 不作为长期账务事实，可从 Session 查询或在创建响应中提供。 |
| `credit_entries.kind` 与 `delta` 约束 | 修改 | 增加 `top_up`，要求 `delta > 0`；原 `registration_grant/message_debit/run_refund` 规则保持。018 迁移已创建固定约束，019 必须显式替换；已有明细无需改写。`event_key` 对本地尝试唯一，`run_id` 保持空。 |
| `user_credits.balance/version` | 保持字段不变，新增写入路径 | 到账事务中加 `amount`、版本加 1；与现有扣费/退款共享余额事实及 Redis 版本规则。无需补分旧账号。 |

现有 `credit_entries` 的 `event_key` 主键已经足以防止同一尝试重复入账；无需另建 Webhook 事件表。新表的两个唯一约束防止请求重放创建重复尝试及 Stripe Session 关联到多个尝试。迁移先执行后部署 API；回滚应用时保留新表和到账明细，停止 Webhook 写入并核对在途尝试，不直接删除财务记录。

## 9. 前置条件、风险与交付

- 实施前在 Stripe 沙盒取得 `sk_test_...` 密钥及 Webhook 签名密钥，并验证实际允许的支付币种；仓库只保存变量名示例。Stripe CLI 本地转发的签名密钥与部署端点密钥分别配置，不互用。若未提供密钥，功能显示不可用，其他积分和聊天流程不受影响。
- 多币种最低收款额可能受结算币种与账户限制影响；配置白名单及每币种范围时需在沙盒逐项核验。UI 的即时提示基于服务端选项，Stripe 拒绝时再给受控错误，不应假称所有全球币种在本账户可用。
