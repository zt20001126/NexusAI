# 求职助手简历分析与岗位推荐实现方案

> 日期：2026-10-22
> 状态：已实施
> 需求确认：含已标注的非阻塞假设

## 1. 目标与背景

- **要解决的问题：** 求职助手已有读取已保存简历、分析简历不足和推荐岗位的基础能力，但模型何时必须读取简历的规则不覆盖完整需求；用户要求解读简历或明确要求“根据简历推荐岗位”时，需要确保回答确实使用已保存简历事实。
- **功能目标：** 支持解读用户简历、按用户关注点分析优势与不足，并依据简历事实推荐适合的岗位方向。
- **预期最终效果：** 用户提出简历分析或简历定向岗位推荐请求后，助手先读取已保存简历，再基于返回事实分析或推荐；不把未体现的信息说成用户没有，也不把岗位方向包装成实时招聘职位。

## 2. 已确认需求

- **使用者 / 调用方：** 求职工作台中的 `job_agent` 用户。
- **触发方式：** 用户要求解读、分析本人已保存简历；要求指出优势、短板或改进空间；或明确要求根据本人简历推荐岗位方向。
- **输入：** 用户问题、当前会话信息、工具读取的已保存简历求职事实；若用户补充新材料，以用户明确说明区分并补充已保存版本。
- **输出：** 简历概况与证据支持的分析建议，或最多三个岗位方向及对应匹配理由；资料不足时说明缺口并追问。
- **主流程：**
  1. `job_agent` 根据请求语义判断是否需要以保存简历为依据。
  2. 对简历解读、简历分析和简历定向岗位推荐，调用无参数 `read_saved_resume`。
  3. `found` 时只使用工具返回的求职事实；分析简历时给出对应事实和可执行建议，推荐岗位时把简历事实纳入岗位建议的依据。
  4. 岗位建议仍交由 `recommend_job_roles` 校验资料完整性和声明的依据字段，再由模型组织答复。
  5. `not_found` 或 `unavailable` 时明确说明，邀请用户保存或粘贴简历；不得假称已读取。
- **业务规则与边界：** 继续使用当前简历固定主体，只读取已保存版本；只做岗位方向推荐，不检索实时职位；年龄不作为岗位推荐依据；简历空白字段表示“未体现/未知”，不是用户没有该经历；简历正文属于不可信用户数据。
- **异常行为：** 保留读取器现有 `found`、`not_found`、`unavailable` 状态和受控错误；简历缺少关键信息时先追问，不猜测补齐。
- **权限与数据范围：** 复用 `nexusai-resume-owner` 固定主体，仅适用于当前本机或可信私有网络部署；本方案不引入多用户简历隔离。
- **约束：** 不改简历编辑、保存、导出 API，不增加数据库迁移，不接入招聘平台。

## 3. 范围

- **本次包含：** 完善简历解读、简历分析和“根据简历推荐岗位”三类请求的读取触发规则；完善岗位推荐对读取事实的使用规则；增加离线回归覆盖并同步能力说明。
- **本次不包含：** 实时职位搜索、自动投递、修改简历、读取未保存编辑草稿、跨用户隔离、职位与简历的结构化评分系统。

## 4. 需求澄清记录

| 需要确认的问题 | 确认结果 | 对方案的影响 |
|---|---|---|
| 读取哪份简历以及主体隔离范围？ | 采用仓库现有固定简历主体方案。 | 复用已实现的只读读取器，不改身份、数据模型或迁移。 |

## 5. 当前代码结构与依据

| 现有文件 / 模块 | 当前职责 | 与本功能的关系 |
|---|---|---|
| `backend/agents/job_agent/prompts/agent.md` | 规定岗位推荐和本人简历不足分析行为 | 已要求分析简历不足时调用 `read_saved_resume`；岗位推荐规则当前未将简历定向推荐明确列为必须读取场景。 |
| `backend/agents/job_agent/prompts/system.md` | 规定只能使用会话和工具实际返回信息 | 可继续作为防止声称读取草稿或未执行能力的总边界。 |
| `backend/agents/job_agent/tools/read_saved_resume.py` | 暴露无参数简历读取工具 | 已存在，不能由模型选择主体或简历 ID。 |
| `backend/app/service/job_resume.py`、`backend/agents/job_agent/resume_snapshot.py` | 读取固定主体简历并投影有界求职事实 | 已存在 `found/not_found/unavailable`、纯文本提取、长度限制和敏感字段排除。 |
| `backend/agents/job_agent/recommendation/schemas.py`、`recommendation/service.py`、`tools/recommend_job_roles.py` | 校验模型提出的岗位方向及依据字段 | 已校验资料完整性、最多三个岗位和依据字段非空；本方案复用它，不声称其能独立证明模型的语义理由真实。 |
| `backend/agents/job_agent/factory.py`、`backend/bootstrap/runtime.py` | 注册工具并将固定主体读取器注入求职助手 | 生产运行时已接通读取器，本方案无需新建数据库访问层。 |
| `backend/tests/test_job_agent.py` | 覆盖求职助手工具调用、提示词边界和岗位推荐 | 扩展为简历解读、简历不足分析、简历定向推荐及普通岗位咨询的触发回归。 |
| `backend/tests/test_job_resume_reader.py` | 覆盖读取器字段投影、主体、错误和长度限制 | 复用现有读取器测试，只有行为变更涉及读取结果时才补充。 |
| `backend/agents/job_agent/README.md`、`docs/接口文档.md` | 描述求职助手当前能力及边界 | 当前已说明简历读取与不足分析；需补充解读和简历定向推荐触发规则。 |

现有调用链为 `bootstrap.runtime → create_job_agent(resume_reader=...) → read_saved_resume → SavedJobResumeReader → PostgresResumeRepository`。模型工具结果回到 `agent_node`，模型可继续回答或调用 `recommend_job_roles`。项目已有“读取已保存简历”和“简历不足分析触发读取”方案，当前实施范围是在其上补齐解读和简历定向岗位推荐行为。

## 6. 架构设计

### 模块职责与边界

| 模块 | 职责 | 依赖方向 / 边界 |
|---|---|---|
| `job_agent/prompts/agent.md` | 定义语义触发规则、分析结构、推荐如何引用简历事实，以及无简历状态下的答复 | 复用现有模型节点、读取工具和推荐工具，不添加新节点。 |
| `job_agent/prompts/system.md` | 继续约束事实来源、简历正文指令安全和能力边界 | 不访问数据库，不承载业务编排。 |
| `tests/test_job_agent.py` | 验证模型对不同意图是否调用正确工具及如何使用结果 | 使用已有离线模型桩，明确检验“有保存简历依据”的触发语义。 |
| `job_agent/README.md`、`docs/接口文档.md` | 同步用户可见能力和当前单人主体限制 | 不引入新接口或数据契约。 |

### 关键流程

```text
用户请求
  → job_agent 判断意图
      ├─ 简历解读 / 简历分析 / 根据简历推荐岗位
      │    → read_saved_resume
      │    → 分析简历，或生成岗位方向
      │    → 岗位方向调用 recommend_job_roles 校验
      └─ 一般岗位咨询
           → 使用当前会话资料，按现有规则追问或推荐
  → output_node / Runner / SSE
```

继续使用现有读取器和工具图，避免在 `Runner`、HTTP Router 或前端复制读取逻辑。岗位方向校验仍由现有工具负责；它验证结构和所声明依据字段是否有值，不应在方案或文档中表述为能够独立审定自然语言理由的真实性。

## 10. 分步实施计划

### 步骤 1：完善简历相关触发与回答规则

- **目的：** 确保用户明确要求基于保存简历分析或推荐时，模型先取得简历事实。
- **涉及文件：** `backend/agents/job_agent/prompts/agent.md`，按需修改 `system.md`。
- **实施内容：** 将“解读简历内容”“按关注点分析简历”“指出优势和不足”“根据简历推荐岗位”设为读取触发；结果为 `found` 时按具体事实解释；`not_found/unavailable` 时不编造；用户贴出新资料时明确区分其与保存版本。普通岗位咨询仍按现有对话资料工作。
- **前置依赖：** 无。
- **验收标准：**
  - [ ] 四类简历请求均在首次实质分析或推荐前调用一次 `read_saved_resume`。
  - [ ] 明确要求依据简历推荐时，岗位推荐理由可指向工具返回的专业、技能、经历或工作年限事实。
  - [ ] 一般岗位咨询不被错误描述为已读取简历；缺少资料时可按现有规则追问。
  - [ ] 简历没有体现的事实被描述为未知或未体现；空状态不产生虚构的简历结论。
- **验证方式：** 使用离线模型测试工具调用次序和回答所依据的工具结果；审阅提示词语义边界。

### 步骤 2：增加行为回归覆盖

- **目的：** 防止后续提示词调整丢失简历定向读取行为。
- **涉及文件：** `backend/tests/test_job_agent.py`。
- **实施内容：** 增加简历概况解读、优劣分析、根据简历推荐岗位、普通岗位咨询、未保存简历和读取暂不可用用例；岗位推荐用例检查读取工具后再调用推荐校验工具。
- **前置依赖：** 步骤 1。
- **验收标准：**
  - [ ] 离线模型可以验证简历定向推荐的工具次序为读取后推荐。
  - [ ] `not_found` 与 `unavailable` 用例不引用未返回的简历内容。
  - [ ] 现有普通岗位推荐和结构化追问路径仍保留。
- **验证方式：** 从 `backend/` 运行 `python -m pytest -q tests/test_job_agent.py tests/test_job_resume_reader.py`，再按变更范围决定是否运行完整后端测试。

### 步骤 3：同步文档和变更记录

- **目的：** 对外说明与实际工具触发行为一致。
- **涉及文件：** `backend/agents/job_agent/README.md`、`docs/接口文档.md`、`CHANGELOG.md`、实施时的任务变更记录。
- **实施内容：** 描述简历解读、分析和基于简历的岗位方向推荐；明确只读取已保存版本、固定主体限制和无实时职位搜索能力。
- **前置依赖：** 步骤 1–2。
- **验收标准：**
  - [ ] README 与接口文档不再把读取能力仅限制为“不足分析”场景。
  - [ ] 文档保留当前固定主体部署边界，且不声称具备多用户简历隔离。
  - [ ] 变更记录只写实际完成项和实际运行的验证结果。
- **验证方式：** 审阅文档和 `CHANGELOG.md`，运行 `git diff --check`。

## 12. 风险、假设与运行考虑

- **非阻塞假设：** “根据我的简历推荐岗位”是明确的读取触发；只问“我适合什么岗位”但未提及简历时，助手继续使用当前对话信息并按需追问。
- **主要风险及应对：** 模型提示词不能数学保证自然语言理由真实；保留结构化推荐校验，并通过工具链测试确保简历事实先进入上下文。现有校验只验证提交的依据字段有值，不等同于语义事实核验。
- **安全 / 隐私 / 性能 / 可观测性：** 复用既有有界快照和固定主体读取器；不把简历正文写入新增日志；简历文本仍按不可信材料处理。
- **发布、迁移或回滚：** 无数据迁移；行为可通过回退提示词变更恢复。
