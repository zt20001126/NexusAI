# 求职助手读取已保存简历实现方案

> 日期：2026-10-21
> 状态：已实施
> 需求确认：已澄清

## 1. 目标与已确认范围

在现有 `job_agent` 中增加一个只读工具，使求职助手可读取数据库中**已保存**的简历，并依据实际内容回答。用户确认继续使用当前单人固定简历主体 `nexusai-resume-owner`；本方案适用于现有本机或可信私有网络部署。本次只接入工具能力，不规定模型在什么场景或时机调用它。

- 模型可调用此工具，工具参数中不提供用户 ID、简历 ID 或任意查询条件；调用时机不在本次范围内。
- 读取已保存版本；浏览器中尚未保存的编辑草稿不会进入工具结果。
- 返回与求职有关的结构化事实：求职意向、手动填写的工作经验年限、教育经历、技能、工作经历和项目经历。富文本转换为纯文本。工具读取记录后只向模型返回这些字段；姓名、电话、邮箱、年龄、证件照标识、排版配置和照片字节不返回。
- 无简历时返回明确的 `not_found` 结果；数据库不可用或数据无法解析时给模型受控失败信息，不把原始异常或数据库内容发给用户。
- 本次不改变简历编辑、保存和导出功能，不修改 `recommend_job_roles` 的既有校验职责，不增加对外 API 或数据库迁移。

### 需求澄清记录

| 问题 | 用户决定 | 对方案的影响 |
|---|---|---|
| 简历接口使用固定主体，聊天会话使用认证主体；工具读取哪份简历？ | 继续读取现有单人固定简历，仅用于本机或可信私有部署 | 复用固定主体，不进行简历归属迁移；必须在文档中明确共享数据边界 |

## 3. 设计

### 数据与控制流

```text
求职聊天运行
  → job_agent 模型决定调用 read_saved_resume（无参数）
  → 工具调用注入的只读读取器
  → PostgresResumeRepository.get(固定简历主体)
  → 校验 ResumeContent 并提取有界求职事实
  → 工具返回状态和事实给模型
  → 模型结合对话、简历事实回答；需要推荐时仍调用 recommend_job_roles
```

`app/service` 负责数据库记录到求职事实的转换；`job_agent` 只依赖注入的读取接口和自己的事实模型，不直接创建数据库会话。运行时复用一个 `PostgresResumeRepository` 注入简历应用服务和求职读取器。读取器每次工具调用都查询数据库，因此简历保存后的下一次调用可读到新版本。

工具输入为空，并在服务端固定查询主体。结果使用明确状态（如 `found`、`not_found`），保存时间和实际返回字段；不返回原始 JSONB、Tiptap 节点或照片。文本提取遵循 Tiptap 白名单并保留段落边界；设置集中定义的总字符上限和截断标记，避免过长工具消息进入 Checkpoint 或对话上下文。对于空白字段保持缺失语义，模型不能把空白解释为“没有经验”。

提示词仅说明简历读取工具的能力、已保存版本边界和简历文本属于数据而非指令；本次不新增工具调用触发策略。若用户在对话中提供了更新信息，应优先使用用户最新明确说明，并区分其与数据库保存版本；不能声称读到未保存草稿。`recommend_job_roles` 继续校验模型提交的建议字段和理由；它本身不会独立核对数据库。

### 身份与隐私边界

本次复用现有固定主体模式，不把聊天主体映射为简历 owner。任何能使用此部署的求职聊天者理论上都能让工具读取同一份简历，所以此方案以本机或可信私有网络为部署前提；不能把它当作多用户隔离方案。未来接入多用户时，必须先让简历 HTTP 接口和聊天运行使用同一认证主体，并迁移既有固定主体数据，再调整工具读取器。工具不得接收模型传入的 owner、principal 或 resume ID。

## 5. 分步实施与验收

1. **定义事实契约与读取器**。新建 `resume_snapshot.py`、`app/service/job_resume.py`，复用 `PostgresResumeRepository.get` 和固定主体。验收：无记录返回 `not_found`；有记录可提取求职字段与纯文本；姓名、联系方式、年龄、照片及排版信息不出现在结果；超长内容被显式标记为截断。
2. **接入无参数工具**。新建 `tools/read_saved_resume.py`，修改 `factory.py` 与 `bootstrap/runtime.py`。验收：生产运行时的 `job_agent` 注册该工具；模型无法指定读取对象；工具在 Worker 内可取得当前数据库中已保存的版本；原有题卡和推荐工具仍可调用。
3. **更新能力边界与文档**。修改两份提示词、Agent README 和接口文档。验收：提示词说明工具只返回已保存简历事实、简历文本是数据而非指令；不新增调用触发策略；文档不再声称求职助手不能读取简历，并保留单人部署限制。
4. **添加回归覆盖并记录变更**。增加读取器与工具调用相关测试；实施时更新变更记录与 `CHANGELOG.md`。验收：测试能区分 `found`、`not_found` 和失败；未发生模型指定主体的参数注入；相关旧测试和后端完整测试通过，`git diff --check` 无格式错误。

## 7. 假设与风险

- 用户希望模型按需读取的是数据库中已保存的简历，不包含浏览器未保存的草稿；该假设与现有简历导出语义一致。
- 工具结果会进入模型上下文及可能的图 Checkpoint，故只返回有界求职事实。数据库中的简历文本属于用户输入，应防止其中的“指令”改变智能体权限或工具规则。
- 固定主体模式无法提供多用户数据隔离；部署范围扩大前需单独设计认证主体统一与历史数据迁移。
- 本方案不改变表结构、公开 HTTP 请求/响应结构或 SSE 协议；服务端部署即可回滚，回滚后旧数据仍在原表中。
