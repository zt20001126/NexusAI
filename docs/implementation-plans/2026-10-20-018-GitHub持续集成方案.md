# GitHub 持续集成实现方案

> 日期：2026-10-20
> 状态：已实施；待首次 GitHub Actions 运行验证
> 需求确认：代码库信息已核实；触发分支按当前 `main`、`dev` 设计

## 1. 目标与背景

- **要解决的问题：** 当前仓库没有 GitHub Actions 工作流，代码提交和 Pull Request 不会自动运行项目检查。
- **功能目标：** 在 GitHub 上自动执行后端测试、前端测试和生产构建，让每次改动都有可见的通过或失败状态。
- **预期最终效果：** 向 `main` 或 `dev` 推送提交、或创建目标为这两个分支的 Pull Request 时，GitHub 并行显示后端和前端检查结果；任一命令失败，对应检查失败。

## 2. 已确认需求

- **使用者 / 调用方：** 向 GitHub 仓库推送代码或创建 Pull Request 的开发者。
- **触发方式：** 推送到 `main`、`dev`，以及目标分支为 `main`、`dev` 的 Pull Request。
- **输入：** 仓库提交及依赖清单。
- **输出：** GitHub Actions 中独立的后端测试和前端检查状态。
- **主流程：**
  1. GitHub Actions 检出提交，并按项目要求设置 Python 和 Node.js。
  2. 后端安装 `backend/requirements.txt` 并运行完整 pytest 套件。
  3. 前端依据已跟踪的 `frontend/package-lock.json` 执行 `npm ci`，然后运行 `npm test` 和 `npm run build`。
  4. 两个检查并行结束；命令退出码反映为对应的 GitHub 检查状态。
- **业务规则与边界：** CI 只验证代码，不部署服务、不推送镜像，也不调用生产模型或云服务。
- **异常行为：** 依赖安装、测试或构建失败时，GitHub 将对应 job 标记为失败并展示日志。
- **权限与数据范围：** workflow 仅需读取仓库内容；测试不得依赖真实 API 密钥、云凭据或用户数据。
- **约束：** 后端 Python 版本由 `backend/pyproject.toml` 固定为 `3.12.13`；前端已有 `test`、`build` 脚本和已跟踪锁文件。

## 3. 范围

- **本次包含：** 一个 GitHub Actions workflow；后端 pytest；前端 npm 测试和 TypeScript/Vite 构建；实施时发现并稳定一个有时序竞争的流式单测；任务级变更记录与 `[Unreleased]` 更新。
- **本次不包含：** CD/自动部署、Docker 镜像构建或发布、代码覆盖率门槛、Lint/静态安全扫描、PR 自动合并。
- **合并门禁：** workflow 会在 PR 上报告状态。若需要阻止失败检查的 PR 合并，还需在 GitHub 的分支规则中将两个 job 设为必需检查；该仓库设置不属于本地文件变更。

## 6. 架构设计

### 模块职责与边界

| 模块 | 职责 | 依赖方向 / 边界 |
|---|---|---|
| `.github/workflows/ci.yml`（拟新增） | 定义触发条件、最小仓库权限、运行环境及两个并行 job | 调用仓库现有脚本，不承载应用逻辑或部署流程。 |
| GitHub Actions runner | 提供 Linux 环境并运行安装、测试、构建命令 | 不连接生产数据库、Redis、模型 Provider、OSS 或其他云服务。 |
| GitHub 分支规则（可选配置） | 将 CI job 状态作为合并条件 | 位于 GitHub 仓库设置，不由 workflow 文件自动启用。 |

### 关键流程

```text
push / pull_request(main, dev)
  -> GitHub Actions
     -> Backend Tests: Python 3.12.13 + requirements.txt + pytest -q
     -> Frontend Checks: Node.js 22 + npm ci + npm test + npm run build
  -> 两个 job 的状态显示在提交和 Pull Request 上
```

使用一个 workflow 和两个并行 job，便于在 PR 页面区分失败来自后端还是前端。`backend/`、`frontend/` 是独立工作目录，所以无需跨 job 共享依赖。设置 `contents: read` 最小权限；不定义 secrets，也不使用 `pull_request_target`。不加路径过滤，避免修改共享配置或跨层契约时漏跑检查，也保证分支规则始终能看到对应状态。

前端当前使用 Vite 8；其官方支持 Node.js `20.19+` 或 `22.12+`，方案固定使用 Node 22 系列。后端按 `pyproject.toml` 固定到 Python `3.12.13`。GitHub Actions 官方 `setup-python` 建议显式指定 Python 版本，避免 runner 默认版本变化。

## 10. 分步实施计划

### 步骤 1：添加 GitHub Actions CI workflow

- **目的：** 让提交和 PR 自动执行可区分的后端与前端检查。
- **涉及文件：** `.github/workflows/ci.yml`（新增）。
- **实施内容：** 配置 `push` 到 `main`/`dev` 和面向这两个分支的 `pull_request`；设 `permissions: contents: read`；使用 `actions/checkout`、`actions/setup-python` 与 `actions/setup-node`；配置两个并行 job。后端在 `backend/` 安装依赖并运行 `python -m pytest -q`；前端在 `frontend/` 使用 `npm ci`、`npm test` 和 `npm run build`。Python 使用 `3.12.13`，Node 使用 22 系列；为 pull request 的同一分支配置并发取消，避免旧提交继续占用 runner。
- **前置依赖：** 无。
- **验收标准：**
  - [ ] workflow 仅在 `main`、`dev` 的 push 和目标为这两个分支的 PR 上触发。
  - [ ] GitHub 检查列表显示独立的后端测试 job 与前端检查 job，二者可并行运行。
  - [ ] CI 仅有仓库只读权限，不要求生产密钥或连接生产服务。
  - [ ] 任一验证命令非零退出时，对应 job 显示失败。
- **验证方式：** 使用 `actionlint` 检查 workflow 语法和表达式；分别在本地执行与 workflow 等价的后端、前端命令；推送实现分支并创建 PR，确认两个 job 在 GitHub 上运行并产生状态。

### 步骤 2：稳定流式测试时序

- **目的：** 保证全量后端测试中的流式时序断言可重复验证，避免偶发红灯。
- **涉及文件：** `backend/tests/test_runtime.py`。
- **实施内容：** 为假模型增加异步第二段释放事件；测试收到首个增量后释放它，模型若没有等到握手则在限定时间内失败。
- **前置依赖：** 步骤 1 的首次全量测试运行暴露了单次时序失败。
- **验收标准：**
  - [ ] 首个 delta 事件被消费时，模型完成标志仍为 false。
  - [ ] 收到首个 delta 后模型能继续完成，最终快照仍为“你好，世界”。
  - [ ] 目标用例连续运行 10 次均通过。
- **验证方式：** 在隔离的 Python 3.12.13 环境中连续执行目标 pytest 用例 10 次，再运行完整套件。

### 步骤 3：记录项目变更

- **目的：** 按仓库交付约定保留面向使用者的摘要和本次工程任务记录。
- **涉及文件：** `CHANGELOG.md`；实施当天新建的 `docs/change-records/<实施日期>-<当日全局序号>-GitHub持续集成.md`。
- **实施内容：** 更新 `[Unreleased]`；任务记录只写实际 workflow 内容和确实运行过的验证结果。若实现与本方案不一致，先更新本方案或在任务记录中说明决策。
- **前置依赖：** 步骤 1。
- **验收标准：**
  - [ ] `[Unreleased]` 有一条简洁说明，不重复粘贴任务背景。
  - [ ] 任务记录使用实施当天 `docs/` 全局未占用的三位序号，并如实列出改动文件和检查结果。
  - [ ] 未执行的检查明确标注原因，没有未运行检查的通过声明。
- **验证方式：** 检查文档链接、日期序号唯一性、`CHANGELOG.md` 条目位置及 `git diff --check`。

### 步骤 4：确认 GitHub 合并门禁（按需）

- **目的：** 在团队希望失败检查阻止合并时，将 CI 状态设为必需检查。
- **涉及文件：** 无；配置位于 GitHub 仓库的 branch protection 或 ruleset 设置。
- **实施内容：** 等 workflow 首次运行后，在 `main` 和 `dev` 的规则中选择两个稳定 job 名称作为必需检查。
- **前置依赖：** 步骤 1 已在 GitHub 成功触发一次；此步骤取决于仓库管理员的分支规则策略。
- **验收标准：**
  - [ ] 若启用门禁，存在失败或尚未完成的必需 job 时，GitHub 不允许合并；两个 job 通过后可按既有规则合并。
- **验证方式：** 在 GitHub 仓库设置核对 required status checks；此项不通过本地测试验证。

## 12. 风险、假设与运行考虑

- **非阻塞假设：** 项目持续使用 `main` 和 `dev` 作为受 CI 检查的集成分支；短期功能分支通过针对这两个分支的 PR 获得检查。
- **主要风险及应对：**
  - 首次后端全量测试中，流式时序单测出现一次失败；假模型以同步、无等待的方式快速发出两段文本，完成标记可能先于事件消费者观察到第一段。实施中用测试握手稳定这一时序，不改变生产 Runner 行为。
  - 测试若将来新增真实 PostgreSQL、Redis 或外部服务依赖，当前无服务容器的 CI 会失败；新增此类测试时应明确使用 Mock，或为相应 job 配置隔离的服务容器。
  - 两个检查状态本身不会自动阻止合并；是否设为必需状态由 GitHub 分支规则决定。
  - 当前 `frontend/package-lock.json` 的包下载地址使用 `registry.npmmirror.com`。npm 锁文件记录实际包源，因此 CI 会访问这些地址；首次 GitHub Actions 运行需验证该镜像可达。若不可达，再评估将锁文件更新为 GitHub runner 可访问的 npm registry 并审阅依赖差异。
  - `Node 22` 是为兼容当前 Vite 8 选择；升级 Vite 或更改本地 Node 支持策略时应同步评估。
- **安全 / 隐私 / 可观测性：** 明确只读仓库权限；不添加密钥；fork PR 使用常规 `pull_request` 事件，不暴露写权限；失败原因通过 Actions 日志查看。
- **发布、迁移或回滚：** 不涉及数据库迁移和部署。若 workflow 配置造成误报，可通过修改或回滚 `.github/workflows/ci.yml` 恢复；不要以跳过失败 job 代替修复。

## 实施验证结果

- 后端：在隔离的 Python 3.12.13 环境安装 `backend/requirements.txt` 后，`python -m pytest -q` 通过，138 passed；保留 1 条 Starlette/AnyIO 弃用警告。流式时序目标用例在修正后连续 10 次通过。
