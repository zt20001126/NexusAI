# 智能体会话流断线重连实现方案

> 日期：2026-10-19（Asia/Shanghai）
> 状态：已实施（2026-10-19）；后端自动化测试受本机依赖环境限制
> 需求确认：已澄清，含已标注的非阻塞假设

## 实施结果与方案差异

- 智能体 SSE 提交、追问恢复和文献问答现已派发到独立 Celery `agents` 队列；Worker 复用 `build_lifespan` 组装已有 Agent Runtime，没有新增第二套图或消息模型。
- 事件以 Redis Streams 按 conversation/run 保存；事件正文按数量和 TTL 清理，单调游标元数据在活动/等待状态保留，运行完成、失败或取消后按事件 TTL 清理。
- request_id 幂等使用可信主体与请求 ID 的 SHA-256 作为 `agent_runs.metadata.request_key`，由部分唯一索引保证；没有新增 `agent_run_requests` 表，也没有把会话、运行和消息写入伪装成单一数据库事务。
- 复用了现有 cancel 路由。活动查询提供 `/api/conversations/active`、`/api/conversations/active/latest` 和 Agent 路由兼容入口；会话状态查询沿用 `/api/conversations/{conversation_id}/status`。
- Worker 使用 `agent-run:{run_id}` advisory lock 避免重复任务同时声明同一 run；旧运行在锁已释放且数据库仍标记 running 时安全地以中断错误终止，不从不确定的 Checkpoint 位置自动重跑。
- 最终实现没有新增独立 `bootstrap/agent_worker.py` 或修改 `ConversationSidebar.tsx`；Worker 入口使用 `app/service/agent_tasks.py`，发送中导航通过页面现有侧栏调用路径启用。
- 自动化覆盖新增 Redis 事件存储游标测试和前端 SSE frame 解析测试。前端 `npm test` 与 `npm run build` 已通过；后端 `compileall` 已通过。`python -m pytest -q` 因当前仅有 Python 3.8/3.11 且缺少项目依赖（如 langgraph、langchain-core、oss2）在测试收集阶段失败，详情记录在 `docs/change-records/2026-10-19-016-智能体流式恢复.md`。

下方分步文件清单和测试矩阵保留方案阶段的预估范围；最终实现以任务级变更记录和代码差异为准。

## 1. 目标与背景

- **要解决的问题：** 当前 AgentRunner 在 SSE 请求的异步生成器内执行。客户端断线会关闭生成器，Runner 将 CancelledError 作为运行取消处理；SSE 事件没有持久化，前端不能补收离线期间的事件。
- **功能目标：** 将智能体任务生命周期与 SSE 连接解耦；用现有 Celery/Redis 基础设施调度任务、用 Redis Streams 保存可回放事件，并复用现有会话、消息、运行和所有权模型。
- **预期最终效果：** 用户提交后可以断网、刷新或切换会话；智能体任务继续执行。用户重新打开会话时，前端按会话、run 和最后收到的事件 ID 续接。用户主动停止仍会取消生成。事件过期后，前端回退到现有会话历史。

## 2. 已确认需求

- **使用者 / 调用方：** 已登录用户及聊天页；文献解读助手的专用聊天入口也使用相同运行与事件基础设施。
- **触发方式：** 现有智能体 SSE 提交、追问恢复、前端页面恢复和显式停止操作。
- **输入：** 现有消息、可选 conversation_id、图片附件或文献选择；新前端为每次提交/追问提交附带 UUID 格式的 request_id。
- **输出：** 原有 AgentEvent 业务事件；新增 listen、活动运行和运行状态查询响应。
- **主流程：**
  1. API 通过可信主体创建或复用会话、运行及用户消息，使用 request_id 去重。
  2. API 将仅含必要运行标识的 Celery 任务发到专用智能体队列，并用 Redis Stream 中的事件继续响应当前 SSE 连接。
  3. Worker 通过共享 AgentRunner 和 LangGraph Checkpointer 执行智能体；每个业务事件先写入按会话和 run 隔离的 Redis Stream，再由任意 API 实例读取。
  4. 连接关闭只结束当前读取器。显式停止才会向共享取消信号写入请求。
  5. 前端保存 conversation_id、run_id 和最后事件 ID；断线或返回会话时调用 listen。页面刷新时先读取当前用户所有排队或运行中的会话。
- **业务规则与边界：** queued 和 running 是活动状态；waiting 表示等待用户回答，不属于后台执行中任务；同一会话仍遵循现有 PostgreSQL advisory lock，同一用户可同时运行多个会话。
- **异常行为：** 会话不存在或越权统一为安全的 404；活动 run 不唯一且未传 run_id 时返回明确冲突；事件游标已被保留策略裁掉时返回 EVENT_STREAM_EXPIRED；Redis/队列不可用返回安全的 503；运行已结束但没有可续事件时返回可识别状态，前端加载历史。
- **权限与数据范围：** 必须先通过会话所有者校验，再查询运行记录或 Redis。run 必须属于指定会话。Redis key 不包含可用于授权的秘密；错误和日志不含消息正文、模型原始异常或其他用户数据。
- **约束：** 不增加第二套会话或消息机制；事件沿用现有 SSE 业务事件名和 AgentEvent JSON 字段；数据库结构变更提供显式迁移；普通非流式聊天和 Research REST 搜索不在本次改造范围。

## 3. 范围

- **本次包含：**
  - 现有通用 Agent SSE、追问恢复 SSE 和文献解读专用 SSE 的后台任务化。
  - Redis Streams 回放、单 run 游标、过期检测、共享取消信号和心跳。
  - 用户级请求幂等、运行状态、活动运行列表、listen 接口和当前停止接口的跨 Worker 行为。

  - Worker/Redis 配置、Compose 服务、迁移和项目文档。
- **本次不包含：**
  - 更换 LangGraph Checkpointer、会话历史或消息存储。

  - 新建新的会话、消息或任务结果表。
  - 对 Worker 被强制终止后的模型副作用提供 exactly-once 保证。

## 6. 架构设计

### 模块职责与边界

| 模块 | 职责 | 依赖方向 / 边界 |
|---|---|---|

| app/service/agent.py | 幂等提交、入队、授权后读取事件、状态/活动运行编排 | 依赖 Runner、CRUD 协议、队列与事件存储抽象。 |

| agent/runner.py | 根据已持久化运行记录和消息 ID 执行现有 LangGraph 图并发出原业务事件 | 不依赖 FastAPI、Celery 或 Redis 客户端；依赖持久化协议。 |
| infra/agent_event_store.py（拟新增） | Redis Stream append/read/blocking wait、ID 分配、长度/TTL、取消标志 | Redis 实现领域协议；事件先写后发；事件 key 按会话和 run 隔离。 |
| infra/agent_task_queue.py（拟新增） | 仅以会话/run/action 等稳定 ID 向 agents 队列投递 | 复用现有 Celery App 和 Redis Broker。 |
| app/service/agent_tasks.py（拟新增） | Celery 任务入口，重建运行环境、声明运行、消费 Runner 事件并持久化 | 调用 bootstrap 提供的 Worker Runtime 和共享 Agent Service/Runner。 |
| bootstrap/runtime.py | 提取 API 与 Worker 共用的 Agent 图和适配器装配 | 仍由 bootstrap 作为组合根；不把运行时组装放到 Router 或业务 Agent 目录。 |
| frontend/src/shared/api/http.ts 与 chat feature | 解析 SSE frame，持有每个活动 run 的 AbortController 和 cursor | 页面切换只 abort 监听；停止操作单独调用后端 cancel。 |

### 关键流程

提交：浏览器 POST /api/agents/{agent}/chat/stream → Service/CRUD 使用可信用户和稳定 request_id 原子创建或查回会话、run、消息及请求映射 → Celery agents queue → 专用 agent-worker → AgentRunner/LangGraph → Redis Stream。Worker 持有现有会话级 PostgreSQL advisory lock，并以 queued -> running 的条件更新声明执行权；重复投递遇到运行中的锁时不修改运行。若 Celery 因 Worker 丢失重投、锁已释放但数据库仍为 running，Worker 写入 AGENT_WORKER_INTERRUPTED 终止事件并标记失败，不从不确定的 Checkpoint/外部副作用位置盲目重放。

当前连接与续接：POST 响应以 SSE 读取同一个 Redis Stream；断线后浏览器 GET /api/agents/listen/{conversation_id}?run_id=...&after=... → Router 先校验会话所有者及 run 归属 → Service 从 Redis Stream 重放游标之后事件并阻塞等待新事件。

活动与历史：页面刷新 → GET /api/conversations/active 返回当前用户的 queued/running 列表 → 恢复会话并从本地保存的游标 listen；无活动 run 或事件已过期 → 使用 GET /api/conversations/{conversation_id}/messages 恢复已入库消息。

终止：显式 cancel → 当前主体授权检查 → Redis 设置 run 取消标志 → Worker 的取消轮询停止图执行 → 先写 run.cancelled 事件，再保存终态并释放 PostgreSQL advisory lock。正常完成和错误同样先持久化现有终止事件，再保存 completed/failed 状态。

采用独立 Agent Worker 是因为现有 SSE 请求取消会关闭 Runner 生成器，而现有 Celery/Redis Broker 可跨 API 进程和实例调度任务。Agent Worker 使用单独队列，避免当前串行 PDF 文献任务阻塞聊天；事件存 Redis Streams 而不是 Broker Pub/Sub，确保离线事件可重放。API 和 Worker 继续共享 PostgreSQL、Checkpointer、AgentRegistry 与既有消息历史，不复制业务图。

## 9. 接口、数据与兼容性变更

### API

| 接口 | 行为 |
|---|---|
| POST /api/agents/{agent}/chat/stream | 保留路径和 SSE 返回；接收 request_id，原子创建/复用 run 后入队；响应头提供 X-Conversation-ID、X-Run-ID，连接读取同一 Redis Stream。 |
| POST /api/agents/{agent}/runs/{run_id}/resume | 保留路径；接收新的 request_id，校验回答后提交续跑任务，并读取该 run 后续事件。 |
| GET /api/agents/listen/{conversation_id}?run_id=...&after=... | 新增续读；Last-Event-ID 优先于 after；没有 run_id 时仅在唯一活动 run 时推断。 |
| GET /api/conversations/active | 新增当前用户的所有 queued/running 会话和 run；没有活动任务时返回空 items 列表。 |
| GET /api/conversations/{conversation_id}/status | 新增该会话最新 run 的状态、最后事件 ID 和经过筛选的错误摘要。 |
| POST /api/agents/{agent}/runs/{run_id}/cancel | 路径保留；取消请求跨 API/Worker 进程生效，并在终态前持久化 run.cancelled。 |
| POST /api/v1/literature/chat/stream | 路径保留；文献范围继续在 Service 校验，任务走同一后台队列与 Redis Stream。 |
| GET /api/conversations/{conversation_id}/messages | 保持现有历史恢复行为；不因事件过期删除或修改历史。 |

SSE 的业务 event、JSON data 和 id 在首次发布与重放中保持一致；AgentEvent 字段继续包含 event_id、event_type、conversation_id、run_id、sequence、timestamp、data。业务事件 ID 改为对应 Redis Stream 的稳定游标，序号对单 run 单调递增。heartbeat 保持连接级行为，不作为生成业务事件写入回放流。

### 数据与 Redis

- PostgreSQL 新增 agent_run_requests，唯一键为 (user_id, request_id)，保存请求摘要和关联 run；相同 key、不同请求摘要返回稳定 409。该表只解决提交去重，不代替会话、消息或运行记录。
- agent_runs.status 增加 queued；活动查询包含 queued/running，等待回答仍是 waiting。
- 运行元数据保存必要的消息 ID、附件/文献 ID、任务结果 ID、安全错误摘要，以及事件是否已开始和终态游标；Worker 通过消息 ID 从既有消息表取回输入。
- Redis key 按 conversation_id 和 run_id 隔离。事件 append 原子分配 Stream ID 和序号，执行长度裁剪和 TTL，并在独立 run 元信息中维护最新游标。重连时检测 earliest ID，避免在游标已被裁剪时静默漏事件；Stream key 缺失但数据库记录显示该 run 已发布事件时按过期处理。
- 事件保留建议默认 AGENT_EVENT_MAX_LENGTH=2000、AGENT_EVENT_TTL_SECONDS=86400。以上是方案默认值，可在审阅时调整。
- Redis 同时承载现有 Celery Broker。使用独立 key 前缀和 agents queue；Compose Redis 已开启 AOF。

### 兼容及部署

- request_id 对旧客户端可选以保持可调用性；新版前端始终发送稳定 UUID。没有 request_id 的旧客户端不享有重试去重保证。
- conversation_id、run_id 继续以十进制字符串传输；事件游标是 opaque 字符串，不按 JavaScript 数字处理。
- 部署顺序：备份数据库 → 应用 011 迁移 → 部署 API 与 Agent Worker → 部署新版前端。Worker 使用 AGENT_WORKER_SNOWFLAKE_ID，需与 API 和 literature Worker ID 不同；扩多个 Worker 时逐实例使用唯一值。
- 回滚旧版前先停止新提交并排空 agents 队列；旧版不了解 queued 状态和新 Worker 任务。事件 key 有 TTL，不需要数据回滚。

## 10. 分步实施计划

### 步骤 1：持久化活动状态与提交幂等

- **目的：** 在排队前得到稳定会话/run，并让同一用户对同一请求重试时复用原运行。
- **涉及文件：** backend/agent/schemas/run.py、backend/app/models/run.py、backend/app/models/agent_run_request.py、backend/app/models/__init__.py、backend/app/crud/agent_submission.py、backend/app/crud/run.py、backend/app/schemas/agent.py、backend/app/schemas/conversation.py、backend/migrations/011_agent_run_requests.sql。
- **实施内容：** 增加 queued 状态和用户级 request 映射；在数据库事务中创建或查回会话、run、首条消息和请求映射；校验同 key 请求摘要；按 owner 查询活动运行和会话最新 run。
- **前置依赖：** 无。
- **验收标准：**
  - [ ] 同用户同 request_id、同请求内容返回同一 conversation/run，数据库只有一条用户消息和一条 request 映射。
  - [ ] 同 request_id 携带不同请求摘要返回稳定冲突，不覆盖旧请求。
  - [ ] 不同用户的 request_id 空间相互独立，活动运行查询只返回调用用户的 queued/running runs。
  - [ ] 迁移后既有五种状态保留且 queued 可写；消息表结构不变。
- **验证方式：** CRUD/Service 单测、PostgreSQL 事务集成测试、迁移在空库和当前结构副本上的验证。

### 步骤 2：将 Runner 执行移到可复用 Worker Runtime

- **目的：** Runner 执行不再由 HTTP SSE 消费者拥有。
- **涉及文件：** backend/agent/persistence/interfaces.py、backend/agent/persistence/memory.py、backend/agent/runner.py、backend/app/service/agent.py、backend/bootstrap/runtime.py、backend/bootstrap/agent_worker.py、backend/app/service/agent_tasks.py、backend/infra/agent_task_queue.py、backend/infra/celery_app.py、backend/infra/settings.py。
- **实施内容：** Runner 接受预先分配的 run 并由 Worker 执行；以持久化消息 ID 读取输入；抽取 API/Worker 共用运行时装配；新增 Celery Agent task 和独立队列；Worker 原子声明 queued 状态，重复投递时不重复执行已完成/等待/终态 run。
- **前置依赖：** 步骤 1。
- **验收标准：**
  - [ ] API 断开 SSE 消费后 Worker 任务仍执行并将最终助手消息写入现有 messages。
  - [ ] 关闭/重启 API 不取消已由 Celery 接收的 Agent task。
  - [ ] 现有七种注册 Agent 均可在 Worker Runtime 中取得原图和 Provider 配置。
  - [ ] literature-worker 继续只处理文献队列；Agent task 进入专用 agents 队列。
  - [ ] Worker 业务异常产生受控错误摘要；硬退出后的重投按 advisory lock 判断原 Worker 是否仍活跃，不能安全续跑时生成 AGENT_WORKER_INTERRUPTED 终态，不静默留下 running run。
- **验证方式：** 静态 Agent task 测试、Worker runtime 组装测试、Redis/PostgreSQL 下的 Worker 启停集成检查。

### 步骤 3：增加 Redis Stream 和共享取消信号

- **目的：** 让已发布事件跨连接和 API 实例可回放，并使停止请求到达真正运行任务的 Worker。
- **涉及文件：** backend/agent/persistence/interfaces.py、backend/agent/streaming/publisher.py、backend/infra/agent_event_store.py、backend/infra/settings.py、backend/.env.example、backend/app/service/agent_tasks.py、backend/agent/runner.py。
- **实施内容：** 在事件 append 时分配稳定 Stream ID/序号，先写入再发布；按会话/run 做 XREAD、heartbeat、长度和 TTL；检查游标是否早于最早保留项；取消 key 以 TTL 限制生命周期，Runner 通过共享信号轮询。
- **前置依赖：** 步骤 2。
- **验收标准：**
  - [ ] 每条业务事件在多个 API/Worker 实例间只分配一次 ID；按 after 读取仅返回后续事件。
  - [ ] 不同会话或不同 run 的事件互不串流；Redis stream 的长度和 TTL 达到配置值。
  - [ ] 过早游标返回明确过期信号，Redis 故障返回稳定 503，不泄漏 Redis URL 或内部异常。
  - [ ] listener 关闭不会写取消信号；显式停止会让 Worker 发出并持久化 run.cancelled。
  - [ ] 完成、错误和主动停止均先持久化原有终止事件，再写入最终 run 状态。
- **验证方式：** 新增事件存储契约测试、Worker 事件顺序测试、真实 Redis Streams 集成验证。

### 步骤 4：接入提交、listen、状态、活动查询和文献专用流程

- **目的：** 让所有前端 SSE 智能体入口都使用后台执行，并为恢复提供经过授权的查询入口。
- **涉及文件：** backend/app/service/agent.py、backend/app/router/agents.py、backend/app/router/conversation.py、backend/app/service/literature.py、backend/app/router/literature.py、backend/app/schemas/agent.py、backend/app/schemas/conversation.py、backend/app/schemas/literature.py、backend/agent/errors.py、backend/app/exceptions/handlers.py。
- **实施内容：** 现有 POST/resume 入队后继续读取 Redis Stream；增加 listen、active list 和会话 status；实现 Last-Event-ID 优先级、唯一活动 run 推断和安全状态码；文献范围在入队前验证/保存；沿用现有 cancel 路径但使用共享取消。
- **前置依赖：** 步骤 1–3。
- **验收标准：**
  - [ ] SSE 业务事件名称和 JSON 字段与原协议相同，重放帧的 event/data/id 与最初发布一致。
  - [ ] listen 在任何事件存储读取前校验主体、conversation 和 run 归属；猜测他人 ID 只能得到安全 404。
  - [ ] Last-Event-ID 优先于 after；无 run_id 时只有一个活动 run 才继续，多于一个时返回清晰 409。
  - [ ] 完成、失败、取消、过期、run 不存在、Redis 不可用分别有可识别且安全的结果。
  - [ ] 文献助手仍拒绝未授权或未就绪文献，图只收到已验证 document IDs。
- **验证方式：** backend/tests/test_api.py 和 test_service.py 覆盖业务事件契约、状态码、授权边界与文献回归。

### 步骤 5：前端续接、刷新恢复与会话切换

- **目的：** 用户可在断线、刷新和切换会话后恢复进度，同时把停止与断开分开。
- **涉及文件：** frontend/src/shared/api/sseParser.mjs、sseParser.d.mts、http.ts、聊天 api/agent.ts、api/conversations.ts、api/literature.ts、hooks/useChatSession.ts、ChatPage.tsx、components/ConversationSidebar.tsx、frontend/tests/sseParser.test.mjs。
- **实施内容：** fetch SSE parser 读取 id/event/data；首个 POST 保存响应头中的会话/run ID；每 run 用 sessionStorage 保存最后游标；断线通过 GET listen + Last-Event-ID 重连；切换时 abort 旧 listener，不调用 cancel；刷新先取活动列表；终态/过期时加载历史；通过 run/message history 恢复未回答的追问题目。
- **前置依赖：** 步骤 4。
- **验收标准：**
  - [ ] 网络断开后相同 run 自动按最后游标重连；重放的重复事件按 event ID 去重。
  - [ ] 切换会话关闭旧读取器且不请求 cancel；旧生成仍继续，回到旧会话显示离线期间结果。
  - [ ] 页面刷新能优先打开活动会话；同用户多个活动会话均可从列表恢复。
  - [ ] 任务结束或事件过期后前端读取历史，waiting 问题可以重新显示和回答。
  - [ ] 显式停止仍调用 cancel 并显示“已停止生成”；普通连接关闭不显示停止状态。
- **验证方式：** Node SSE parser 单测、前端类型构建，以及浏览器人工检查断线/刷新/切换/停止流程。

### 步骤 6：部署、配置和文档

- **目的：** 将共享存储和后台 Worker 变成可部署、可运维的项目能力。

- **实施内容：** 增加 agent-worker 服务、配置和队列说明；记录接口、状态、迁移、Redis 保留策略、运行边界和实际验证。
- **前置依赖：** 步骤 1–5。
- **验收标准：**

## 12. 风险、假设与运行考虑

- **非阻塞假设：**
  - 事件流默认最多 2,000 条/run、保留 24 小时；SSE 心跳复用现有 SSE_HEARTBEAT_SECONDS。
  - 每个 Agent Worker 进程使用 solo/单并发，避免共享 Snowflake Worker ID 产生重复 ID；通过部署多个 Worker 扩展并发，每个实例必须配置唯一 ID。首个本地/Compose 实例建议用 AGENT_WORKER_SNOWFLAKE_ID=2（API 默认 0，literature-worker 默认 1）。
  - request_id 为 UUID，幂等映射在 PostgreSQL 随运行记录保留，不依赖 Redis TTL。
- **主要风险及应对：**
  - Celery/Redis 是至少一次投递。重复投递用用户级 request 映射、run 状态原子 claim 和 PostgreSQL advisory lock 控制；Worker 强制终止后不能保证外部模型或图片工具副作用 exactly-once。若原进程死亡且无法安全续跑，按 AGENT_WORKER_INTERRUPTED 终止并允许用户重新提交，避免静默悬挂或重复执行未知副作用。
  - API 无法与 Redis Broker 做跨系统原子提交。提交先保存 queued run/message，再确认投递；投递暂时失败返回 503，同一个 request_id 重试会复用原 run 并再次投递，不应要求客户端换 key。
  - Redis 与 Celery 共用 Redis 服务。使用不同 key 前缀/queue；事件数量与 TTL 有界，监控内存和 Broker 队列长度。
  - 活动运行查询需批量获取 Stream 最新 ID，避免对每条记录逐个建立 Redis 连接；Redis 故障不应错误宣告 run 终止。
  - listen 在发送 SSE 响应头前完成鉴权和状态预检；开始流后遇到 Redis 故障则断开连接并由客户端重试，不能伪装为生成失败事件。
  - 用户消息已入库，助手消息在 Runner 收到完整 AIMessage 时入库。若 Stream 过期且回复尚未完整入库，历史只能恢复已保存消息，无法还原尚未持久化的部分 token。
- **安全 / 隐私 / 性能 / 可观测性：**
  - 先查会话 owner，再读取 run 和 Stream；越权与不存在统一 404。稳定错误码区分事件过期、任务结束和基础设施不可用。
  - Redis 事件内容沿用已过滤的 AgentEvent，不保存异常堆栈、凭据或原始第三方响应；任务 payload 以 ID 为主，输入文本从已有消息记录读取。
  - Worker 日志仅记录 run/conversation ID、Agent、稳定错误码和异常类型，不记录消息原文。
  - 监测 queued/run 执行时间、任务失败数、事件流过期数、Redis 错误和队列积压；运行状态以 agent_runs 为准，不以 HTTP/SSE 连接判断。
- **发布、迁移或回滚：**
  - 011 迁移只新增幂等映射和扩大状态允许值，不修改既有消息内容；部署前备份并先迁移。
  - 先启用数据库迁移，再部署 API/Agent Worker，最后部署前端；新 Worker 队列必须有消费者后才开放新版本提交。
  - 回滚前暂停新提交、等待 active Agent runs 终止并排空 Agent queue；保留向前迁移的数据表，旧版不会处理新 queued 状态。
