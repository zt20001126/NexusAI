# SSE 协议重构实施方案

> 日期：2026-10-20（Asia/Shanghai）  
> 状态：已实施；实际验证结果见 [任务级变更记录](../change-records/2026-10-20-012-SSE协议重构.md)

## 1. 结论与已确认需求

方案可行，但需要先修正消息标识、追问结束、Redis 写入和结果卡关联四处边界。目标事件 JSON 恰有 `event_id`、`event_type`、`timestamp`、`data`；类型为 `start/message/status/end/heartbeat`。`end.data.status` 为 `completed/waiting/cancelled/failed`，失败详情为 `error: {code, message}`。业务事件使用同一 run 的 Redis Stream ID，UTC 时间；SSE 帧 `id/event` 与 JSON 对齐。`conversation_id/run_id` 保留在服务端内部事件、运行记录、请求路径和提交/恢复响应头，不出现在 SSE JSON 的任意层级。保留后台执行、断线续传、取消、追问恢复及所有权校验。

非流式 `/api/agents/{agent}/chat` 同步投影四字段；Research REST 从内部运行上下文和消息快照提取会话及任务结果。

## 3. 必要设计修正

1. **消息身份与落库。** `runner.py::_events_for_message` 目前只在 AIMessage 完成后调用 `MessageStore.save`，增量既无 ID 也无块 ID。先由运行器为每条将要展示的助手消息预留雪花 `message_id`，建立或预留对应数据库记录，然后发送第一个增量；最终以同一 ID 更新内容并发快照。消息存储协议和 PostgreSQL/Memory 实现需支持按 ID 更新且校验会话、角色；避免重试重复建行。不能把一整个 run 当作一条消息，因一个 run 可有题卡、回复等多条消息。文本块 `block_id` 在消息创建时分配，所有增量及快照保持不变。若生成中断，历史消息应有明确的已持久化部分或受控清理规则。
2. **快照与增量。** `runner.py::_stream_graph` 目前按节点缓存文本并以 `startswith` 比较后补发，前端 `upsertAssistantMessage` 按 `assistant-${runId}` 拼接/替换。需按消息和文本块缓存；最终快照来自已保存的规范化内容，覆盖该 `message_id`。对同一节点多次输出、模型改写、断线重放及历史刷新，均以快照收敛。不要把工具原始响应或大结果放进块；结构化结果仅放 `task_result_id` 与有界摘要。
3. **追问阶段顺序。** `runner.py::_events_for_message` 当前先写待答元数据（仅内存）、保存题卡，再发送 `question.required`，随后可能发 `task_result.updated`；`RedisAgentEventStore.listen` 在题卡事件立即返回，故其后事件不会进入本次监听。建议先确认图 Checkpoint 可读取，持久化待答元数据和题卡及任务关联，发送 `message(snapshot)`（含 question、必要的 task_result 块），最后发送 `end(waiting)`；`listen` 只以 `end` 停止。恢复继续原 run_id，产生新 `start` 阶段；等待态不得清理问题、Checkpoint 或游标元数据。
4. **任务卡归属。** 当前 `task_results.message_id` 初始可为空，稍后由 `_events_for_message` 的 `link_message` 关联；前端临时卡按 `assistant-${runId}` 放置。新协议每次结果状态变化必须明确所属 `message_id`，先建立该消息/关联，再发含 `task_result` 块的**完整快照**；保留数据库 `task_results` 作为结果状态权威来源，历史查询投影出同样的卡片。若结果在题卡阶段产生，关联题卡消息；恢复后有新回复时，是否迁移卡片必须给出单一规则。建议不迁移既有卡片，仅更新原题卡消息；最终回复可另建消息。
5. **游标与去重。** Redis 按 run 分流；前端按 `conversation_id/run_id` 存最近已处理业务 ID，在调用回调后才确认游标，回放时丢弃 `<=` 已处理 ID。现有 `http.ts` 在回调前调用 `onEventId`，`useChatSession.ts` 又从每条事件取 run 标识，均需修改。心跳不更新已处理游标；流结束只看 `end`，其中 `waiting` 进入待答态。410 时以已持久化历史和运行状态重建，再从安全游标续接，不能默默跳过可能未落库的消息。
6. **Worker 异常补偿。** `_record_worker_start_failure` 目前以 `question.required` 识别 waiting，需改成识别 `end(waiting)`，并区分同一 run 的不同阶段。状态与终止事件写入有失败窗口，补偿应基于 PostgreSQL run 状态、待答元数据及 Redis 最后阶段事件，幂等补写同状态 `end`；不能把 waiting 补成 failed，也不能为已完成阶段重复发布。检查 Celery 丢进程、Redis 写入失败、终态落库失败三种窗口。

## 4. 接口及数据约定建议

`message.data` 用判别联合：`{operation:"delta", message_id, block_id, offset, text}` 或 `{operation:"snapshot", message_id, content:{blocks:[...]}}`。增量带文本块字符偏移，前端据此忽略已包含在数据库快照中的重放片段，并按位置合并同一游标重放。每块含稳定字符串 `id` 和 `type`；`text` 含 `text`，`image` 含受授权保护的应用 URL（及必要附件标识），`question` 含题目/轮次，`task_result` 含任务 ID、类型、状态和有界可展示摘要。追问的 `run_id` 仅在历史消息响应中供刷新恢复，不复制到 SSE 块；运行标识从响应头和当前监听上下文读取。`status.data` 只提供有界工具阶段和安全摘要。`end.data.error` 仅失败时出现。可使用 Pydantic 判别联合约束事件载荷，并在外发投影处拒绝未知块及多余顶层字段。

当前 PostgreSQL `messages.content` 是 JSONB，`task_results.message_id` 已存在，`agent_runs.status` 已允许 `waiting`；只增加 JSON 内容块 ID 和存储更新方法时，**不需要 SQL 数据库迁移**。旧历史块没有 `id`，建议在历史 API 投影时确定性生成兼容块 ID（如消息 ID 加块序号），不批量改写旧 JSONB；历史 API 可以渐进保留旧 `question_batch/question_answers`，由前端适配，SSE 新协议仍严格四种内容块。若要求历史 API 的数据库原文也立即只含四种块，才需要数据迁移，并需另行审阅。

无旧 Redis 协议兼容的发布切换应先停止旧 API/Worker 写入、等待或有控制地结束 `queued/running/waiting` 运行，完成 Checkpoint/消息/结果核对，再隔离旧事件键（新版本前缀或按 run 明确删除）并同时发布新 API/Worker/前端。保留 PostgreSQL 历史。对仍在等待追问的运行，优先在新协议下验证其 Checkpoint 与待答元数据后恢复；无法验证者维持历史可读并提示重新发起，不能悄然置 completed。旧 Redis 游标与新流不可混用，前端需清理旧 `sessionStorage` 游标。旧事件自然 TTL 过期并非充分迁移策略：旧 run 可能重用键及游标。

## 6. 分阶段实施与验收

1. **冻结契约和上线门槛。** 在 `agent/streaming/events.py`、`features/chat/api/agent.ts` 与 `docs/接口文档.md` 写类型与示例，明确历史题卡和非流式 API 取舍；验收：四字段和每种 data 均有可校验样例，旧运行处置步骤可执行。
2. **后端消息持久化。** 在 `agent/runner.py`、`agent/persistence/interfaces.py`、`agent/persistence/memory.py`、`app/crud/message.py`、`app/service/conversation.py`、`app/schemas/conversation.py` 添加预留/更新消息及规范块 ID；验收：首个 delta 前已有稳定消息 ID，多个助手消息不串，完成后历史 ID/内容与快照一致，取消/失败中断可恢复。
3. **事件流、追问与任务结果。** 在 `agent/streaming/sse.py`、`agent/runner.py`、`infra/agent_event_store.py`、`app/service/agent.py`、`app/service/agent_tasks.py` 以及相应 Router/文献/Research Service 调整原子写入、投影与补偿；验收：`question` 后有且仅有 `end(waiting)`，之后原 run 恢复新阶段；任务卡更新可见且回放一致；SSE 帧 ID/类型与 JSON 相等，旧字段不泄露。
4. **前端切换。** 在 `shared/api/http.ts`、`features/chat/api/agent.ts`、`api/conversations.ts`、`model/messages.ts`、`hooks/useChatSession.ts`、`components/MessageList.tsx` 按 ID/块合并消息，按游标去重并渲染所有块；验收：加载、空、失败、完成、waiting、刷新和 410 历史恢复均正确，图片和题卡可操作。
5. **联合回归与发布。** 更新清单所列测试、`docs/架构说明.md`、`docs/数据库文档.md`、变更记录与 `CHANGELOG.md`；验证权限、取消、Celery 重试/丢进程、Redis 裁剪/过期、文献和 Research 非流式入口；按停写、清理/隔离旧流、同步部署执行。验收：无旧事件被新客户端解析，已有历史可读；运行状态与最终事件/数据库一致。

## 7. 自测清单与主要风险

- 后端在 `backend/` 执行 `python -m pytest -q`，重点补充消息预留/完成、图输出改写、追问题卡顺序、同 run 多阶段、任务卡状态、Redis 原子 ID/裁剪/过期、断线重复帧、Worker 异常补偿和越权测试。
- 前端执行 `npm test`、`npm run build`，补消息归并/游标去重/题卡和卡片更新测试；人工用多个智能体检查图片、Listing、科研、劳动法律和文献对话的刷新与恢复。
- 风险：消息先建行后失败可能留下空记录；题卡显示先于可恢复 Checkpoint；Redis 写入和数据库提交非同一事务；结果状态与消息卡片快照可能暂时分叉；长 run 达到 2,000 事件裁剪或 24 小时 TTL。分别用明确消息状态/历史收敛、Checkpoint 可读检查、幂等补偿、任务结果权威查询及 410 恢复处理。
- 实施验收后检查 `git diff`、`git diff --check`，写实际变更记录与 `[Unreleased]`；不由 Agent 创建 commit。

实施完成后更新任务级变更记录并汇报实际验证结果；旧事件由 Redis v2 键空间隔离，不提供转换路径。
