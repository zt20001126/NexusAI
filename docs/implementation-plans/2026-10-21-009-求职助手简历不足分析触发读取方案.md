# 求职助手简历不足分析触发读取实现方案

> 日期：2026-10-21
> 状态：待审阅
> 需求确认：含已标注的非阻塞假设

## 1. 目标与背景

- **要解决的问题：** `read_saved_resume` 已提供给求职助手，但当前提示词仅说明工具能力，没有规定何时使用，模型可能在用户要求分析本人简历不足时不读取已保存简历。
- **功能目标：** 将“用户要求诊断本人简历并指出不足或改进空间”设为读取已保存简历的明确触发场景。
- **预期最终效果：** 用户明确要求分析自己简历不足时，求职助手先调用 `read_saved_resume`，再依据工具返回的简历事实给出有证据的不足分析和可操作建议；其他一般性简历问题不会仅因涉及简历而触发该工具。

## 2. 已确认需求

- **使用者 / 调用方：** 求职助手 `job_agent` 的模型。
- **触发方式：** 用户明确要求解析、诊断或评估自己的简历，并指出不足、缺失、弱项或改进空间；按语义识别，不依赖固定关键词。
- **输入：** 当前用户消息、会话上下文，以及无参数 `read_saved_resume` 工具返回的已保存求职事实。
- **输出：** 基于已保存简历实际内容的不足分析；区分简历没有写明与用户实际没有相关经历，并给出具体补充或改写建议。
- **主流程：**
  1. 模型判断用户是否在请求评估本人简历的不足或改进空间。
  2. 命中时，回答前调用 `read_saved_resume` 一次，不向工具传入主体或简历 ID。
  3. 根据读取状态和返回字段分析；不得把空字段推断为用户没有相应经历。
  4. 不命中时，按原有求职对话处理，不调用该工具。
- **业务规则与边界：** 一般简历知识、模板咨询、单纯润色用户给出的片段、岗位推荐等不单独触发该工具；若同一请求也明确要求评价本人简历不足，则按触发流程处理。工具只读固定主体下的已保存简历。
- **异常行为：** `not_found` 时说明没有可读取的已保存简历，请用户保存或提供内容；`unavailable` 时说明暂时无法读取，不得假装已分析。仅使用实际返回字段，不臆测简历中没有提供的事实。
- **权限与数据范围：** 继续使用现有主体 `nexusai-resume-owner` 和工具字段白名单，不改变固定主体共享访问边界。
- **约束：** 不修改工具实现、简历 CRUD/API、数据库、会话、SSE、前端或模型 Provider；不新增依赖。

## 3. 范围

- **本次包含：** 提示词明确正向触发条件和不触发场景；更新提示词契约测试、工具调用测试及求职助手能力文档；更新 CHANGELOG 和实施任务记录。
- **本次不包含：** 引入确定性意图分类器或在图节点强制调用工具；扩展简历读取字段；调整岗位推荐、简历编辑或多用户授权。

## 6. 架构设计

### 模块职责与边界

| 模块 | 职责 | 依赖方向 / 边界 |
|---|---|---|
| `prompts/system.md` | 简明声明简历不足分析需要先读取已保存简历。 | 作为 Agent 系统指令，不实现数据访问。 |
| `prompts/agent.md` | 定义触发语义、反例、工具结果解释和失败处理。 | 使用现有工具名称和状态，不直接访问数据库。 |
| `tests/test_job_agent.py` | 验证提示词明确包含触发/不触发规则，并覆盖合格请求的工具调用闭环。 | 复用现有 Agent 工厂和脚本模型，不新增依赖。 |

### 关键流程

```text
用户请求
  → job_agent 根据语义判断是否为“分析本人简历不足”
      → 是：调用 read_saved_resume（无参数）→ 按返回状态和事实分析
      → 否：沿用原有回答流程，不调用读取工具
```

本项目已由模型绑定工具并依据模型发出的 tool call 进入工具节点。自然语言意图需要结合语境判断，当前没有独立意图分类器。因此推荐先用明确、优先级清晰的系统/Agent 提示词规则约束调用，并用提示词契约和工具链测试覆盖；本方案不把这描述为对任意模型的代码级确定性保证。若后续需要硬性保证，再单独评估确定性分类/路由。

对工具结果的提示规则：

- `found`：只评价实际返回的字段；描述“简历未体现”时不要断言“用户没有”。建议必须对应到可观察的内容或信息缺口。
- `not_found`：告知当前没有已保存简历，请用户保存或粘贴简历内容；不生成针对该简历的具体不足结论。
- `unavailable`：告知读取暂不可用；不声称已读取或分析数据库简历，可邀请用户粘贴内容继续。
- 当前对话里用户明确给出比数据库更新的信息时，优先采用该明确更新，并区别说明保存版本与当前补充内容。

## 10. 分步实施计划

### 步骤 1：定义简历不足分析触发契约

- **目的：** 让模型能够区分本人简历诊断和一般简历话题。
- **涉及文件：** `backend/agents/job_agent/prompts/system.md`、`backend/agents/job_agent/prompts/agent.md`。
- **实施内容：** 明确用户要求分析/诊断本人简历的不足、缺失或改进空间时，必须在作答前调用 `read_saved_resume`；自然语言等价表达按语义识别。明确通用简历建议、单纯片段润色和无关求职请求不触发，除非同一请求还要求评价本人简历不足。列明 `found`、`not_found`、`unavailable` 的答复边界。
- **前置依赖：** 无。
- **验收标准：**
  - [ ] 提示词明确要求符合条件的请求先调用读取工具后再分析。
  - [ ] 提示词明确排除一般简历知识和单纯润色等未请求简历诊断的场景。
  - [ ] 提示词禁止根据空字段推断用户没有相关经历，并说明两种失败状态的处理。
- **验证方式：** 检查提示词文本和现有系统/Agent 提示拼接结果。

### 步骤 2：增加触发行为回归覆盖并同步文档

- **目的：** 防止后续提示词修改移除触发约定，并保持能力说明一致。
- **涉及文件：** `backend/tests/test_job_agent.py`、`backend/agents/job_agent/README.md`、`CHANGELOG.md`、实施任务变更记录。
- **实施内容：** 增加对正向触发与非触发规则的提示词断言；调整脚本模型工具链用例，使用户请求明确分析已保存简历不足并验证最终回复依赖工具结果；更新项目文档与任务记录。
- **前置依赖：** 步骤 1。
- **验收标准：**
  - [ ] 提示词测试可验证明确的触发和排除规则。
  - [ ] 脚本模型在简历不足分析用例中调用无参数工具，工具结果送回模型后完成答复。
  - [ ] 文档描述的触发范围与提示词一致。
- **验证方式：** 执行后端求职 Agent 相关测试及后端完整测试；审阅 `git diff --check` 和最终差异。

## 12. 风险、假设与运行考虑

- **非阻塞假设：** 若简历诊断请求附带粘贴/上传内容，仍调用保存简历工具；将当前用户明确提供的最新信息与数据库事实区分使用。用户若审阅时不接受该假设，可调整方案后再实施。
- **主要风险及应对：** 提示词无法形成硬性的程序级调用保证；通过强制措辞、明确反例及回归契约降低漏调概率。如未来要求绝对确定性，需要另行设计意图路由，而非扩充本次工具。
- **安全 / 隐私 / 性能 / 可观测性：** 工具主体和字段白名单不变；触发频率仅增加于简历不足分析请求，每次该类请求最多要求读取一次。固定主体仍共享同一份已保存简历。
- **发布、迁移或回滚：** 无数据库迁移及 API 变更；回滚提示词和测试/文档改动即可恢复原有模型自主选用行为。
