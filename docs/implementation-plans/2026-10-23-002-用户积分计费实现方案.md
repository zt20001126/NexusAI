# 用户积分计费实现方案

> 日期：2026-10-23（Asia/Shanghai）
> 状态：已实施；目标 Compose 数据库迁移完成，浏览器手工验收待进行
> 依据：[用户积分计费需求](../requirements/2026-10-23-001-user-credit-billing.md)
> 本文同时记录本次实施结果；实际差异和验证见[任务级变更记录](../change-records/2026-10-23-003-用户积分计费实现.md)。

## 1. 目标、范围与确认记录

已确认：新注册用户一次性获得 100 积分；旧用户从 0 分开始；所有智能体的新对话轮次消耗 1 分；智能体回复、同一运行的追问答案免费；系统运行失败或用户主动取消后退款；余额展示在顶部账号邮箱左侧；每次 API 项目进程启动预热 Redis；增加独立的积分表和积分明细表。本期没有充值、人工补分或积分明细页面。

用户进一步确认：**所有新对话提交入口必须提供稳定 `request_id`，允许旧调用方为此升级**。相同主体、相同 `request_id`、相同输入重试时复用既有运行及结果；同一标识搭配不同输入返回冲突。结构化追问恢复也统一要求 `request_id`，但不发生新扣费。

预期体验：余额足够时，受理新消息并立即显示扣 1 分；余额不足时请求被拒绝，聊天历史不产生该条消息；失败或取消后余额回升 1 分。`waiting` 是中途等待答案，暂不退款；正常完成但内容为“不知道”或业务弃答，仍属于完成态并保留扣费。

## 3. 设计与关键流程

### 3.1 持久余额、明细和 Redis

PostgreSQL 的 `user_credits` 是余额事实来源，`credit_entries` 是每次赠送、扣费、退款的不可变明细。Redis 只保存 `{balance, version}` 的共享读取缓存；启动时分页加载全部余额，用版本比较写入，避免 API 多实例启动的旧快照覆盖较新扣费。注册、扣费和退款在数据库提交后发布新版本。API 进程启动预热；Celery 每次任务会重建 `build_lifespan`，因此 Worker 运行时跳过全量预热，只按实际变动更新缓存。

发送前先读 Redis 作快速预检。对同一 `request_id` 的重试，先核对已有 run 与输入摘要并复用，**即使当前余额为 0 也不能误拒或再次扣费**。新请求遇到缓存缺失或值为 0 时以数据库余额复核，避免退款已提交但缓存尚未更新造成误拒；缓存值为正也必须由数据库事务再次检查余额，防止并发超扣。Redis 无法访问时按需求文档的假设拒绝新提交并返回受控 503。缓存更新失败不能撤销已提交的数据库事务；余额查询以数据库为准，下一次成功的更新、缺键回填或重启预热修复缓存。

### 3.2 注册与新消息受理

注册：`AuthApplicationService.register` 调用仓储在**同一 PostgreSQL 事务**内创建 `users`、`user_credits(balance=100)` 和一条 `registration_grant(+100)` 明细。邮箱已存在时三个写入均不发生。缓存发布在事务提交后执行。项目其他内部路径若按可信主体隐式创建 `users` 账号，只建立 0 分积分行，不享受注册赠送。

新消息：Router 完成参数和主体校验，Service 统一预检积分，Runner 校验智能体、会话及附件并生成稳定 `run_id`、`message_id`。新增事务型 `PostgresBilledChatSubmissionStore` 在一个数据库事务中先按请求键检查既有 run，再验证会话归属、锁定该用户积分行，并原子写入会话（若新建）、用户消息、queued run、余额减 1 和 `message_debit(-1)` 明细。余额不足则整个事务不写入会话/消息/run；并发请求被行锁串行化。现有 `agent_runs.metadata.request_key` 唯一约束继续承担提交去重；明细的事件键承担扣费/退款去重。成功提交后才绑定已校验附件并入队；绑定或入队失败时使本轮失败并按终态退款，避免可执行的未计费 queued run。监听/补投队列必须先验证该 run 有扣费明细或属于同轮免费恢复。失败 run 的同键重试返回原失败结果；用户重新发起一轮需要新的请求键。

这需要将 `AgentRunner.prepare_chat` 的验证/构造与多次独立 `save` 拆开，通过新的持久化协议一次提交；不能仅在现有 `prepare_chat` 前后加一条独立扣费语句，否则进程崩溃会留下“已扣费但无运行”或“未扣费但可执行”状态。内存测试适配器保留同一协议契约。`AgentApplicationService.chat`、`submit_chat` 和文献包装服务共用此受理路径；追问 `submit_resume` 继续原 run，不触发新扣费。

### 3.3 终态退款与异常恢复

Worker 对 `end(failed)`、`end(cancelled)` 在对客户端发布终态前调用幂等退款：锁定余额行，按 `refund:<run_id>` 唯一键写 `run_refund(+1)` 并更新余额版本；重复 Worker 或重复终态只返回已有结果。`end(waiting)`、`end(completed)`不退款。取消请求本身仅发出取消信号，待运行实际变为 `cancelled` 才退款。断开 SSE 监听不改变运行状态。

`_record_worker_start_failure` 的终态恢复也调用相同退款操作。API 启动时先扫描已持久化的 `failed/cancelled` run 与未退款的扣费明细并补退，再预热 Redis；该对账只处理已确认终态的运行，不能将排队/运行/等待状态误退。Worker 崩溃后现有任务恢复仍负责确定终态；对账确保“终态已保存、退款前崩溃”最终可修复。日志只记 run/user 内部 ID 和错误码，不记录消息正文、密钥或完整请求。

### 3.4 余额展示与一致性

复用 `GET /api/auth/session`，在已登录的 `data` 中增加 `credits`，不新增余额查询端点，也不改变注册/登录成功响应。余额值从持久表读取，避免页面刷新时读到未发布成功的旧缓存。前端注册或登录后调用现有会话查询，取得余额再展示；新消息获受理、收到失败/取消终态、重新聚焦窗口时刷新会话余额。余额加载失败显示独立错误/待重试状态，不把未知余额伪装为 0。0 分仍可浏览历史和提交已等待的免费追问答案。

### 3.5 有取舍的决定

1. **两表而非 `users.credits` 字段**：用户明确要求积分表和积分明细表；`users` 继续负责账号，余额与流水由积分模块维护。
2. **PostgreSQL 负责扣费原子性、Redis 负责读取加速**：只在 Redis 扣减无法与 run、消息、明细一起提交，也难以安全处理重启及并发；数据库每次扣费仍需一次写事务，Redis 消除普通预检的频繁余额读。
3. **扩展会话响应而不新增余额 API**：现有会话查询已用于账号栏，增加一个非敏感余额字段即可满足展示与刷新；注册/登录成功响应保持原样，本期无明细查询页面。

## 4. 数据库设计与迁移清单

| 表 / 字段 | 操作与约束 | 用途、复用判断和迁移 |
|---|---|---|
| `users.user_id` | 保持不变；被两表外键引用 | 复用现有可信账号映射，不增加用户积分列 |
| `user_credits.user_id` | 新增 `BIGINT` 主键、外键到 `users.user_id` | 一人一份余额；现有 `users` 无积分，不能承担用户要求的独立积分表 |
| `user_credits.balance` | 新增 `BIGINT NOT NULL DEFAULT 0 CHECK (balance >= 0)` | 可用积分；迁移为每个旧用户插入 0，注册事务显式写 100 |
| `user_credits.version` | 新增 `BIGINT NOT NULL DEFAULT 0` | 余额单调修订号，保护 Redis 并发缓存更新顺序 |
| `user_credits.updated_at` | 新增 `TIMESTAMPTZ NOT NULL` | 最近积分变化时间，便于核对缓存与运行日志 |
| `credit_entries.event_key` | 新增 `TEXT` 主键；`grant:<user_id>`、`debit:<run_id>`、`refund:<run_id>` | 每个业务事件只记一次；现有消息/run 表不保存积分变动，无法替代明细 |
| `credit_entries.user_id` | 新增 `BIGINT NOT NULL` 外键到 `users.user_id`；索引 `(user_id, created_at)` | 按用户追溯明细；不提供跨用户读取 |
| `credit_entries.run_id` | 新增可空 `BIGINT`，消息扣费和退款填同一 run ID，注册赠送为空；不设删除级联外键 | 关联计费轮次并保留审计线索；由同事务创建的 run 保证新写入关联有效，历史 run 后续清理不删除积分明细 |
| `credit_entries.kind` | 新增 `TEXT NOT NULL`，限定 `registration_grant/message_debit/run_refund` | 明细类型可解释，拒绝未知事件 |
| `credit_entries.delta` | 新增 `BIGINT NOT NULL`，注册 `+100`、扣费 `-1`、退款 `+1` | 与业务规则一一对应；加入类型/符号检查 |
| `credit_entries.balance_after` | 新增 `BIGINT NOT NULL CHECK >= 0` | 便于核对每次变动后余额与争议排查 |
| `credit_entries.created_at` | 新增 `TIMESTAMPTZ NOT NULL` | 明细发生时间；索引支持按用户、时间审计 |
| `conversations`、`messages`、`agent_runs` | 表结构保持不变 | 复用现有会话、消息和 run ID；仅改变新消息受理时的事务组装 |

迁移拟新增 `backend/migrations/018_user_credits.sql`：创建两表和约束/索引，按现有 `users.user_id` 插入余额 0 的积分行，**不写赠送明细**。全新数据库通过 ORM 元数据创建两表；已有数据库先运行 018 再启动新版 API/Worker，因为 `create_all` 不会回填旧用户。迁移须可在已执行过的库上安全识别状态，采用明确的执行记录或可重入 SQL，避免重复回填覆盖现有余额。回滚应用版本前必须先停止新计费写入并保留两表数据；直接删除表会丢失余额和审计，不能作为无损回滚。

| `POST /api/agents/{agent}/runs/{run_id}/cancel` | 保持不变 | 返回仍表示“已请求取消”；退款在实际 `cancelled` 终态发生 | 主动取消退款 |

| `GET /api/conversations/{conversation_id}/messages` | 保持不变 | 读取历史不扣费 | 非消息操作免费 |
| `GET /api/conversations/{conversation_id}/status` | 保持不变 | 查询运行状态不扣费 | 失败/取消后的余额刷新依据 |
| `POST /api/uploads/images`、`POST /api/v1/literature/documents` | 保持不变 | 上传附件/文献不扣费 | 非对话操作免费 |
| `end` SSE 事件 | 保持不变 | 继续使用 `completed/waiting/failed/cancelled`；余额刷新由前端按既有终态触发 | 失败和取消退款 |

`request_id` 必填属于**明确接受的兼容性变化**：既有直接调用这些 POST 接口的客户端必须生成一次并在网络重试时复用。`ChatRequest`、`LiteratureChatRequest`、`ResearchRequest` 和 `ResumeRequest` 的校验及 `docs/接口文档.md` 要同步。注册之外不增加可修改积分的公开接口，也不公开他人的余额或明细。错误由 `backend/app/exceptions/handlers.py` 转为统一 `success/code/message`，不暴露底层 Redis/SQL 异常。

## 9. 风险、假设与发布顺序

- **业务假设：**以运行 `failed` 判定系统失败；正常完成但业务弃答不退款。缓存无法核验时拒绝新消息。两项来自需求文档的已标注假设。
- **兼容性：**`request_id` 必填会使旧请求返回校验错误；上线前更新所有前端和直接 API 调用方。相同请求必须保存并复用该 ID；不能用相同消息文本推断重试。
- **一致性：**必须验证 run/消息/扣费一次事务、终态退款幂等、Redis 版本比较和补偿对账；任何一项缺失都会导致错扣或错退。
- **性能：**API 启动对账和全量预热应分页读取，避免一次性加载全部用户；Worker 每次任务启动不做全量预热；Redis 只作读缓存，数据库仍承担每次真实扣费写入。
- **发布：**先备份并执行 018 迁移，确认旧用户 0 分，再同时部署 API、Worker、前端；上线后核对余额表与明细及失败退款。旧用户在本期无补分入口，故无法发起收费对话；这是已确认的产品影响。
- **回滚：**停止新写入后回退应用版本并保留积分两表；如要继续恢复计费，先核对终态和明细，不对旧用户重新赠分。不可直接删除两表做无损回滚。
