# 聊天消息显示上传图片实现方案

> 日期：2026-10-19（Asia/Shanghai）  
> 状态：已实施，待审核  
> 需求确认：用户明确要求消息表仅保留 `message_id`、`conversation_id`、`role`、`content`、`created_at`

## 1. 目标与已确认需求

用户发送图片后，图片应在对应聊天消息中显示，刷新及历史翻页后仍可查看。消息正文统一写入 `content JSONB`：文字、图片引用和用户回答的问题可以位于同一条消息的内容块中。`messages` 不保留 `run_id`、`sequence`、`attachment_ids` 或 `status` 字段。图片字节留在私有 OSS，`content` 只保存附件 ID。按 `created_at` 展示消息；时间相同时以 `message_id` 稳定排序，避免翻页重复或漏项。

适用范围为现有图片智能体、Listing 智能体及共用消息历史；PDF 文献上传沿用独立流程。上传失败时保留待发送草稿和图片。消息读取与图片读取继续校验可信主体的会话归属。

## 3. 架构与数据流

`content` 统一采用 `{"blocks": [...]}`。块类型包括 `{"type":"text","text":"..."}`、`{"type":"image","attachment_id":"..."}` 和 `{"type":"question_answers","answers":{...}}`。发送图片时，Runner 把文字和已验证的附件 ID 写入同一用户消息。回答追问时，同时保存可见文字和结构化答案。历史 Service 为图片块补充受控 `image_url`，不把对象键或字节写入数据库/API。

上传 → Runner 保存消息 `content` → OSS 绑定 → 会话历史按 `(created_at, message_id)` 分页 → 前端渲染内容块 → 授权图片接口校验消息关联并读取 OSS。

历史接口采用 `before_message_id` 游标；存储层先读取锚点的 `created_at` 和 `message_id`，再用二元组比较查询更早消息。图片接口为 `GET /api/conversations/{conversation_id}/messages/{message_id}/attachments/{attachment_id}/image`，越权或不存在返回 404，OSS 故障返回 502。

006 迁移先把旧文本 `content` 转成文字块，再把运行元数据中的历史附件 ID 回填到每次运行首条用户消息，最后删除旧字段、约束和索引。旧追问答案只有可见文本，无法无损恢复结构化键值，保留为文字块。新消息记录结构化答案。007 迁移将 JSON `context` 字段更名为 `content`。迁移应先于新版后端部署；未在真实数据库执行前不宣称已上线。

## 5. 分步实施与验收

1. **统一消息内容。** 修改模型、Runner、存储协议和迁移。验收：文字、图片和答案按约定写入 `content`；旧文字与历史附件可转换；目标表只有五个字段。
2. **历史与授权读取。** 修改 Service、Schema 和 Router。验收：返回时间正序消息；相同创建时间按 ID 排序；图片只能由消息所属会话的用户读取；错误关联返回 404。
3. **前端展示。** 修改 API 类型、转换模型、列表和游标。验收：发送后及刷新历史后图片位于正确消息；向前翻页无重复遗漏；图片链接可键盘聚焦。
4. **验证与记录。** 运行相关后端测试、前端测试和构建、迁移语法解析及 `git diff --check`，同步文档与变更记录。验收：结果如实记录，工作区仅含任务改动。
