# 求职助手简历内容优化与确认保存方案

> 日期：2026-10-22
> 状态：已实施
> 需求确认：已结合现有代码形成方案，含已标注的非阻塞假设

## 1. 目标与背景

- **要解决的问题：** 当前 `job_agent` 可以读取已保存简历、分析简历并推荐岗位，但没有简历修改候选、用户确认和受控写回能力。
- **功能目标：** 允许用户指定一个简历部分或整份简历进行优化；未指定范围时先用题卡询问；优化结果先展示给用户，用户明确采纳后才更新当前简历记录。
- **预期最终效果：** 用户能在聊天中完成“选范围 → 预览优化稿 → 采纳、重生成或取消 → 确认后写回”，未经明确采纳时数据库简历保持原样。

## 2. 已确认需求

- **使用者 / 调用方：** 简历工作台中的求职助手 `job_agent`。
- **触发方式：** 用户明确要求优化本人简历内容。
- **输入：** 用户的优化目标与指定范围；已保存简历；补充的事实或写作偏好；对候选版本的确认选择。
- **输出：** 优化候选内容、确认题卡、保存结果或未保存说明。
- **主流程：**
  1. 识别用户指定的简历部分；若未指定，先调用现有 `ask_user_questions` 询问范围。
  2. 调用现有 `read_saved_resume` 获取当前已保存简历及其版本标记。
  3. 若缺少完成优化所需的事实，先向用户补问；不得生成或补入虚构经历、技能、成果、数据、学历或雇主信息。
  4. 模型生成仅针对所选范围的候选补丁，经新增的结构化候选工具校验后展示给用户。
  5. 调用现有题卡询问用户是否采用、重生成、补充要求后重生成或取消。
  6. 用户明确选择采用后，由后端确定性节点校验待确认候选与当前答案匹配，再执行数据库更新；模型不能直接调用数据库写入能力。
  7. 部分优化仅合并所选范围，其他数据原样保留；整份优化覆盖可优化的职业内容，但保留身份和展示字段。
  8. 保存成功后清除待处理候选状态并告知用户；保存失败或简历版本已变化时不覆盖现有数据，说明原因并要求重新读取/生成。
- **业务规则与边界：** 仅更新当前简历记录；未确认、取消、重生成和运行中断均不写库。简历事实以最新数据库内容为准。姓名、电话、邮箱、年龄、照片引用和排版配置不由模型改写。公司、学校、职位、专业、学位、日期和成果数字等事实只能保留或依据用户明确补充修改。优化局部不得改写未选择的区域。
- **异常行为：** 无已保存简历时提示用户先保存简历或提供内容；简历读取/保存失败时不伪称完成；保存期间若检测到简历版本变更，拒绝覆盖并重新读取；候选不符合简历 DTO 时拒绝写入并要求重新生成。
- **权限与数据范围：** 沿用当前固定主体 `nexusai-resume-owner`。模型工具不接收 owner、principal 或数据库记录 ID；本方案仍只适用于本机或可信私有网络部署。
- **约束：** 沿用现有 Resume JSONB 表和题卡/SSE 协议，不新增简历 API，不引入新的简历版本表。

## 3. 范围

- **本次包含：** 优化范围选择、候选生成与结构验证、候选 Checkpoint 状态、用户确认/重生成/取消、确认后局部合并或整份可编辑内容更新、并发版本冲突保护、文档和测试。
- **本次不包含：** 自动发布或投递简历、职位检索、简历历史版本/撤销系统、修改照片和排版、跨用户主体迁移、增加简历自由文本字段。

## 4. 需求澄清记录与非阻塞假设

| 事项 | 方案约定 | 对方案的影响 |
|---|---|---|
| 未指定范围时题卡如何覆盖部分与整份简历？ | 使用现有单选题卡四个选项：“求职意向与基本信息”“教育经历与专业技能”“工作经历与项目经历”“整份简历”。用户也可在问题中直接指定更精确范围。 | 无需更改题卡协议；分组保持四选项限制。 |
| “整份简历”是否允许修改个人身份资料？ | 不允许；整份优化只覆盖求职内容，姓名、联系方式、年龄、照片和排版配置保留原值。 | 避免模型改写身份字段和触发照片存储流程。 |
| 事实字段能否由模型改写？ | 公司/学校/职位/专业/学位/日期及数值成果默认原样保留；只有用户明确给出更正事实后才可更新。 | 结构化字段进入候选前需要与读取数据核对。 |
| 可重复重生成次数 | 求职助手单次运行最多 10 轮结构化提问；其余智能体保留现有 3 轮限制。 | 需要给共享 Runner 增加可注入的每 Agent 轮数上限，支持多次确认和重生成而不放宽全局边界。 |
| 提案未完成时的留存 | 待确认候选临时保存在当前会话 Checkpoint，便于用户稍后恢复；采用、取消或重新生成替换候选后清除待处理状态。聊天中已经展示的文本仍按现有会话消息保留规则留存。 | Checkpoint 会在等待期间包含用户简历候选内容；不新增日志或独立长期存储。 |

## 6. 架构设计

### 是否新增节点与工具

**新增一个模型可调用工具和一个专用图节点；复用现有读取与提问工具；不新增模型可直接调用的保存工具。**

| 能力 | 方案 | 原因 |
|---|---|---|
| 读取源简历 | 复用 `read_saved_resume`，按需扩展版本/条目标识 | 已有固定主体和隐私投影。 |
| 询问范围和用户决策 | 复用 `ask_user_questions` | 已支持四选项单选、暂停与恢复。 |
| 提交优化候选 | 新增 `stage_resume_optimization` 工具，严格校验范围、候选字段和简历版本；只生成候选，不写数据库 | 模型需要把候选以结构化形式交给图状态，供用户确认后恢复。 |
| 确认与保存 | 新增 `resume_optimization_node`，处理候选暂存、确认答案门控、写入和清理 | 数据库写入必须由服务端根据当前题卡 ID 和明确的 `accept` 答案触发，不能仅依赖模型“听懂了同意”。 |
| 文本优化 | 继续由现有 `agent_node` 调用模型完成 | 不需要单独的生成模型节点；提示词限定事实边界和输出结构。 |
| 数据合并与持久化 | 新增/扩展 `app.service.job_resume` 用例，调用仓储条件更新 | 应用 Service 负责简历校验与保存规则；Agent 只依赖注入的读写能力。 |

`resume_optimization_node` 不提供给模型任意保存入口。模型生成 `stage_resume_optimization` 调用后，节点校验工具调用结果并把最小补丁写入 `JobAgentState`；向用户展示候选并发出确认卡。用户恢复运行时，节点仅在 Checkpoint 中存在待确认补丁、上一张题卡 ID 为 `resume_optimization_decision` 且本次答案精确为 `accept_and_save` 时执行写入。选择重新生成或取消时清理/替换候选，数据库不变。未匹配到有效待确认题卡的普通消息不能触发写入。

### 模块职责与数据流

```text
用户请求
  → job_agent 识别范围；未指定时调用 ask_user_questions
  → read_saved_resume 获取简历和 updated_at
  → agent_node 生成结构化优化候选
  → stage_resume_optimization 工具校验候选（无副作用）
  → resume_optimization_node 暂存最小补丁到 Checkpoint
  → agent_node 展示候选并调用 ask_user_questions 决策
  → 等待用户
      ├─ 重新生成：清理旧补丁，按原始简历与补充要求再生成
      ├─ 取消：清理补丁，不写库
      └─ 采用：resume_optimization_node 校验题卡答案
            → JobResumeWriter 比较 updated_at、合并选定区域、校验完整 ResumeContent
            → PostgreSQL 条件更新；成功后清理补丁并回复
```

部分补丁仅允许更新目标区：求职意向、技能文档、工作经历描述、项目经历描述。教育经历只保留原始事实，不允许模型改写。对工作/项目条目使用读取快照中的稳定序号键定位，写入时以源 `updated_at` 做比较；公司、学校、岗位、学历、日期及条目 ID 不因模型重写而改变。全简历候选覆盖上述可编辑职业内容；姓名、电话、邮箱、年龄、照片 ID 和 `style_config` 从最新数据库记录保留。所有富文本和合并后的完整内容通过现有 Pydantic 简历契约后才能写入。

## 9. 接口、数据与兼容性变更

- 不新增 HTTP API、SSE 事件或数据库表/列；简历继续存于现有 JSONB `content` 与 `style_config`。
- 不修改现有外部简历保存 API。智能体确认保存通过内部 Service/Repository 条件更新。
- 新增的模型工具只处理结构化候选，不接受主体或数据库 ID；用户确认卡使用现有题卡契约。
- Runner 轮数参数向后兼容，默认值仍为现有 3；仅 `job_agent` 使用专用较高上限。
- 用户会话中已展示的候选按聊天历史现有保留策略保存；等待确认期间 Checkpoint 暂存候选补丁，流程结束时清除待处理状态。不会新增候选专用长期表或将候选内容写入日志。

## 10. 分步实施计划

### 步骤 1：定义优化补丁和候选工具

- **目的：** 使模型只能提交目标明确、结构化并可验证的候选内容。
- **涉及文件：** 新增 `resume_optimization.py`、`tools/stage_resume_optimization.py`；修改 `resume_snapshot.py`（如需增加版本/条目映射）。
- **实施内容：** 限制 section 和目标字段；候选携带源 `updated_at`；工作/项目按有序条目标识；拒绝身份/照片/样式等模型修改字段；候选工具不产生数据库副作用。
- **前置依赖：** 无。
- **验收标准：**
  - [x] 模型无法在候选结构中提交 `owner_id`、principal、简历数据库 ID 或照片/联系方式字段。
  - [x] 候选范围外字段无法被更新。
  - [x] 伪造经历、结构不合法或超出简历 Schema 限制的候选被拒绝。
- **验证方式：** 候选 Schema 和工具单元测试覆盖允许范围、额外字段、长度与事实字段边界。

### 步骤 2：实现候选暂存及确认保存门控

- **目的：** 在同一 Checkpoint 会话中预览候选，并保证只有本次明确确认才写数据库。
- **涉及文件：** 修改 `state.py`、`graph.py`、`factory.py`；新增 `nodes/resume_optimization_node.py`；修改 `backend/app/service/job_resume.py`、`backend/app/crud/resume.py`、`backend/bootstrap/runtime.py`。

## 12. 风险、假设与运行考虑

- **非阻塞假设：** “整份简历优化”覆盖现有职业内容字段，不包含姓名、电话、邮箱、年龄、照片或样式；简历题卡使用四个预设分组，用户可在原消息中给出更细范围。
- **主要风险及应对：** 模型可能生成无依据的成果表述；要求候选字段仅能修改所选的自由文本/求职意向，结构化事实保持原样，且用户确认前不保存。纯文本语义事实仍需用户预览确认，结构校验不能证明其真实。
- **并发风险及应对：** Checkpoint 中候选可能基于旧版本；保存时比较简历 `updated_at`，不匹配则拒绝覆盖并要求刷新候选。
- **隐私与留存：** 等待确认期间候选补丁保存在会话 Checkpoint；采纳、取消、重生成后清理待处理 state。聊天中给用户展示的候选仍会按现有聊天历史保留。不得将简历正文或候选内容写入应用日志。
- **单人主体限制：** 保留固定 `nexusai-resume-owner` 部署边界，不能将此方案视为多用户授权模型。
- **发布、迁移或回滚：** 不需要数据库迁移；代码回滚不影响现有简历记录。新工具及 Runner 参数须保证非求职 Agent 的默认轮数不变。
