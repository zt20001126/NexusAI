# 基础智能体提问工具实施方案

> 日期：2026-10-20
> 状态：已实施（自动化验证完成，人工 UI 验收未执行）
> 需求确认：已确认题卡回答方式、每批题数和题型；触发规则按通用助手最小行为设计

## 1. 目标与背景

- **要解决的问题：** `base_agent` 已有模型与普通工具循环，但工具执行后只能回到模型，不能把问题交给用户、暂停运行并继续原任务。
- **功能目标：** 为基础对话助手增加一个通用结构化提问工具，并用现有 Runner、题卡、SSE 和恢复 API 跑通一次完整的人机交互。
- **预期最终效果：** 用户可要求助手用选项题卡澄清信息；助手也可在缺少关键选择、无法继续时询问。用户选完后，原运行恢复并继续回答。

## 2. 已确认需求

- **使用者 / 调用方：** 使用 `basic_conversation_agent` 的聊天用户；基础智能体通过共享 `AgentRunner` 接入聊天应用。
- **触发方式：** 模型根据通用提示词判断何时调用；测试使用脚本模型明确触发，避免依赖模型临场判断来验证流程。
- **输入：** 每批 1–3 道结构化问题；本工具仅接受单选题，每题恰好 4 个带说明的选项，不允许自定义输入。
- **输出：** 复用现有 `question` 消息块、`end(waiting)`、恢复 API 和最终助手消息。
- **主流程：**
  1. 用户请求需要选择的信息，或明确要求用题卡提问。
  2. 模型调用 `ask_user_questions`，工具校验并返回共享问题协议。
  3. 基础智能体图在工具节点后结束本阶段；Runner 保存题卡，运行转为 `WAITING` 并发送现有 SSE 事件。
  4. 用户在现有题卡中选择答案；前端调用恢复 API，Runner 校验答案并从同一 run、同一 Checkpoint 继续。
  5. 模型结合用户答案完成任务，Runner 保存并发送最终回复。
- **业务规则与边界：** 每批至少 1 题、最多 3 题；本工具只出单选题，每题恰好 4 个选项；每次运行最多 3 轮。题目字段沿用 `agent.schemas.question`，工具入参 schema 将题型进一步限制为 `SingleChoice`，不改变其他智能体继续使用多选题的能力。
- **异常行为：** 畸形题卡由 Runner 以稳定错误码终止；工具异常使用现有受控工具错误；不进入无限等待状态。
- **权限与数据范围：** 沿用现有会话归属校验、run 授权、Checkpointer 线程隔离和恢复幂等规则。
- **约束：** 当前没有具体领域场景；提示词只定义通用触发边界，不加入业务流程或新的题型。

## 3. 范围

- **本次包含：** 基础对话助手注册提问工具；图支持提问后暂停；Python 直接调用能返回待回答结果；在现有聊天应用中验证选择、恢复和最终回答；更新基座说明。
- **本次不包含：** 自由文本题、自定义选项、领域专用工具、专用前端交互、数据库迁移、新的 HTTP/SSE 协议。

## 4. 需求澄清记录

| 需要确认的问题 | 确认结果 | 对方案的影响 |
|---|---|---|
| 用户如何回答工具提出的问题 | 沿用结构化选项题卡；新工具只允许单选 | 复用现有题目字段、题卡组件和恢复接口；以工具专属 schema 收窄题型，不改其他智能体共享 schema。 |
| 每批题目数量和题型 | 用户确认每批 1–3 题，且必须是单选题 | 工具入参 schema 强制 1–3 道 `SingleChoice`；每题继续使用现有四选项结构。 |
| 尚无具体应用场景时如何验证触发 | 用户说明先走通基础流程，暂不复杂化 | 提示词采用通用边界；自动化测试用脚本模型强制调用，人工验收使用明确请求题卡的消息。 |

**通用出题规则：** 只在用户明确要求选择题卡，或任务缺少会实质改变结果的关键选择时调用。每批生成 1–3 道最重要的问题；不重复询问上下文已有信息；每题提供 4 个清晰、互斥且有意义的选项。若问题需要自由描述、选项不足 4 个、选项无法合理穷尽，或该信息不会改变结果，则使用普通自然语言澄清或基于已知信息继续，不调用题卡工具。每批只调用一次工具。提示词和工具描述表达这些语义规则；工具专属 schema 强制题目结构与单选类型，共享 Runner 继续负责答案校验。

## 6. 架构设计

### 模块职责与边界

| 模块 | 职责 | 依赖方向 / 边界 |
|---|---|---|
| `agents/base_agent/tools/ask_user_questions.py`（新增） | 定义无外部副作用的提问工具及清晰的工具描述；复用共享 Question 字段，使用局部 payload schema 强制 1–3 道单选题，并返回 `{success, data.questions}` | 基础智能体依赖共享 `agent.schemas.question`，不访问应用、数据库或前端；不改变其他智能体的多选能力。 |
| `agents/base_agent/factory.py`、`tools/__init__.py` | 将提问工具作为基础对话助手的内置能力；自定义 `BaseAgent` 仍可显式注入工具 | 保留基座依赖注入边界。 |
| `agents/base_agent/graph.py` | 普通工具执行后继续模型循环；提问工具执行后结束图阶段 | Runner 通过现有暂停工具协议识别结束原因。 |
| `agent/tools/registry.py`、`agents/base_agent/agent.py` | 让 Runner 识别新暂停工具；让直接 `ainvoke` 返回可辨识的待答结果 | 复用共享题卡协议；不改 HTTP API。 |
| Runner 与前端现有模块 | 保存题卡、等待答案、校验并恢复、渲染交互卡 | 不增加新的业务层或前端状态机。 |

### 关键流程

```text
用户消息
  -> BaseAgent agent_node
  -> ask_user_questions
  -> tool_node
  -> 图结束本阶段
  -> AgentRunner 校验题卡、保存 question block、end(waiting)
  -> 前端现有题卡组件
  -> resume API（结构化答案）
  -> 同一 run / Checkpoint
  -> BaseAgent agent_node
  -> 最终回答
```

将题卡作为一个无副作用工具接入 `base_agent`，而不是在工具内部直接访问前端或暂停 HTTP 请求。LangGraph 只负责返回可序列化的问题结果；共享 Runner 负责运行状态、历史消息、事件及恢复。这样新增能力复用现有协议，也保留基座模型与运行时解耦。

基础工厂默认提供该工具；低层 `BaseAgent` 仍通过 `tools` 注入，便于后续业务智能体决定是否启用。`AgentResponse` 需表达 `completed` 与 `waiting` 两种结果，避免直接调用在提问后误报“缺少最终答案”；产品聊天路径仍由 Runner 提供题卡和严格恢复校验。

## 9. 接口、数据与兼容性变更

- 对外 HTTP、SSE、恢复请求和题卡历史格式不变；前端继续提交 `{question_id: selected_label}`。
- 不新增表、数据库字段或迁移。问题继续保存在已有消息 JSON 和 run 元数据中，图 Checkpoint 仍复用现有存储。
- Python `AgentResponse` 从仅表达最终文本扩展为可区分 `completed`（含 `answer`）与 `waiting`（含 `questions`）。调用方需检查状态后读取对应字段；实施时更新基座 README 示例。
- 新工具只在基础对话工厂默认启用。`common_agent` 继续按普通自然语言交流，不改变既有产品行为。

## 10. 分步实施计划

### 步骤 1：定义提问工具与最小触发规则

- **目的：** 提供可被模型调用、且无需业务服务依赖的题卡工具。
- **涉及文件：** `backend/agents/base_agent/tools/ask_user_questions.py`（新增）、`backend/agents/base_agent/tools/__init__.py`、`backend/agents/base_agent/factory.py`、`backend/agents/base_agent/prompts/agent.md`。
- **实施内容：** 从共享 `Question` 继承/复用字段，定义工具专属 payload schema，将批次限定为 1–3 题、题型限定为 `SingleChoice`；将工具注册到基础助手；提示词和工具描述明确触发边界、题目优先级和四个互斥选项规则，普通开放式澄清仍用自然语言。
- **前置依赖：** 无。
- **验收标准：**
  - [x] 工具接受 1–3 道符合共享字段结构的单选题；拒绝 0 题、4 题、多选题、选项数不为 4、重复选项或允许自定义输入的题目。
  - [x] 其他智能体仍可通过共享 schema 使用现有允许的题型，未被新工具的单选限制影响。
  - [x] 仅 `create_basic_conversation_agent` 默认提供此工具；不启用的自定义 `BaseAgent` 不会意外获得它。
  - [x] 提示词和工具描述说明题型必须是单选，且只在用户明确要求题卡或关键选择确实影响结果时出题；未加入领域专属问题或固定业务流程。
- **验证方式：** 工具 schema 单元测试；检查基础工厂 `tool_registry` 内容及提示词文本。

### 步骤 2：贯通图暂停和基础调用响应

- **目的：** 让题卡工具结束当前图阶段，并让 Runner/直接调用都能识别等待状态。
- **涉及文件：** `backend/agents/base_agent/graph.py`、`agent/tools/registry.py`、`backend/agents/base_agent/agent.py`、`backend/agents/base_agent/schemas.py`、`backend/tests/test_base_agent.py`（新增）。
- **实施内容：** 增加工具后路由；登记暂停工具名供 Runner 使用；`ainvoke` 将问题结果映射成 `waiting` 响应，最终文本仍映射成 `completed`。
- **前置依赖：** 步骤 1。
- **验收标准：**
  - [x] 提问工具的 ToolMessage 结束该图阶段，不再被当作最终文本，也不触发普通工具循环。
  - [x] 普通工具调用后仍回到模型节点并产出最终文本。
  - [x] 直接 `ainvoke` 调用可返回带问题的 `waiting` 结果；正常回复仍返回 `completed` 和 `answer`。
- **验证方式：** 基座图路由测试、直接调用响应测试、已有基座输入与工具异常测试。

### 步骤 3：通过现有 Runner、题卡和恢复接口走通全流程

- **目的：** 验证产品聊天路径从工具调用到用户选择再到原任务完成。
- **涉及文件：** `backend/tests/test_runtime.py`；如需补充基座交互说明则同步 `backend/agents/base_agent/README.md`。
- **实施内容：** 使用确定性脚本模型触发题卡，调用现有 Runner 产出题卡事件和 `end(waiting)`，再提交合法选项并恢复同一 `run_id`，验证最终回答及历史答案。
- **前置依赖：** 步骤 2。
- **验收标准：**
  - [x] 首次运行保存 assistant `question` block、问题批次和待答 ID，并以 `waiting` 结束。
  - [x] 合法答案恢复同一 run；不匹配题目 ID 或无效选项仍被拒绝。
  - [x] 恢复后模型能读取用户选项并生成完成态回复，消息历史同时包含题卡和答案。
  - [ ] 前端现有交互卡片可渲染题目，并可通过现有 resume API 提交答案，无需新增 UI 协议。

自动化 Runner 集成已验证后端题卡、等待、答案校验、同一运行恢复及历史消息。人工 UI 验收未执行；本次没有启动前后端应用并连接真实模型服务，因此该验收项保留未完成。
- **验证方式：** `backend/` 下与 Runtime/Question 相关的 pytest；人工启动应用后，用“请用四选项题卡让我选一个学习计划风格，然后按我的选择给出计划”验证 UI。

- **实施内容：** 记录图路由、触发原则、waiting 响应和同会话恢复方式；任务记录只写实际完成内容与实际验证结果。
- **前置依赖：** 步骤 1–3。

## 12. 风险、假设与运行考虑

- **非阻塞假设：** 在没有领域场景时，用“用户明确要求题卡”作为稳定的人工验收触发；真实模型是否会主动判断某个信息“关键”由通用提示词引导，不作为自动化测试的唯一依据。必须具备 4 个有意义选项的离散选择才适合题卡；开放式问题留给自然语言。
- **主要风险及应对：** 模型可能不必要地出题或生成无意义选项；提示词强调克制，Question schema 校验格式，自动化使用脚本模型验证控制流。
- **安全 / 隐私 / 可观测性：** 工具没有外部副作用；题目与答案受现有长度和选项限制；权限与日志使用现有 Runner 机制。
- **发布、迁移或回滚：** 无数据库迁移。回滚时从基础工厂移除该工具并恢复图路由；已存题卡遵循当前共享协议，历史消息仍可读取。
