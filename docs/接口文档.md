# API 接口文档

后端使用 FastAPI 提供接口，OpenAPI/Swagger 地址为 `/docs`。大部分 JSON API 使用 `{"success": true, "data": ...}` 包装；SSE 事件直接使用公共事件协议。

## 身份与错误响应

API 使用服务端认证上下文中的可信主体标识，不接受请求体中的 `user_id`。浏览器通过 HttpOnly 会话 Cookie 认证；缺失、过期或撤销的会话访问用户数据 API 时返回 HTTP 401。健康检查和智能体目录为公开接口。会话、附件和任务结果均按可信主体校验。

## 邮箱账号认证

注册和找回密码使用邮箱验证码；日常登录使用邮箱和密码。验证码有效 10 分钟，最多允许 5 次错误尝试，每个邮箱和用途 60 秒可重新发送一次；验证码和临时会话放在现有 Redis 并设置 TTL。密码使用 scrypt 哈希保存在 `users.password_hash`。登录和注册成功后设置 HttpOnly、SameSite=Lax Cookie；生产环境默认启用 Secure。退出删除当前 Redis 会话，密码重置更新密码哈希后使此前会话失效。状态变更请求若包含 Origin，后端会校验其主机与请求 Host 一致。

| 路由 | 认证 | 说明 |
|---|---|---|
| `POST /api/auth/email-codes` | 否 | 请求注册或密码找回验证码；找回请求对未知邮箱保持相同成功响应 |
| `POST /api/auth/register` | 否 | 提交邮箱、验证码、密码及确认密码并建立登录会话 |
| `POST /api/auth/login` | 否 | 邮箱密码登录并建立登录会话 |
| `GET /api/auth/session` | 否 | 返回当前 Cookie 会话是否有效及邮箱 |
| `POST /api/auth/logout` | 否 | 撤销当前会话并清除 Cookie |
| `POST /api/auth/password-reset` | 否 | 通过找回验证码设置新密码并清除当前 Cookie |

新部署须配置 `MAIL_SMTP_USERNAME`（完整 QQ 邮箱地址）、`MAIL_SMTP_PASSWORD`（QQ 邮箱生成的 SMTP 授权码）和随机 `AUTH_CODE_PEPPER`；授权码不是 QQ 邮箱网页登录密码，不得提交到仓库。邮件使用独立的注册和密码重置主题，包含纯文本及 HTML 正文。验证码及会话依赖现有 `CELERY_BROKER_URL` 对应的 Redis，不增加 PostgreSQL 认证表。

会话、运行、消息、任务结果、附件和文献标识由后端生成雪花 ID，并以十进制字符串返回；请求中的这些 ID 也必须是纯数字字符串。前端应继续按字符串处理，避免 JavaScript 数值精度损失。智能体使用 `AgentType` 字符串枚举，当前值为 `common_agent`、`basic_conversation_agent`、`image_agent`、`listing_agent`、`research_agent`、`labor_law_agent`、`literature_reader_agent` 和 `job_agent`。会话列表和任务结果响应中的 `agent` 字段返回对应枚举值。

Agent 领域错误使用 `{"success": false, "code": "...", "message": "..."}`；冲突返回 HTTP 409，权限失败和资源不存在统一返回 404，事件流过期或运行已结束返回 410，队列或 Redis 暂时不可用返回 503。上传内容错误由 HTTP 400、413 或 415 表示。

## 简历助手

智能体市场中的“简历助手”是独立编辑工具，不属于聊天 Agent 注册表。每个邮箱账号通过服务端可信主体读写各自简历；既有固定主体 `nexusai-resume-owner` 的简历保留在原位置，不自动分配给新账号。

简历工作台左侧“07 求职助手”打开右侧对话区，使用已注册的 `job_agent` 和通用会话/SSE/追问接口。普通回复在模型生成期间发送 `message.delta`，完成后发送消息快照。求职助手按当前登录账号读取已保存简历的求职相关字段；不读取未保存草稿，不返回姓名、联系方式、年龄、照片或排版信息。用户要求优化已保存简历时，候选先暂存于会话 Checkpoint 并展示；只有对应确认题卡选择“确认采用并保存”且简历 `updated_at` 未变化时才调用后端写入。重新生成、取消和版本冲突均不保存。优化范围限于求职意向、工作年限、技能及工作/项目正文；身份资料、教育经历事实、雇主/职位/日期、照片与排版保持不变。用户要求解读或分析本人简历、评价优缺点，或明确要求根据简历推荐岗位时，助手会先读取保存版本；一般岗位咨询和单纯片段润色不会单独触发读取。用户询问适合的岗位时，助手仍可用现有题卡或普通对话补充关键资料，再由模型根据对话及已读取简历中的实际信息自主提出最多三个岗位方向及理由，经过工具校验后回答；不使用固定岗位列表，年龄不能作为推荐依据。用户提出与求职无关的问题时，助手会说明职责并引导用户提供求职信息；混合请求优先处理求职相关内容。求职助手不检索实时招聘职位。

成功 JSON 使用项目 envelope。简历及照片/PDF 响应均设置 `Cache-Control: private, no-store`。请求体不接受 `owner_id`、数据库 `id` 或时间戳。

### `GET /api/resume`

读取已保存简历。首次访问返回 `exists=false`、默认内容和排版配置，不创建用户或简历行。`content.skills` 使用 Tiptap JSON 文档，在一个编辑框中编写全部技能；可用 `doc`、`paragraph`、`text`、`hardBreak`、`bulletList`、`orderedList`、`listItem` 节点，以及 `bold`、`italic`、`underline` marks。工作和项目描述使用相同白名单的 Tiptap JSON。已有数据库升级此 API 前，必须先执行 `backend/migrations/015_resume_skills_tiptap.sql`。

### `PUT /api/resume`

整体保存 `content` 与 `style_config`。`content.basic_info` 的年龄 `age` 和工作经验年限 `work_experience_years` 均为可空整数，由用户手动填写，分别限制在 0–120 岁和 0–80 年；不接受出生年月字段，也不从工作经历日期计算年限。简历页首展示求职意向、工作经验年限，以及手机号、邮箱、年龄、第一条已填写学历。服务端还校验必填姓名、电话和邮箱、教育/工作/项目年月、条目数量与唯一 ID、Tiptap 节点和深度；技能文档最多 10,000 字符，单条工作/项目文档最多 4,000 字符，全简历富文本合计最多 20,000 字符。不再接受旧版 `string[]` 技能载荷。JSON 请求体上限为 256 KiB；校验失败返回 422，超限返回 413。保存后返回数据库确认的数据和时间戳。

`content.basic_info` 主要字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `name` | `string` | 姓名，保存时必填 |
| `phone` | `string` | 联系电话，保存时必填 |
| `email` | `string` | 邮箱，保存时必填 |
| `intended_position` | `string` | 求职意向 |
| `age` | `integer`（可空） | 手动填写的年龄，范围 0–120 |
| `work_experience_years` | `integer`（可空） | 手动填写的工作经验年限，范围 0–80 |
| `photo_id` | `string`（可空） | 私有证件照引用 |

教育背景按 `content.educations` 顺序保存；页首学历取其中第一条 `degree` 非空的记录。年龄或工作经验年限留空时传 `null`。

### `POST /api/resume/photo`

以 multipart/form-data 的 `file` 字段上传 PNG/JPEG 证件照，最大 5 MiB（也受 `IMAGE_UPLOAD_MAX_BYTES` 配置的更低上限约束）。服务端检查文件签名并写入当前主体的私有 OSS staging 前缀，不会立即替换已保存照片。成功响应包含随机 `photo_id`、`mime_type` 和 `file_size`；超过文件上限返回 413，空文件或签名无效返回 415。OSS 未配置返回 503，OSS 故障返回 502。

### `DELETE /api/resume/photo?photo_id={id}`

取消未保存的暂存照片，只能删除当前主体 staging 前缀中的对象；不接受对象键，也不删除已保存照片。格式不合法的 ID 返回 400，重复取消保持幂等，成功返回 `{ "photo_id": "...", "deleted": true }`。

### `GET /api/resume/photo`

读取数据库当前简历引用的私有证件照，返回经过签名和大小验证的 PNG/JPEG 字节，并设置 `X-Content-Type-Options: nosniff`。草稿照片使用浏览器本地 URL 预览，不通过此接口读取。

### `GET /api/resume/export/pdf`

只根据数据库已保存版本生成 A4 单页 PDF，不接收前端草稿。简历未保存返回 404；内容溢出返回 422 和 `RESUME_PAGE_OVERFLOW`；渲染超时返回 504，Chromium 不可用返回 503。导出以 `application/pdf` 附件返回，不写入后端持久目录。

## 后端健康检查

健康检查接口不要求用户认证，响应只包含健康状态、探测耗时和稳定错误码，不返回连接地址或底层异常文本。

### `GET /health/live`

返回 HTTP 200 表示后端进程当前能够处理 HTTP 请求。该接口不检查数据库和 Redis。

```json
{"status": "healthy"}
```

### `GET /health/ready`

返回最近一次后台巡检结果。后端启动时立即检查 PostgreSQL 和 Redis Broker，之后默认每 30 秒检查一次。依赖均可用且状态未过期时返回 HTTP 200；任一探针失败或巡检结果超过三个巡检周期时返回 HTTP 503。

```json
{
  "status": "unhealthy",
  "checked_at": "2026-10-19T02:30:00Z",
  "stale": false,
  "checks": {
    "postgres": {
      "status": "healthy",
      "latency_ms": 4.2,
      "checked_at": "2026-10-19T02:30:00Z",
      "error_code": null
    },
    "redis": {
      "status": "unhealthy",
      "latency_ms": 3000.1,
      "checked_at": "2026-10-19T02:30:00Z",
      "error_code": "TIMEOUT"
    }
  }
}
```

`HEALTH_CHECK_INTERVAL_SECONDS` 和 `HEALTH_CHECK_TIMEOUT_SECONDS` 分别控制巡检间隔和单项探针超时。Compose 每 10 秒检查一次 `/health/ready` 并将结果显示为后端容器健康状态；容器被标记为 `unhealthy` 本身不会触发自动重启。

### `POST /api/agents/{agent}/chat`

执行非流式对话，返回该次运行的完整事件数组。

### `POST /api/agents/{agent}/chat/stream`

以 `text/event-stream` 返回同一事件协议。请求 JSON：

```json
{
  "message": "帮我生成一张淘宝商品主图",
  "conversation_id": null,
  "attachment_ids": []
}
```

`message` 长度为 1–20,000 个字符。`conversation_id` 可省略或传 `null`，此时运行时创建会话。`attachment_ids` 可省略；最多 3 个不重复的上传标识。只有声明支持图片上传的智能体能接收附件。会话创建后绑定所属主体和 `agent`，不能在其他智能体路由下继续使用。

请求可附带 `request_id`（建议使用 UUID）；同一请求因网络重试时必须复用该值和相同输入。服务端按数据库运行记录中的幂等键复用会话、运行和用户消息。成功 SSE 响应的 `X-Conversation-ID`、`X-Run-ID` 响应头可在收到首个事件前用于建立恢复信息。

通过各智能体的 SSE 聊天入口请求时，统一返回五类事件：`start`、`message`、`status`、`end` 和 `heartbeat`。通用智能体与基础对话助手会转发面向用户模型节点的生成片段；图片、Listing、科研检索、劳动法律和文献解读等工作流会在任务结果或证据校验完成后，分段发送安全的最终文本。追问和任务结果作为消息内容块返回。

### `POST /api/agents/{agent}/runs/{run_id}/resume`

使用追问事件返回的会话和运行标识恢复原运行。

```json
{
  "conversation_id": "<conversation_id>",
  "request_id": "<本次恢复的稳定幂等 ID>",
  "after_event_id": "12-0",
  "answers": {
    "image_size": "1:1 方图（1024×1024）"
  }
}
```

追问恢复同样由 Agent Worker 在后台执行，并继续使用同一个 `run_id`。重试时复用 `request_id` 和答案；`after_event_id` 是提交答案前已收到的最后事件游标。成功响应通过 `X-Event-Cursor` 返回本阶段监听起点，浏览器在 POST 连接中断时从该游标重连，避免重放上一阶段的 `end(waiting)`。

### `GET /api/agents/listen/{conversation_id}?run_id={run_id}&after={last_event_id}`

重连既有运行的 SSE 事件流。服务端先校验会话所有权及 run 与会话的关系，再读取 Redis Stream。`Last-Event-ID` 请求头优先于 `after` 查询参数；只返回游标之后的事件，并在没有新事件时发送 heartbeat。未提供 `run_id` 时，只有该会话恰好有一个 queued/running 运行才会自动选择；多个活动运行返回 `RUN_ID_REQUIRED`。

每条事件 JSON 固定为 `event_id`、`event_type`、UTC `timestamp`、`data` 四个字段；不包含 `conversation_id`、`run_id` 或序号。SSE 帧 `id/event` 分别等于 JSON 的 `event_id/event_type`。事件 ID 是该 run 的 Redis Stream 单调游标（例如 `13-0`）。`end` 结束当前监听阶段；`waiting` 允许同一 run 后续恢复。收到 `EVENT_STREAM_EXPIRED` 或 `RUN_ALREADY_ENDED` 时，客户端应读取会话历史或运行状态。

若活动 run 的事件正文已过期，前端加载历史后会从活动接口提供的最新游标继续等待新事件，并附带 `X-Agent-History-Loaded: true`。服务端仍会重新校验会话所有权、run 归属和游标；该头只表示客户端已用数据库历史恢复旧内容。

| HTTP 状态 | 错误码 | 说明 |
|---|---|---|
| 400 | `EVENT_CURSOR_INVALID` | 游标超出该 run 已生成的事件范围 |
| 404 | `CONVERSATION_ACCESS_DENIED`、`RUN_NOT_FOUND` | 会话或 run 不存在或当前主体不可访问 |
| 409 | `RUN_ID_REQUIRED`、`RUN_PREPARATION_PENDING` | 会话活动 run 不唯一，或幂等请求仍在保存首条消息 |
| 410 | `EVENT_STREAM_EXPIRED`、`RUN_ALREADY_ENDED` | 事件不能续读；加载数据库会话历史 |
| 503 | `EVENT_STORE_UNAVAILABLE`、`AGENT_QUEUE_UNAVAILABLE` | Redis 事件存储或后台队列暂时不可用 |

### `GET /api/conversations/active`

返回当前登录主体所有 queued/running 运行，支持一个用户同时有多个后台会话：

```json
{
  "success": true,
  "data": {
    "items": [
      {
        "conversation_id": "<conversation_id>",
        "run_id": "<run_id>",
        "agent": "common_agent",
        "status": "running",
        "last_event_id": "13-0"
      }
    ]
  }
}
```

没有活动运行时返回空 `items`。`GET /api/conversations/active/latest` 和 `GET /api/agents/conversation/active/latest` 返回最近一条活动运行；没有时 `data` 为 `null`。

### `GET /api/conversations/{conversation_id}/status?run_id={run_id}`

按会话归属返回最近一次运行（或指定 `run_id`）的 `run_id`、`status`、`last_event_id` 和安全错误摘要。状态包含 `queued`、`running`、`waiting`、`completed`、`cancelled` 和 `failed`。已有会话历史接口 `GET /api/conversations/{conversation_id}/messages` 用于事件过期或 run 结束时恢复已入库消息。

答案 key 必须与待回答问题 ID 集合完全匹配。结构化题卡每轮包含 1–3 道题，每次运行最多 3 轮；每题只能是单选或多选，必须恰好提供 4 个 `{label, description}` 选项对象，并且不接受自定义输入。单选答案是一个选项标签，多选答案是 1–4 个不重复标签。后端按题型和选项校验答案；空白答案、空多选答案和当前批次之外的问题 ID 会被拒绝。恢复运行和读取题卡历史时使用相同的结构化题目协议。

### `POST /api/agents/{agent}/runs/{run_id}/cancel`

请求取消当前主体拥有且仍在运行的任务。成功响应包含 `run_id` 和 `cancel_requested`。

## SSE 事件

每条事件 JSON 固定为：

```json
{
  "event_id": "12-0",
  "event_type": "message",
  "timestamp": "2026-10-20T02:50:00Z",
  "data": {}
}
```

支持事件：

| 事件名 | `data` 内容 |
|---|---|
| `start` | 空对象；表示本次执行阶段开始。 |
| `message` | `operation=delta` 含 `message_id`、`block_id`、文本块内字符偏移 `offset` 和 `text`；`operation=snapshot` 含 `message_id` 和完整 `content.blocks`。每块有稳定 `id`，类型为 `text`、`image`、`question` 或 `task_result`。偏移使历史快照已含该增量时可安全重放。图片 URL 为应用内受授权路径；完整 Listing/Research 结果由 `task_result_id` 获取。 |
| `status` | 工具进度等临时状态，含 `status`、工具名称等有界字段；不承载完整任务结果。 |
| `end` | `status` 为 `completed`、`waiting`、`cancelled` 或 `failed`；失败时含 `error.code` 和 `error.message`。`waiting` 只结束本阶段，答案提交后原 run 再次发送 `start`。 |
| `heartbeat` | 空对象，仅维持连接；复用当前游标，不推进业务事件序号。 |

同一消息的增量、完整快照和数据库记录使用相同的 `message_id`；增量与快照中的对应文本块使用相同的 `block_id`/块 `id`。追问题卡和关联任务结果先保存到历史消息，再发送快照，之后发送 `end(waiting)`。

切换时不读取旧协议事件。新版使用独立 Redis v2 事件键，旧键不参与新监听并按既有 TTL 过期。部署时需停止旧版 API/Worker 写入并处理旧版 queued/running 任务；等待中的运行可由数据库题卡和 Checkpoint 恢复。

图片状态包括 `pending`、`awaiting_input`、`running`、`succeeded`、`failed` 和 `cancelled`。图片结果事件中的 URL 是应用内路径，不含 TokenHub 临时签名地址或密钥。生成事件写入 Redis Streams，默认每个 run 保留最多 2,000 条、24 小时；事件流过期不会删除 PostgreSQL 中的会话历史。

Redis Stream 正文按配置 TTL 过期；活动和等待回答的 run 会保留轻量的 sequence/latest 游标元数据，以便事件正文过期后的续跑仍使用递增 ID。completed、failed 或 cancelled 的游标元数据会随事件 TTL 过期；waiting 不清理游标，直到同一 run 恢复并最终结束。

聊天任务进入 Celery `agents` 队列，Redis 同时提供 Broker 和有界事件回放存储。关闭或切换 SSE 连接只结束监听；只有显式调用 cancel 接口才会设置共享停止信号。本地 Compose 的单个 Worker 同时消费 `agents` 和文献任务使用的默认 `celery` 队列，并以 `solo` 单并发模式串行执行。部署可配置 `AGENT_EVENT_MAX_LENGTH`、`AGENT_EVENT_TTL_SECONDS`、`AGENT_EVENT_REDIS_TIMEOUT_SECONDS` 和每个 Agent Worker 实例唯一的 `AGENT_WORKER_SNOWFLAKE_ID`。

所有结构化追问都使用统一题目结构：`type` 为 `SingleChoice` 或 `MultiChoice`；`title` 包含完整问题；`options` 恰好有 4 个互不重复的对象，每项包含 `label`（最多 100 字符）和 `description`（最多 300 字符）；`allow_custom_input` 固定为 `false`。题目不包含 `prompt` 或 `placeholder`。题目 ID 使用英文 snake_case，题目和选项文本会去除两端空白并拒绝空值或多行内容。恢复运行和读取历史题卡遵循同一协议；通用对话通过普通自然语言消息澄清，不产生结构化文本题卡。

以下 Listing 事件数据示例同样适用于其他智能体：

```json
{
  "questions": [
    {
      "id": "material",
      "title": "请确认商品的主要材质。",
      "type": "SingleChoice",
      "options": [
        {"label": "棉", "description": "商品主体由棉制成"},
        {"label": "涤纶", "description": "商品主体由涤纶制成"},
        {"label": "混纺", "description": "商品主体由多种纤维混合制成"},
        {"label": "不确定/暂不提供", "description": "暂时无法确认材质"}
      ],
      "allow_custom_input": false
    }
  ],
  "question_round": 1,
  "max_question_rounds": 3
}
```

### GET /api/task-results/{task_result_id}

读取 Listing 或科研文献检索任务的完整 JSON 结果。接口按可信主体执行任务结果所有者校验；结果不存在、属于其他主体或不是允许公开的结果类型时统一返回 HTTP 404。

成功响应的 data 包含 task_result_id、agent、result_type、generation_status 和 result_data。Listing 结果包含商品事实、图片识别结果及 3 个版本；Research 结果的 result_type 为 research_search，result_data 含检索状态、筛选条件、数量和标准化论文列表。接口不返回输入快照、图片字节、OSS 内部对象键或模型凭据。

## 上传参考图片

### `POST /api/uploads/images?agent=image_agent&file_name=product.png`

请求体是图片原始字节（不是 multipart 或 JSON）；请求头 `Content-Type` 不作为文件类型依据。服务端按文件签名识别 PNG/JPEG，单张最多 5 MiB。最多可在同一聊天请求中提交 3 个附件 ID。

```http
Content-Type: image/png

<PNG 原始字节>
```

成功响应：

```json
{
  "success": true,
  "data": {
    "attachment_id": "<attachment_id>",
    "file_name": "product.png",
    "mime_type": "image/png",
    "file_size": 12345
  }
}
```

附件暂存在阿里云私有 OSS；发送聊天请求时按当前主体校验并绑定到用户消息。`messages.content` 的图片块保存附件 ID，数据库不创建附件表，也不保存参考图字节。对象键和引用图片元数据可随任务输入保存在 `task_results.input` 中。

## 读取生成图片

### `GET /api/task-results/{task_result_id}/image`

成功时以 `image/png` 或 `image/jpeg` 返回阿里云 OSS 中的图片字节。只有结果所有者可以读取；不存在、未完成或其他用户的结果均返回 HTTP 404。结果地址是稳定应用路径，TokenHub 临时链接会在服务端立即下载并转存。数据库 `task_results.result` 保存对象键、MIME、大小和图像尺寸，不保存图片字节。

使用图片上传或读取接口时，后端必须配置 `ALIYUN_OSS_ACCESS_KEY_ID`、`ALIYUN_OSS_ACCESS_KEY_SECRET`、`ALIYUN_OSS_ENDPOINT` 和 `ALIYUN_OSS_BUCKET`。未配置时图片上传返回 HTTP 503；OSS 操作失败返回受控 HTTP 502。Bucket 必须保持私有，前端不直接访问 OSS。

## 文献解读助手

文献助手使用独立 API；通用 `/api/agents/{agent}/chat` 路由会拒绝该智能体，确保每次问答都绑定用户选择的文献。文献元数据和处理状态存入 PostgreSQL，PDF 原件放入私有 OSS，正文分块和向量保存在 PostgreSQL + pgvector。PDF 解析、切分和向量化由 Celery Worker 异步执行，Redis 为 Broker。

### `POST /api/v1/literature/documents`

以 `multipart/form-data` 字段 `file` 上传 PDF。单个文件默认上限 30 MiB。成功返回 HTTP 202 和 `{ "document_id": "...", "status": "queued" }`；Worker 处理完成后变为 `ready`，无法解析时为 `failed`。

### `GET /api/v1/literature/documents?limit=20&offset=0`

返回当前主体文献库摘要及 `queued`、`processing`、`ready`、`failed` 状态，支持 1–100 条分页。`GET /api/v1/literature/documents/{document_id}` 可读取单篇状态；`DELETE` 删除文献、分块、会话文献关系和 PDF OSS 原件。

### `GET/PUT /api/v1/literature/conversations/{conversation_id}/documents`

GET 返回历史会话当前选中的 `document_ids` 和摘要。PUT 的 JSON 结构为 `{ "document_ids": ["..."] }`，替换会话关联；允许空数组以清除选择。仅能关联当前主体拥有且状态为 `ready` 的文献。新会话在首次问答时创建此关系。

### `POST /api/v1/literature/chat/stream`

通过 SSE 提问。JSON 请求包含 `message`、可选的 `conversation_id` 和 `document_ids`。新会话首轮必须提供 1–10 个已就绪文献 ID；继续历史会话时可传 ID 更新选择，或省略以沿用已保存选择。模型只接收这些文献的检索证据。回答为中文；每项事实须附模型从原文逐字摘录的片段，服务端确认摘录属于对应证据后生成 PDF 章节、页码和段落标注；章节无法识别时会明确说明。总结和比较任务要求每篇所选文献均检索到足够证据并出现在最终回答中；依据不足或引用校验失败时明确弃答。事实支持关系由模型复核，因此仍需用真实文献语料进行效果验收。

部署需配置 `TENCENT_TOKENHUB_API_KEY`、私有 OSS 参数、Redis 和唯一的 `LITERATURE_WORKER_SNOWFLAKE_ID`；执行 `backend/migrations/005_literature_reader.sql` 后启动 API 与消费默认 `celery` 队列的 Celery Worker。本地 Compose Worker 同时监听文献 `celery` 队列和聊天 `agents` 队列。

## 会话历史

- `GET /api/conversations?limit=50&offset=0` 返回会话列表，其中每项有 `agent` 和会话标题。新会话的标题由首条用户消息生成；模型命名不可用时，服务端回退为首条消息摘要。
- `GET /api/conversations/{conversation_id}/messages?limit=50&before_message_id=...` 返回按 `(created_at, message_id)` 时间正序排列的消息。新写入的 `content.blocks` 均有稳定 `id`，支持文字、图片、追问和任务结果块；追问块包含 run、轮次和问题/选项，答案以同类问题块中的 `answers` 与 `question_titles` 保存。旧历史块缺少 `id` 时由服务端读取投影确定性补齐。图片块含 `attachment_id` 和服务端补充的 `image_url`，不含图片字节。助手消息可含 `task_results` 数组。
- `GET /api/conversations/{conversation_id}/messages/{message_id}/attachments/{attachment_id}/image` 以 PNG/JPEG 返回消息内引用的上传图片；会话、消息或附件不属于当前用户时返回 404，OSS 读取故障返回 502。部署升级时依次执行 `backend/migrations/006_message_context.sql` 和 `backend/migrations/007_rename_message_context_to_content.sql`，再启动新版后端。

## listing生成智能体

listing_agent 使用配置的 DeepSeek ChatModel（默认 `deepseek-flash`）通过多模态 Chat Completions 识别商品外观、可读包装文字和可见特征，并使用同一模型判断必要信息及生成文案。图片以 Base64 `image_url` 内容块传入，模型名称、鉴权、地址和超时均使用现有 `DEEPSEEK_MODEL`、`DEEPSEEK_API_KEY`、`DEEPSEEK_BASE_URL` 和 `DEEPSEEK_TIMEOUT_SECONDS` 配置。TokenHub 仍用于 `image_agent` 的生图能力。

Listing 请求必须带至少一张 PNG/JPEG 图片附件；每次最多 3 张、每张不超过 5 MiB。商家可在消息中补充任意已知信息。智能体根据图片观察和商家文字判断必要问题，每轮可返回最多 3 道当前最重要的问题；回答后再评估是否需要追问。问题结构遵循统一题卡规则。一次运行最多追问 3 轮；第三轮答案提交后直接生成，并省略无法确认的属性，不将其猜测为事实。

成功 JSON 包含恰好 3 个版本，每个版本有标题、卖点、纯文本详情描述、关键词和商品属性，保存在 `task_results.result`。完整结构通过 GET /api/task-results/{task_result_id} 读取；SSE 只发布任务结果摘要。

## 图片智能体参数

`image_agent` 使用 TokenHub Hy-Image-3.5-preview。用户未明确提供尺寸或面积档位时，题卡以 4 个画幅比例选项询问；用户已在原始请求中给出尺寸或档位时直接采用，不重复询问。`seed` 和 `footnote` 只从用户主动提供的值中读取，未提供水印时不加水印，未提供 seed 时不传 seed。参考图 `resize_max_pixels` 只采用用户明确提供的值；未指定时使用 TokenHub 默认面积 1,048,576，不额外追问。参考图最多 3 张，每张最多 5 MiB。`session`、`model` 和 `messages` 由服务端组装。API 文档没有定义输出张数或独立清晰度参数，因此接口和问答不引入这两个字段。完整上游字段及限制请见[腾讯混元生图接入文档](https://cloud.tencent.com/document/product/1823/135745)。

## 科研文献检索智能体

research_agent 可从智能体选择器使用通用聊天 SSE，也提供一次返回结构化结果的 REST 接口。REST 请求复用 Agent Runner、当前用户的会话和 task_results；session_id 是数字雪花 conversation_id 的别名。新会话省略该字段，后续请求传回响应中的 ID。

### POST /api/v1/research/search

请求字段示例：

~~~json
{
  "message": "检索 2020 年以来关于图神经网络的英文论文",
  "session_id": null,
  "limit": 10,
  "year_from": 2020,
  "year_to": 2025,
  "language": "en",
  "sort": "relevance"
}
~~~

message 必填且长度为 2–20,000；limit 范围为 1–50。session_id 可省略，或使用数字雪花 ID。年份、语言和排序条件可选；支持 relevance、citation_count 和 publication_date。显式年份与语言筛选由服务端固定应用到所有查询轮次。

成功响应使用项目统一 envelope，data 字段形如：

~~~json
{
  "success": true,
  "data": {
    "session_id": "123456789012345678",
    "status": "success",
    "query": "检索 2020 年以来关于图神经网络的英文论文",
    "papers": [
      {
        "id": "https://openalex.org/W123",
        "title": "论文标题",
        "authors": ["作者姓名"],
        "year": 2024,
        "language": "en",
        "publication_date": "2024-06-01",
        "venue": "期刊名称",
        "abstract": null,
        "doi": "10.example/example",
        "citation_count": 12,
        "paper_url": "https://openalex.org/W123",
        "pdf_url": null,
        "source": "OpenAlex"
      }
    ],
    "returned_count": 1,
    "message": "找到符合条件的论文。"
  }
}
~~~

status 为 success、partial、no_results 或 failed。有效查询无匹配论文时仍返回 HTTP 200 和 no_results；已取得部分可用结果时返回 partial。论文完整字段保存在 `task_results.result`，Checkpoint 和 SSE 工具事件只携带任务 ID、业务状态和数量摘要。OpenAlex API Key 可选，通过 OPENALEX_API_KEY 配置；超时、有限重试和最多 3 轮查询由 OPENALEX_TIMEOUT_SECONDS、OPENALEX_MAX_RETRIES、OPENALEX_RETRY_DELAY_SECONDS 和 RESEARCH_MAX_SEARCH_ROUNDS 控制。

GET /api/task-results/{task_result_id} 按所有者读取该结果的完整论文 JSON；越权、未知和未公开的结果类型统一返回 HTTP 404。
