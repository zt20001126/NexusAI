## 1. 产品概述

新增一个面向淘宝中国站商家的 listing生成智能体。商家上传商品图片，并用自然语言补充已知信息。智能体识别图片中的商品外观、可读包装文字和可见特征，判断生成 Listing 所需的信息是否齐全；发现必须由商家确认的信息时，将全部当前问题一次性列出。收到回答后，智能体生成 3 个可选版本，并把完整 JSON 保存到项目现有的任务结果表。

本能力是独立智能体，稳定标识为 listing_agent。它复用项目共享的 Agent Runner、结构化追问、Checkpoint、SSE、附件存储和 task_results，不修改默认智能体或淘宝图片生成智能体的业务流程。

## 2. 目标与非目标

### 2.1 目标

- 商家可以只提供商品图片和零散文字，不必预先了解 Listing 所需字段。
- 智能体能够把图片观察、包装 OCR、用户提供信息和用户确认信息分开处理。
- 智能体根据商品类别和已知资料判断必要字段缺口，并一次性提出所有当前待确认问题。
- 必须确认的商品事实由商家回答；提示词要求不得把无法从图片确认的材质、规格、功效或认证写成事实。
- 每个生成版本均包含标题、卖点、详情描述、关键词和商品属性。
- 所有版本以结构化 JSON 完整写入统一任务结果表，并可由结果所有者读取和选择。

### 2.2 非目标

- 不调用淘宝商家后台或商品发布 API，不自动发布商品。
- 不生成商品主图、详情页图片或其他图像资产。
- 首版不承诺自动同步淘宝实时类目属性、标题规则或违禁词规则；可维护的类目字段配置和内容校验规则另行建设。
- 不以商品图片推断不可见的商品事实，也不替商家背书其真实性。

## 3. 用户角色

| 角色 | 目标 |
|---|---|
| 淘宝商家 | 用商品图片和已知信息快速获得多套 Listing 文案，并补齐必须确认的商品信息 |

## 4. 输入与输出

### 4.1 输入

- 必需：至少一张商品图片；每次最多 3 张 PNG/JPEG，每张最多 5 MiB。
- 可选：商家以自然语言提供的商品名称、品牌、规格、卖点、目标买家等已知信息。
- 追问答案：按结构化问题 ID 提交的商家确认信息。

不要求商家在初次提交前填写固定字段表。智能体先处理图片和自由文本，再决定要向商家询问什么。

### 4.2 输出

每个版本具有相同字段：

- 标题：文本。
- 卖点：有序文本列表。
- 详情描述：纯文本，可保留自然段换行，不使用 Markdown 或 HTML。
- 关键词：文本列表。
- 商品属性：属性名称到属性值的 JSON 对象；只填写明确已知的属性。

## 5. 核心用户流程

1. 商家选择 listing生成智能体，上传商品图片并提交已知信息。
2. 智能体识别图片中的外观、可读包装文字和可见特征，整理商家提供的信息。
3. 智能体根据商品类别、图片可见信息和商家资料判断必须核实的字段。
4. 如有必要信息缺口，智能体在同一个问题事件中列出全部当前问题。
5. 商家回答后，智能体合并答案并检查仍未解决的必要字段；只对未完成的问题继续追问，不重复已确认问题。
6. 信息满足生成条件后，智能体生成多个版本，校验结构和事实来源。
7. 智能体将完整 JSON 写入 task_results.result_data，前端展示版本并允许商家选择。

## 6. 功能需求

### 6.1 图片和信息接收

- 智能体注册信息声明支持图片上传。
- 图片上传继续通过项目既有授权接口执行；附件必须属于当前可信主体，并绑定至会话和运行。
- 图像内容只在后端授权流程中从私有 OSS 读取，不将 OSS 对象键或访问密钥传给模型或前端。
- 商家可以在初次消息中以自然语言给出任意已知资料，不强制使用未确认的固定表单。

### 6.2 商品识别和事实分层

图片理解 Provider 输出结构化观察，至少包含：

- 候选商品类别。
- 图片中直接可见的外形、颜色、图案、结构、包装元素。
- 可辨认的包装文字。
- 无法识别或需要商家确认的内容。

图片只能证明可见内容；例如无法仅凭外包装可靠确认的材质、实际尺寸、功效、适用范围、认证和安全声明必须向商家提问。无法确认的包装文字和观察会进入不确定观察字段。

### 6.3 信息完整性判断与追问

- 由智能体结合商品类别判断必要信息；首版不维护固定类目属性目录。
- 类目不明确或必要信息缺失时，生成结构化问题。
- 首轮追问一次列出所有当前能确定的问题，不逐题等待。
- 问题需有稳定 ID、标题、说明、答案类型和必要时的示例，兼容现有 question.required / resume 协议。
- 前端要求回答当前批次的全部问题，后端按问题 ID 校验并拒绝空白答案；明确回答“不清楚”等内容会作为未知状态处理，不得被模型补造。
- 必要字段仍缺失时继续等待并只询问未解决项；选填字段可省略。

### 6.4 多版本内容生成

- 只有必要字段完成核实后才生成。
- 固定生成 3 个版本，每个版本均包括标题、卖点、纯文本详情描述、关键词和商品属性。
- 各版本表达角度应有清晰差异，但所有版本必须使用同一份已确认商品事实。
- 提示词要求只使用商家信息、明确回答和图片直接可见内容，不补造不可验证事实。
- 生成结果必须通过本地 Pydantic Schema 校验；校验失败时任务以受控失败结束。

### 6.5 结果保存、读取与展示

- 使用统一 task_results 表，result_type 为 listing；不创建专门的 Listing 输出表。
- generation_status 沿用 pending、awaiting_input、running、succeeded、failed、cancelled。
- succeeded 时将完整 JSON 写入 result_data；输入文本、答案、附件元数据及识别快照按需写入 input_data，不把图片二进制写入 PostgreSQL。
- 使用任务结果所有者校验保护完整 JSON 读取接口。
- 前端按版本卡片展示标题、卖点、详情描述、关键词和属性，支持商家查看并选择版本。
- SSE 事件只发送任务结果标识、类型和状态等摘要；完整内容由授权结果读取接口获取。

## 7. 页面与模块结构

### 前端

- 智能体选择器：从智能体发现接口读取 listing_agent。
- 聊天输入区：支持图片上传和自然语言商品信息。
- 追问表单：使用现有结构化问题组件，一次展示当前全部问题。
- Listing 结果区：按版本展示各输出字段，提供版本选择。

### 后端

- 独立 Listing 图：负责图像理解、信息补全、追问、生成和结果落库。
- 视觉 Provider：调用 TokenHub 混元视觉模型并输出有界结构化观察。
- 信息规划节点：由模型根据当前商品信息判断必要字段缺口并一次性给出问题批次。
- 文案生成 Provider：调用 DeepSeek 生成符合 schema 的多版本内容。
- 任务结果读取接口：按可信主体返回 Listing JSON。

## 8. 验收标准

- 商家能通过智能体发现接口找到 listing_agent，并能为其上传图片。
- 图片观察、用户原始输入和问题答案分别保存在运行状态及任务输入元数据中。
- 缺少多个必要信息时，一次性收到包含全部当前问题的结构化追问。
- 提示词要求必要核实的事实未经商家回答时，不得写入标题、卖点、描述或属性。
- 提交答案后可恢复原运行，已回答内容不重复提问。
- 成功结果是有效 JSON，所有版本均含五类约定字段。
- 完整 JSON 持久化到统一 task_results.result_data，并通过用户所有权校验的接口读取。
- 未授权用户不能读取其他用户的任务结果或图片附件。
- Provider 超时、格式错误或数据库失败时返回安全、稳定的错误状态，不泄露密钥和上游原始响应。

## 9. 非功能需求

### 性能与可靠性

- 视觉理解调用配置超时和安全错误映射；文案模型沿用已有有限重试配置。
- 继续使用现有 SSE、运行取消和 Checkpoint 恢复能力，不增加首版消息队列。
- Listing 版本数固定为 3；沿用最多 3 张、每张 5 MiB 的图片上限，并限制输出字段长度。

### 安全与隐私

- 延用可信主体、会话归属、附件访问和任务结果所有权检查。
- 图片字节留在私有 OSS；数据库只保存对象元数据和业务 JSON。
- 不记录图片 Base64、模型密钥、完整上游响应或未经清洗的敏感内容日志。
- 商品资料和模型输出按用户授权边界访问。

### 扩展性

- 智能体目录与默认智能体、淘宝图片生成智能体隔离。
- 模型 Provider 通过依赖注入；首版由信息规划提示词判断必要字段，后续可增加确定性的类目规则。
- 结果 schema 有版本号，后续增加字段时可兼容已有 JSON 结果。

## 10. 已确认决策

1. 智能体稳定标识为 listing_agent。
2. 每次生成 3 个版本。
3. 详情描述为纯文本。
4. 必要问题不能留空或跳过；一次展示当前全部问题。
5. 首版由智能体根据商品类别判断必要问题，不维护固定类目字段目录。
