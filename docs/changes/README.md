# 任务级变更记录

在 `docs/changes/` 为每个重要开发任务保存一份独立记录。新功能、缺陷修复、核心逻辑或架构调整、公共接口或数据模型变化，以及重要工程化改造都应记录。拼写修复、纯格式调整和无业务影响的简单清理通常不必单独记录。

文件名格式为 `YYYY-MM-DD-序号-简短英文描述.md`，例如 `2026-10-03-001-add-change-log-process.md`。序号按日期分别从 `001` 开始；创建前先检查当天已有记录，选择尚未使用的下一个序号。描述使用简短英文、小写和连字符。

任务记录基于实际差异，写明实际执行的检查及结果；未执行检查时说明原因，不猜测或补写历史。根目录 [`CHANGELOG.md`](../../CHANGELOG.md) 面向项目使用者，汇总未发布及已发布变化；它与任务级记录用途不同，两者都不替代 Git commit。发布时将已发布条目整理到版本标题下，并保留空的 `[Unreleased]` 区域。

## 模板

复制以下模板，为每项重要任务新建文件：

```markdown
# <任务标题>

- 日期：YYYY-MM-DD
- 变更类型：<新功能 / 缺陷修复 / 架构 / 工程化 / 文档 / 其他>
- 影响范围：<受影响的组件、用户或流程>

## 背景

<为什么需要这项变更；只写已知事实。>

## 变更内容

- <实际完成的内容>

## 涉及文件

- `<路径>`：<实际变化>

## 设计决策

- <采用的方案及已知理由；没有特别决策时写“无”。>

## 测试与验证

- 命令：`<实际执行的命令>`
- 结果：<实际观察到的结果>

<若未运行检查，写明未运行的原因。>

## 潜在影响

- <已知影响或风险；没有已知项时写“暂无已知影响”。>

## 后续事项

- <已确认的后续工作；没有时写“无”。>
```
